# ADR 0001 : 저장소 해시를 키 있는 SipHash-2-4 로 바꾼다

## 상태

- 채택
- 날짜 : 2026-11-17

## 배경

- v1.0.0 의 `hash_key` 는 고정 상수를 쓰는 FNV-1a 입니다.
- 상수가 공개돼 있어서 누구나 같은 값을 계산할 수 있습니다.
- 공격자는 같은 버킷으로 몰리는 키 N개를 미리 만들어 SET 으로 보냅니다.
- 그러면 한 버킷의 체인 길이가 N 이 됩니다.
- 체인 끝까지 따라가며 비교해야 하므로 N개를 넣는 전체 비용이 O(N^2) 이 됩니다.
- 서버는 단일 스레드라서 그동안 모든 클라이언트가 멈춥니다.
- 이것이 해시 충돌 공격(hash flooding)입니다.

## 결정

- 서버 시작 때 운영체제 난수로 무작위 128비트 키를 한 번 뽑습니다.
- 그 키로 SipHash-2-4 를 계산해 버킷을 정합니다.
- 키는 프로세스 안에만 있고 파일에 저장하지 않습니다.
- 난수를 얻지 못하면 예측 가능한 키로 돌리지 않고 `store_init` 이 실패합니다.

## 검토한 대안과 버린 이유

1. FNV-1a 에 무작위 시드만 섞기
   - 구현은 가장 쌉니다.
   - 하지만 시드와 무관하게 FNV 내부 상태가 같아지는 충돌 입력이 남을 수 있습니다.
   - 그런 입력은 시드를 몰라도 만들 수 있으므로 막는다는 근거가 약합니다.
2. SHA-256
   - 키가 없는 해시라서 공격자도 똑같이 계산할 수 있습니다.
   - 짧은 키 하나에 쓰기에는 느립니다.
3. 체인 대신 다른 충돌 처리 방식
   - 저장소 구조 전체를 바꾸는 일이라 이번 범위 밖입니다.

## 결과

얻는 것

- 키를 모르는 공격자가 같은 버킷으로 몰리는 키를 미리 계산할 수 없습니다.
- 테스트로 입증할 수 있는 근거가 생겼습니다 (아래 검증).

내주는 것

- 짧은 키에서는 FNV-1a 보다 느립니다.
- 벤더링한 소스 파일 `src/siphash.c` 하나가 늘었습니다.
- 서버가 시작될 때마다 버킷 배치가 달라져 순회 순서(스냅샷 저장 순서)가 실행마다 달라집니다.

공개 API 변화

- `store_init_with_key(Store *, const uint8_t key[16])` 추가 : 테스트가 키를 직접 줍니다.
- `store_longest_chain(const Store *)` 추가 : 가장 긴 체인 길이를 돌려주는 진단 함수입니다.
- `store_init` 의 시그니처는 그대로입니다.

저장 형식

- 스냅샷과 AOF 는 해시 값을 저장하지 않으므로 형식이 바뀌지 않습니다.
- 기존 파일은 그대로 읽힙니다.

## 검증

- `tests/test_siphash.c`
  - 참조 저장소의 공식 테스트 벡터 64개(길이 0부터 63)와 `siphash24` 출력을 대조합니다.
  - 구현이 SipHash-2-4 와 같다는 것을 증명합니다.
- `tests/test_store.c` 의 `test_old_collision_keys_spread`
  - 옛 FNV-1a 의 하위 12비트가 모두 0 인 키 1000개를 모읍니다.
  - 옛 해시에서는 전부 같은 버킷이므로 체인 길이가 1000 이었습니다.
  - 같은 키를 SipHash 저장소에 넣었을 때 측정한 가장 긴 체인은 4 였습니다.
  - 1000개 모두 GET 으로 조회됩니다.
- `tests/test_store.c` 의 `test_hash_key_changes_bucket_layout`
  - 키가 다른 두 저장소는 같은 문자열을 다른 버킷에 넣습니다.
  - 같은 키로 만든 저장소는 같은 버킷에 넣습니다.
- 증명하지 못한 것
  - SipHash 의 암호학적 강도는 이 테스트로 증명하지 않습니다. 참조 구현과 공개된 분석을 믿습니다.

# Mini DBMS 구조

## Phase 1 — SQL 처리기

### 요청 흐름

`main.c` → `cli.c` → `db_open` → `db_execute_sql` → `result_print_text` → `db_close` 순서다. CLI는 옵션과 SQL 입력만 처리하며 SQL 실행은 반드시 `db_execute_sql`을 통한다. 입력을 끝까지 읽고 I/O 오류와 NUL 바이트를 검사한 뒤 데이터베이스를 연다. 파일 읽기 실패로 불완전한 SQL이 실행되는 것을 막는다. 시작의 UTF-8 BOM은 제거한다. `run -`는 읽기 전에 `os_stdin_binary`를 호출한다. Windows에서는 `_setmode`로 이진 모드를 설정하여 0x1A와 CRLF를 파일 입력과 똑같이 읽으며 POSIX에서는 아무 작업도 하지 않는다.

`db_open`은 데이터 폴더를 잠그고 `catalog.txt`를 읽어 모든 테이블을 연다. 카탈로그는 시작 이후 읽기 전용이다. 폴더와 카탈로그는 미리 있어야 하며 테이블 파일은 없으면 생성한다. 실패하면 이미 열린 테이블과 폴더 잠금을 해제한다.

`db_execute_sql`은 문자열·이스케이프·주석을 구분하여 문장을 나누고 각 문장을 `parse_sql`에 넘긴다. 내부 흐름은 lexer(줄·칸이 있는 토큰) → parser(Statement) → executor다. 뒤 문장의 구문 오류도 앞 문장의 실행을 취소하지 않는다. 첫 오류에서 멈추며 결과에는 성공한 문장만 남는다. 트랜잭션은 없다. `committed`는 성공한 문장 수이며 SELECT도 포함한다. 여러 행 INSERT 는 문장 단위로 원자적이다(아래 INSERT 절). 실패한 문장은 행을 하나도 남기지 않으므로 `committed`, 파일, 인덱스가 서로 어긋나지 않는다.

executor는 스키마·컬럼·타입·값 개수를 확인하고 INSERT 또는 SELECT를 수행한다. id는 자동 부여하며 사용자가 지정하면 오류다. Phase 1의 SELECT는 id 조건도 모두 선형 탐색(`plan=scan`)이다. 결과는 행, 실행 계획, 조사한 행 수, 소요 시간을 소유하고 `result_free`로 해제한다. CLI는 앞 결과와 오류를 출력하고 종료 코드 1을 반환한다.

`DbError.kind`는 문법·의미·타입 오류인 `DB_ERROR_SQL`과 파일 I/O·메모리·락·저장 데이터 손상 등의 `DB_ERROR_INTERNAL`을 구분한다. SQL 오류는 기존 `error at L:C: …` 형식을 유지한다. 옵션 오류와 NUL 입력 오류는 위치 0:0이며 카탈로그 형식 오류는 카탈로그 위치를 유지한다. 내부 오류는 위치를 0:0으로 두고 `internal error: …`로 출력한다. executor나 문장 위치 보정이 내부 오류에 SQL 위치를 덧씌우지 않는다. 향후 서버가 종류에 따라 400/500을 선택할 수 있는 정보만 마련했으며 서버는 구현하지 않았다.

### 파일 형식과 불변식

- 카탈로그: 기본 `data/catalog.txt`, `테이블 : 컬럼 타입, ...` 형식. 첫 컬럼은 항상 `id INT`다. 테이블·컬럼 이름은 ASCII `[A-Za-z_][A-Za-z0-9_]*`이며 최대 63바이트다. lexer가 키워드로 분류하는 모든 단어(`INSERT`, `INTO`, `VALUES`, `SELECT`, `FROM`, `WHERE`, `LIMIT`)는 대소문자를 무시하고 이름으로 거부한다. lexer와 카탈로그가 `lex_identifier_kind`를 함께 호출하므로 키워드 목록은 lexer 한 곳에만 있다. 모든 플랫폼에서 대소문자를 무시한 중복 테이블 이름을 거부한다. SQL에서 이름을 찾는 동작은 기존처럼 대소문자를 구분한다.
- 테이블: `data/<table>.tbl`. `--data DIR`이면 해당 폴더 아래 같은 이름을 쓴다.
- 레코드: `[u32 payload 길이][u32 길이 검사값][u32 payload CRC32/IEEE][i64 id][필드들]`. 모든 정수는 리틀 엔디언이며 길이는 12바이트 헤더를 제외한다. 길이 검사값은 길이를 인코딩한 리틀 엔디언 4바이트의 `CRC32/IEEE XOR 0x4D444231`이다. payload CRC 범위는 id부터 payload 끝까지다. 기존 8바이트 헤더 및 `~길이` 검사값을 쓰던 12바이트 헤더 파일의 자동 변환은 제공하지 않는다.
- INT 필드: `[i64]`. TEXT 필드: `[u32 바이트 길이][바이트]`. 종결 NUL은 저장하지 않는다. TEXT는 최대 64 KiB, 헤더를 포함한 레코드는 최대 1 MiB다.
- 메타 레코드: 일반 레코드와 같은 헤더(길이 · 길이 검사값 · CRC)에 id 칸이 0이고 본문이 `[u8 종류][i64 값]`인 29바이트 레코드다 (일반 id 는 양수라 구별된다). 종류 1 = COMMIT (값 = 바로 앞 문장이 쓴 행 수), 종류 2 = ID_FLOOR (값 이하의 id 는 다시 쓰지 않는다). 메타 레코드는 행이 아니다: 탐색 · 위치 지정 읽기 · 인덱스 · 행 수 어디에도 행으로 나오지 않는다. 종류나 길이가 틀리거나 값이 0 이하면 손상이다.
- id는 양수이며 파일 순서대로 증가한다. 시작 때 다음 id = max(확정된 마지막 id, 본 ID_FLOOR 값들의 최댓값) + 1 이다. int64 범위를 소진하면 추가를 거부한다.

INSERT 한 문장은 쓰기 락 안에서 다음 순서로 실행한다 (계획의 "행마다 추가 · 동기화"에서 문장 단위 원자성으로 바꾼 설계 결정, 2026-11-18).

1. 문장 시작 위치 = Table 의 확정된 끝 위치를 기억한다.
2. 모든 행을 검증하고 레코드 크기를 계산한다. 하나라도 틀리면 파일을 건드리지 않는다.
3. 인덱스 노드를 행 n개 분량으로 먼저 확보한다 (`bpt_reserve_insert_range`). 실패하면 파일을 쓰기 전에 돌려준다.
4. n개 레코드를 모두 파일 끝에 쓴다. 한 번에 최대 1 MiB 블록으로 모아 `os_append`한다.
5. 기본 `sync always`면 동기화한다 (첫 번째).
6. COMMIT 레코드 (값 = n) 를 쓴다. `sync none` 이어도 COMMIT 은 쓴다.
7. `sync always`면 다시 동기화한다 (두 번째). 1000행 문장도 동기화는 2번이다. `sync none`은 두 동기화를 모두 생략한다.
8. 성공하면 확보한 노드만으로 n개를 인덱스에 등록하고(`bpt_insert_reserved`, 할당 없음) 확정된 끝 위치를 COMMIT 뒤로 옮기고 id를 공개하며 문장 하나를 committed 로 센다.
9. 3~7 어디서든 실패하면 (COMMIT 쓰기 · 동기화 포함) 1의 위치로 잘라 동기화하고 확보한 노드를 반납한다. 그 문장은 행이 하나도 남지 않으며 id 도 이어서 쓴다. 인덱스 등록 단계 (8) 가 실패하면 파일도 같은 방식으로 되돌린다. 이미 등록된 키를 인덱스에서 뺄 수는 없으므로 한 행이라도 등록됐으면 테이블을 `write_failed` 로 만든다. 되돌리기도 실패하면 어느 경우든 `write_failed` 다.

CLI는 실행 후 표준 오류에 마지막 동기화 뒤 쓴 행은 OS 장애 시 잃을 수 있다는 범위와 이번 실행의 실제 추가 행 수(성공한 문장의 행만)를 표시한다. 되돌리기(자르기 또는 동기화)까지 실패한 테이블은 닫고 다시 열기 전까지 추가를 거부한다.

**확정된 끝 위치.** Table 은 `end` 를 가지며 문장이 성공했을 때만 늘린다. `table_scan` 과 `table_read_at` 은 `end` 까지만 본다. 되돌리기가 실패해 파일에 확정 안 된 바이트가 남아도 같은 Db 의 SELECT 는 그것을 보지 못하므로 id 조회(인덱스)와 name 탐색(scan)이 같은 결과를 낸다. 남은 바이트는 다시 열 때 아래 시작 복구 규칙이 처리한다. 확정 안 된 행에는 COMMIT 이 없으므로 다시 열면 일부든 전부든 사라진다 (문장 확정 레코드, 2026-11-18). 단 COMMIT 까지 파일에 써진 뒤 그 동기화나 되돌리기가 실패한 경우는 COMMIT 이 살아 있을 수 있어 다시 열면 문장이 확정으로 보일 수 있다 (호출자는 실패를 받았지만 디스크는 확정 — 쓰기는 끝났으나 확정 응답은 못 한 경우와 같다).

### 시작 복구와 실패 정책

시작할 때 파일 전체를 훑어 길이·CRC·필드 형식·id 증가를 검사한다. 오프셋 `off`에서 다음 순서로 분류한다. 이 분류는 레코드 하나의 모양에 대한 것이고, 문장 단위 규칙(보류 · 확정)은 그 아래에 따로 있다.

1. 남은 바이트가 헤더 12바이트보다 적으면 끝 잘림이다.
2. `off`부터 파일 끝까지 전부 0이면 0으로 채워진 끝 잘림이다. 헤더만 0이고 뒤에 비영 바이트가 있으면 이 규칙에 해당하지 않는다.
3. 검사값이 길이 4바이트의 `CRC32/IEEE XOR 0x4D444231`과 다르거나 길이가 0 또는 상한 초과면 손상이다.
4. 정상 헤더의 본문이 파일 끝을 넘으면, 즉 `파일 끝 − off < 12 + 선언된 길이`이면 꼬리를 추가 검사한다. `off + 1`부터 바이트마다 헤더를 시도하여 허용 길이·길이 검사값·본문 CRC가 모두 맞고 파일 안에 온전히 들어 있는 레코드가 하나라도 있으면 손상이다. 후보의 필드 형식이나 id 순서와 무관하게 거부한다. 그런 레코드가 없을 때만 끝 잘림이다. 헤더 포함 레코드 상한이 1 MiB이므로 이 경우 꼬리는 1 MiB보다 작으며 기존 블록 버퍼 안에서 검사한다.
5. 본문이 모두 있는데 CRC가 다르면 손상이다. CRC가 맞아도 필드 형식이나 id 증가 규칙이 틀리면 손상이다.

끝 잘림은 `off`로 자르고 동기화한 뒤 표준 오류에 `N bytes of incomplete tail truncated at offset X`를 남긴다 (끝나지 않은 문장이 있으면 아래 보류 규칙이 먼저 적용된다). 손상은 파일을 그대로 두고 시작을 거부하며 오프셋을 오류에 남긴다. `--repair`를 지정했을 때만 첫 손상 지점부터 이후를 모두 잘라낸다. 읽기·메모리 확보 같은 운영 실패는 repair로도 잘라내지 않는다.

**문장 확정 규칙 (보류 · 확정).** 시작 복구는 레코드를 읽으며 COMMIT 이 나오기 전의 일반 레코드를 "보류" 로 모은다.

- COMMIT 의 값이 보류 수와 같으면 그 행들이 확정이다. 이때에만 행 수 · next_id 에 반영하고 인덱스 일괄 구축 콜백 (`TableOpenVisitor`) 에 넘긴다. 콜백은 확정된 행만 받는다.
- 값이 다르거나 보류가 없는데 COMMIT 이 나오면 손상이다 (시작 거부, `--repair` 로만 자른다).
- 보류가 있는데 COMMIT 이 아닌 메타 레코드 (ID_FLOOR) 가 나오면 손상이다. 보류 중에는 COMMIT 만 올 수 있다.
- 파일 끝에서 COMMIT 없이 남은 보류 (와 그 뒤의 끝 잘림) 는 "끝나지 않은 문장" 이다. 보류가 시작한 위치에서 자동으로 자르고 동기화하며 표준 오류에 `incomplete statement: N records (M bytes) truncated at offset X` 를 남긴다. 앞 문장은 그대로다.
- ID_FLOOR 레코드는 값을 다음 id 의 하한으로 반영한다. 그 뒤의 행 id 는 하한보다 커야 한다 (id 증가 검사와 같다).
- `--repair` 가 보류 중에 손상을 만나면 그 문장의 시작부터 자른다 (문장의 앞쪽 행만 남기지 않는다).

`--repair` 는 조용히 지우지 않는다.

- 자르기 전에 잘라 낼 바이트 전체를 같은 폴더의 `<table>.tbl.repair-<YYYYMMDD-HHMMSS>` 로 복사하고 동기화한다. 같은 초에 이름이 겹치면 `-2`, `-3` … 을 붙인다. 복사가 실패하면 자르지 않고 내부 오류로 시작을 거부하며 반쯤 쓴 백업은 지운다.
- 잘라 낸 구간 (보류 중이던 문장의 시작부터 파일 끝까지) 을 바이트마다 훑어 헤더 검사값과 payload CRC 가 모두 맞는 레코드를 찾는다. 구간에서 본 모든 것의 최댓값 F 를 구한다 : 정상 레코드의 id (보류 행 포함 : 이미 클라이언트에게 준 id 일 수 있다), 구간 안 ID_FLOOR 값, 구간 안 COMMIT 으로 짐작되는 마지막 id (그 문장의 첫 id + COMMIT 행 수 − 1. 첫 id 는 문장의 정상 행 중 가장 앞 id, 없으면 직전 확정 id + 1), 그리고 손상 레코드 자신의 id 칸. 손상 레코드의 id 칸은 헤더 검사값이 맞고 값이 정확히 "그 직전까지 읽은 마지막 id (보류 행 포함) + 1" 일 때만 쓴다. id 는 1씩 늘므로 그 레코드가 원래 가졌을 id 는 그 값뿐이고, 다른 값은 깨진 쓰레기로 보아 무시한다. (옛 규칙은 기준을 "확정된 마지막 id" 로 잡아, 보류 행 2 · 3 뒤의 손상 행 4 를 무시하고 id 4 를 다시 주었다.)
- 자른 뒤 F 가 확정된 마지막 id 보다 크면 그 자리에 ID_FLOOR(F) 메타 레코드를 쓰고 동기화한다. 다음 id 는 F + 1 부터다. 이 하한은 파일에 남으므로 repair 를 한 실행이 SELECT 만 했어도, 다음 실행의 INSERT 가 잘려 나간 id 를 다시 쓰지 않는다. 쓰기가 실패하면 시작을 거부한다 (백업은 남아 있다).
- 표준 오류에 자른 위치 · 바이트 수 · 백업 파일 이름 · 잘라 낸 구간에서 찾은 정상 레코드 수와 id 범위를 한 줄로 남긴다 (`repair: cut N bytes at offset X, backup PATH, K intact records in the cut bytes, ids A..B`). 손상된 레코드 자체의 id 칸은 이 보고 범위에는 들지 않는다. 위 조건을 만족할 때만 ID_FLOOR 에 반영되므로 id 칸이 깨져도 id 가 크게 건너뛰지 않는다.

#### 복구 규칙의 알려진 한계 (2026-11-18 독립 재검증)

- 지키는 것 : 무작위 단일 손상. 첫 · 중간 · 마지막 레코드의 길이 · 검사값 · CRC 각 32비트를 하나씩 뒤집은 288건이 모두 파일 크기 그대로 시작 거부였다.
- 구별하지 못하는 것 : 길이와 길이 검사값이 서로 맞게 함께 바뀌고(무작위로는 약 2^-32), 그 뒤 레코드까지 손상돼 꼬리 안에 온전한 레코드가 남지 않은 복합 손상. 정상적인 "쓰다 멈춘 마지막 레코드" 와 바이트 모양이 같아서 끝 잘림으로 자른다. 자를 때는 표준 오류에 크기와 위치를 남긴다.
	- 길이 · 체크섬으로 프레임을 나누는 로그 형식이 공통으로 가진 한계다. 더 막으려면 마지막으로 동기화한 파일 크기를 따로 기록해야 한다 (지금 범위 밖).
- 거짓 양성 : TEXT 값 안에 "검사값과 CRC 가 모두 맞는 레코드 바이트" 가 그대로 들어 있고, 바로 그 레코드를 쓰다 멈췄으면 끝 잘림인데도 손상으로 보고 시작을 거부한다. 데이터는 지우지 않으며 `--repair` 로 앞 행을 유지한 채 복구된다.
- 선택 : 의심스러우면 지우지 않고 거부하는 쪽을 택했다 (조용한 삭제 < 시작 거부).

#### 다시 연 뒤에도 문장 원자성이 지켜지는 범위 (2026-11-18, 문장 확정 레코드)

- 지켜지는 것 : INSERT 문장은 COMMIT 이 파일에 있어야 행으로 인정된다. 쓰던 도중 실패해 되돌리기까지 실패한 경우, 1 MiB 를 넘는 문장을 쓰다 프로세스가 죽은 경우 모두 다시 열면 그 문장의 행은 0개이고 앞 문장은 그대로다 (실패 주입 테스트 : 전부 쓴 뒤 동기화 실패 · 일부만 쓴 뒤 append 실패 · 약 1.3 MiB 문장의 둘째 블록 쓰기 실패, 각각 truncate 실패와 함께).
- 한계 1 : 실제 전원 차단 · 커널 중단은 시험하지 않았다. 위 주장은 실패 주입(`os_test_fail_*`)으로 만든 파일 모양에 대한 것이다. 실제 장치가 쓰기 순서를 보장하는지 (행 쓰기가 COMMIT 쓰기보다 먼저 디스크에 닿는지) 는 첫 번째 동기화에 기댄다. `--sync none` 에서는 순서 보장이 없어 COMMIT 은 있는데 앞 행 일부가 비는 모양이 가능하며, 이는 COMMIT 값(행 수) 과 CRC 검사에서 손상으로 드러나 시작을 거부한다 (조용히 틀린 행을 보이지는 않는다).
- 한계 2 : COMMIT 을 쓴 뒤 그 동기화가 실패하고 되돌리기(truncate)까지 실패하면 결과가 불확정이다. COMMIT 이 파일에 남아 다시 열면 그 문장의 행이 모두 보일 수 있다. 이때 응답은 "커밋 안 됨" 이 아니라 `statement outcome unknown: commit record was written but could not be confirmed or rolled back; reopen the table to see whether the rows exist` (내부 오류, HTTP 500, 서버 JSON 도 같은 문구) 이고 테이블은 다시 열 때까지 추가를 거부한다. 구분 : (a) COMMIT 을 쓰기 전 실패 + truncate 실패 → 다시 열면 보류 행이 잘리므로 `no row of this statement was committed` 가 맞다. (b) COMMIT 뒤 실패여도 truncate 와 동기화가 성공했으면 정말 되돌린 것이므로 `no row of this statement was committed` 가 맞다. (c) COMMIT 뒤 실패 + 되돌리기 실패 → 불확정. 셋 다 `test_commit_failure_messages_match_what_a_reopen_shows` 가 메시지와 다시 연 뒤 행 수를 확인한다.
- 한계 3 : 기존 형식 (COMMIT 없는 파일) 의 변환은 없다. COMMIT 이 없는 옛 파일은 끝의 보류 행이 "끝나지 않은 문장" 으로 잘리므로 열기 전에 새로 만들어야 한다.
- 한계 4 : repair 가 ID_FLOOR 를 쓰기 전에 죽으면 (백업은 남아 있음) 잘라 낸 구간의 id 하한 정보가 없어진다. 다음 repair 는 이미 잘린 파일만 보므로 하한을 다시 알 수 없고, 백업 파일에서 직접 확인해야 한다.

폴더 잠금 파일 `.mini-dbms.lock`으로 다른 프로세스가 같은 데이터 폴더를 동시에 여는 것을 막는다. 없는 데이터 폴더는 잠금을 시도하기 전에 `data directory not found: …`로 보고한다. 종료 때 핸들과 잠금을 해제하며 잠금 파일 자체는 남을 수 있다. 현재 OS 계층은 프로세스당 하나의 열린 데이터베이스만 지원한다.

### 락과 결과 소유권

각 Table 안에 `pthread_rwlock_t`가 있다. executor가 SELECT에는 읽기 락, INSERT에는 쓰기 락을 잡는다. table 저장 함수는 내부에서 락을 중복 획득하지 않는다. 한 문장은 테이블 하나만 잠그므로 테이블 간 락 순환이 없다. 열기·닫기는 실행 요청과 동시에 수행하지 않는다.

읽기는 `os_read_at`의 위치 지정 읽기만 사용하여 공유 파일 커서를 움직이지 않는다. 행과 TEXT를 포함한 결과 전체를 락 안에서 요청 소유 메모리로 복사하고, 락을 푼 뒤 출력한다. 동시에 실행할 때 요청마다 별도의 Result를 사용한다. Windows와 POSIX 차이는 `os.c` 안에만 둔다.

`table_scan`과 시작 검사는 같은 블록 읽기를 사용한다. 요청별 1 MiB 입력 버퍼에 여러 레코드를 읽고 경계에 걸친 헤더·본문은 남은 바이트를 옮긴 뒤 다음 블록을 채운다. 행 해석용 필드와 NUL 종결 TEXT 작업 공간도 요청별로 한 번 확보하여 행마다 malloc하지 않는다. 방문자는 호출 중에만 Row를 빌리며 SELECT 결과는 별도로 복사한다. Windows 읽기 이벤트는 TLS로 스레드마다 한 개를 재사용하며 워커 종료 때 해제한다. OVERLAPPED와 읽기 버퍼는 공유하지 않는다.

`table_open_with_visitor`는 검증한 각 행의 `(id, 파일 오프셋)`을 파일 순서대로 호출자 콜백에 전달한다. 기존 `table_open`은 NULL 콜백을 쓰는 래퍼다. 콜백 실패는 내부 오류이며 repair로 파일을 자르지 않는다. 뒤 레코드에서 열기가 실패할 수 있으므로 콜백 상태와 실패 정리는 호출자 책임이다. 인덱스 구축은 이번 범위에 포함하지 않는다.

### 검증 방법

`mingw32-make test`는 기존 C 단위 테스트와 `tests/run_cli_tests.py`를 실행한다. CLI 기능 테스트는 임시 폴더에 카탈로그를 복사하며 실제 실행 파일의 stdout과 종료 코드를 `tests/sql/*.expected`와 비교한다. expected 파일의 첫 줄은 `exit_code=N`, 이후는 stdout이다. 변동하는 실행 시간만 메타데이터 위치에서 `<time>`으로 치환하고 나머지 표·값·plan·조사 수·오류 위치는 그대로 비교한다.

파일 입력 6개와 표준 입력, 기본 옵션, 동기화 옵션과 실제 추가 행 수, 재실행 후 id 유지, 빈 입력·BOM, 잘못된 인자·입력, 없는 데이터 폴더, 카탈로그 열기 실패·이름 중복·잘못된 이름·모든 lexer 예약어의 대소문자별 거부, 끝 잘림 복구·길이/검사값/CRC 손상 거부·명시적 복구, 0x1A 오류와 CRLF 저장 바이트 동등성, 중간 구문 오류의 앞 문장 보존, 1 MiB보다 긴 CLI 입력을 확인한다. 길이 검사값은 Python zlib으로 독립 대조하며 첫·중간 레코드에서 길이와 검사값의 같은 비트 32개를 각각 뒤집어 파일 보존을 확인한다. 끝 잘림 후보 안의 완전한 레코드는 바이트 정렬과 무관하게 거부하며 불완전한 후보·검사값 또는 CRC가 틀린 후보는 자동 복구를 막지 않는지 확인한다. C 테스트는 독립 이진 fixture(행 + COMMIT, COMMIT 바이트는 Python zlib 으로 계산), 최대 크기 레코드, 헤더·본문의 블록 경계, 시작 콜백의 id/오프셋과 실패, 동시 스캔 및 파일 커서 보존, 주입한 읽기·쓰기·동기화 실패를 확인한다. 테스트 종료 시 임시 데이터 폴더를 정리한다. 각 C 테스트 프로세스는 `build/t-<이름>-<프로세스 id>-<시각>` 폴더를 만들어 그 안에서만 쓰고(`tests/test_dir.h`) 끝나면 지우므로 같은 작업 트리에서 두 테스트가 동시에 돌아도 파일이 겹치지 않는다. 실패 주입 변수(`os.c`, `bptree.c`)는 `stdatomic` 이다.

문장 원자성 테스트는 `table_test_set_write_chunk` 로 레코드마다 `os_append` 가 한 번씩 나가게 한 뒤 둘째 · 셋째 append 실패, 동기화 실패, 노드 확보 실패(처음 · 중간)에서 파일 크기 · 인덱스 · 행 수 · 다음 id 가 문장 전과 같음을, sync always 의 1000행 문장이 동기화 2회(행 · COMMIT)이고 sync none 은 0회임을(`os_test_sync_calls`), truncate 실패(`os_test_fail_truncate`) 뒤 같은 Db 에서 id 조회와 name 탐색이 같은 결과임을 확인한다. repair 테스트는 백업 바이트가 잘라 낸 바이트와 같고 표준 오류 내용이 맞으며 다음 id 가 뒤 레코드 최댓값보다 큼을 확인한다. 문장 확정 테스트는 되돌리기 실패 뒤 다시 열면 실패 문장의 행이 (전부 · 일부 · 1 MiB 초과 경우) 0개이고 앞 문장이 남는지, COMMIT 없이 끝난 행이 자동으로 잘리고 표준 오류 문구가 맞는지, COMMIT 값 불일치 · 행 없는 COMMIT · 보류 중 ID_FLOOR 가 시작 거부인지, 시작 콜백이 확정된 행만 받는지, 여러 문장 뒤 재열기에서 인덱스와 탐색이 일치하는지, repair 가 ID_FLOOR 를 써서 다음 실행의 INSERT id 가 5 가 아니라 6 부터이고 마지막 레코드를 손상시킨 경우에도 그 id 를 다시 쓰지 않는지, 문장 중간 손상의 repair 가 그 문장을 통째로 자르는지를 확인한다. 실패 주입 카운터(`bptree.c`, `os.c`)는 compare-exchange 로 갱신하며 여러 스레드에서 정해진 횟수만 실패함을 확인한다. `bptree.c` 의 `take_node` 는 예약한 노드가 없으면 NULL 을 돌려주고 삽입은 오류를 반환한다 (가득 찬 잎에서는 아무것도 바꾸기 전에 실패한다).

성능 재현은 `python tests/measure_scan.py`로 수행한다. `build/` 아래 새 임시 폴더에 CLI와 `--sync none`으로 20만 행을 넣고, `db_open` 시작 시간과 `db_execute_sql`의 `SELECT * FROM users WHERE name = 'user_199999'` 실제 결과를 세 번 출력한다. 프로세스 실행 시간은 시작 측정에서 제외되며 데이터 작성 직후의 OS 캐시가 따뜻한 상태다. 측정용 실행 파일·SQL·테이블은 완료 후 제거한다.

## Phase 2 — B+ 트리 인덱스와 벤치

### 구조와 일괄 구축

Phase 2에서는 `db_open`이 테이블마다 메모리 B+ 트리를 만들어 Table에 소유권을 넘긴다. 차수는 64이며 내부 노드는 최대 63개 분리 키와 64개 자식을 가진다. 분리 키는 오른쪽 부분 트리의 최솟값이다. 잎은 최대 63개 `(id, 파일 오프셋)`과 다음 잎 링크를 가진다. 루트 이외 잎은 최소 32개 항목, 내부 노드는 최소 32개 자식을 유지한다. 탐색은 내부 노드에서 upper bound, 잎에서 lower bound로 진행한다. 모든 잎의 깊이는 같다.

시작 시 `table_open_with_visitor`가 12바이트 헤더·CRC·필드·id 증가를 검사하면서 `(id, off)`를 콜백에 전달한다. `db.c`는 증가 순서의 두 배열을 모아 `bpt_bulk_load`를 호출한다. 파일을 인덱스 때문에 다시 훑거나 키를 정렬하지 않는다. 잎을 고르게 채우고 아래에서 위로 부모 레벨을 묶으며 루트를 제외한 최소 채움 비율을 유지한다. 시작 배열은 구축 뒤 해제한다. 어느 단계든 실패하면 부분 인덱스·열린 테이블·폴더 잠금을 정리하고 시작을 거부한다. 인덱스는 파일로 저장하지 않으며 매번 재구축한다.

INSERT는 테이블 쓰기 락 안에서 `bpt_reserve_insert_range`로 문장의 n개 행(앞으로 올 id 는 항상 기존 최댓값보다 큼)이 만들 수 있는 모든 노드를 먼저 확보한 뒤 레코드를 쓴다. 필요 노드 수는 "한 번 쪼개진 노드는 32번 더 들어와야 다시 쪼개진다"는 상한으로 계산하며 `tests/test_bptree.c` 가 여러 높이 · 크기 조합에서 등록 중 노드 할당이 0임을 확인한다. 동기화가 성공하면 `bpt_insert_reserved` 로 할당 없이 n개를 등록하고 남은 노드를 반납한다. 파일 쓰기 · 동기화 실패는 문장 시작 위치로 되돌리고 확보한 노드를 반납하며, 인덱스 메모리 확보 실패는 파일을 쓰기 전에 반환한다. SELECT와 INSERT는 같은 Table의 rwlock을 공유한다.

### 인덱스 선택과 결과

executor는 스키마와 WHERE 타입을 검증한 뒤 `WHERE id = <INT>`만 `PLAN_INDEX`로 선택한다. 단, 인덱스가 붙지 않은 Table(저장소만 쓰는 호출자)이면 0행을 돌려주지 않고 `PLAN_SCAN` 으로 내려간다. `bpt_find`가 반환한 오프셋을 `table_read_at`으로 읽고, 읽은 레코드의 id 가 찾던 id 와 다르면 0행 대신 내부 오류 `index/file mismatch` 를 반환한다. 찾았으면 `rows_examined=1`, 없으면 0이다. 다른 열 조건이나 WHERE 없는 조회는 블록 단위 `table_scan`을 사용하고 실제 방문 행을 센다. `LIMIT 0`은 어느 계획에서도 읽지 않는다. 두 경로 모두 읽기 락 안에서 결과 전체를 복사하며 기존 `DbError.kind`와 결과 소유권 규칙을 유지한다.

### 벤치 실행과 측정 범위

`mini-dbms bench --query-only --data DIR [--queries 100] [--seed 42]` 는 이미 있는 bench 폴더를 열어 삽입 없이 `startup_ms` 와 조회 묶음만 잰다 (행 수는 열 때 센 users 행 수, `--rows` 와 함께 쓸 수 없고 폴더가 필수). 폴더를 새로 만들거나 행을 쓰지 않는다. 출력 첫 줄은 `rows=N queries=Q seed=S query_only=1 sync=none` 이며 `insert_total_ms` 와 동기화 경고가 없다. 재부팅 뒤 첫 실행으로 콜드 캐시를 재는 절차는 `docs/benchmark.md` 에 있다.

두 모드 모두 조회마다 index 와 scan 의 실행 순서를 번갈아 바꾼다 (짝수 번째는 index 먼저, 홀수 번째는 scan 먼저). 한쪽이 늘 먼저 도는 것에서 오는 캐시 편향을 줄이기 위해서다.

`mini-dbms bench --rows N [--data DIR] [--queries 100] [--seed 42]`는 CLI의 기존 진입점 `cli_main`에서 처리한다. `--rows`는 필수 양수, `--queries`는 양수, `--seed`는 0을 포함한 uint64 값이다. 기본 데이터 폴더는 현재 디렉터리의 `bench-data`다. 지정한 폴더는 존재하지 않아야 하며 부모 폴더는 이미 있어야 한다. 기존 폴더는 비어 있어도 거부한다. 새 폴더에 `users : id INT, name TEXT, age INT` 카탈로그를 만들며 데이터는 실행 후에도 보관한다. 옵션 오류는 데이터 생성 전에 거부하고 생성·I/O·메모리 실패는 내부 오류로 출력한다.

`name='user_<id>'`, `age=id % 100`을 1000행씩 여러 행 INSERT SQL로 만든다. 마지막 배치만 남은 수만큼 넣으며 모든 INSERT와 SELECT는 `db_execute_sql`을 호출한다. `sync none`을 적용하고 실제 추가 행 수와 OS 장애 시 손실 범위를 표준 오류에 남긴다. `insert_total_ms`는 SQL 생성·파싱·실행·결과 해제를 포함한다. 삽입 뒤 DB를 닫고 다시 열며 `startup_ms`는 프로세스 실행과 삽입을 제외한 `db_open` 전체, 즉 카탈로그 읽기·파일 검사·인덱스 재구축 시간이다.

SplitMix64와 seed로 재현 가능한 무작위 id를 선택한다. 각 id에 대해 `SELECT * ... WHERE id = ...`와 유일한 `name = 'user_<id>'`를 번갈아 실행한다. 매번 세 필드의 값·타입·결과 한 행·실제 plan·조사 수를 검사하며 불일치하면 측정을 실패시킨다. 기본 100번씩인 첫 조회 묶음 뒤 같은 순서를 다시 실행한다. 각 묶음은 `StmtResult.elapsed_us`(executor 시간, SQL 파싱과 출력 제외)를 정렬하여 중앙값·p99·최댓값을 밀리초로 출력한다. 짝수 표본 중앙값은 가운데 두 값의 평균, p99는 nearest rank `ceil(0.99 * 표본 수)`다. `rows/result`와 `rows_examined/query`도 검증한 실제 결과에서 가져온다.

첫 조회 묶음도 INSERT와 재열기 직후여서 OS 캐시가 따뜻하다. 이를 출력에 명시하고 반복 묶음과 구분한다. 캐시를 비우는 기능은 없으므로 설계 2.9의 캐시가 비어 있는 첫 실행은 확인하지 못했다. `peak_memory_bytes`는 삽입부터 조회까지 프로세스 전체 수명의 최대 상주 메모리이며 인덱스만의 메모리가 아니다. Windows는 `K32GetProcessMemoryInfo`의 `PeakWorkingSetSize`, POSIX는 `getrusage`를 쓰고 플랫폼 분기는 `os.c`에만 둔다. 실제 측정 환경과 출력은 `docs/benchmark.md`에 기록한다.

CLI 테스트는 1만 행 기본 실행, 사용자 지정 폴더·조회 수·seed, 1000행 미만의 마지막 배치, 한 행·한 조회·seed 0, 숫자 범위·누락·중복 옵션 거부, 기존 폴더 보존을 직접 확인한다. 출력된 네 통계 행과 시간·메모리 형식을 검사하고, 별도 CLI 실행으로 저장된 마지막 행과 재구축된 인덱스를 확인한다.

## Phase 3 — API 서버 (스레드 풀 · HTTP)

### 요청 흐름

`main.c` 가 첫 인자가 `serve` 이면 `server_main`(`server.c`)을, 아니면 `cli_main` 을 부른다. 서버도 SQL 은 `db_execute_sql` 하나로만 실행한다.

1. 메인 스레드가 accept 루프를 돈다 (`127.0.0.1` 만 listen, 기본 포트 8100). 연결을 받으면 받은 시각을 적고 스레드 풀 큐에 넣는다. 연결당 요청 하나, 응답은 `Connection: close`.
2. 워커(기본 4)가 연결을 하나 맡아 `http_read_request` → 라우트 → `db_execute_sql` → `result_to_json` → `http_send` 순서로 처리하고 닫는다.
3. 큐가 가득 차 `tp_submit` 이 -1 이면 accept 스레드는 기다리지 않고 그 연결을 거절 전담 스레드 1개(`rejector`, 큐 256)에 넘긴다. 이 스레드가 503 을 보내고 닫는다. 거절 전담 큐도 가득 차면 연결을 그냥 끊는다. 이유 : 클라이언트가 아직 요청을 보내는 중일 수 있어, 응답 뒤 읽지 않은 요청이 남은 채 닫으면 TCP 리셋이 응답을 지운다. 그래서 오류 응답 뒤에는 `os_sock_close_graceful` (FIN 을 보내고 상대가 보낸 것을 최대 4 MiB · 시한까지 버린 뒤 닫기)을 쓰고, 그 기다림을 accept 스레드가 하지 않게 했다. 본문이 `Content-Length` 보다 길게 온 요청 (`HttpRequest.extra_bytes > 0`) 도 정상 응답을 보낸 뒤 같은 방식으로 닫는다. 그 뒤에 더 올 입력이 남아 있어도 리셋이 응답을 지우지 않게 하려는 것이다. 한계 : 남은 입력이 첫 읽기에 함께 오지 않은 경우는 알 수 없어 일반 닫기를 쓴다.

| 라우트 | 동작 |
|---|---|
| `POST /query` | 본문 = SQL (`Content-Length` 필수). 200 `{ok:true, results, elapsed_us, worker}` |
| `GET /health` | 200 `{"ok":true}` |
| `GET /stats` | 테이블별 행 수, `workers`, `busy`, `queued`, `queue_capacity`, `processed`, `rejected`, `insert_lock_wait_us {p99, max, samples}` |

### 상태 코드

| 코드 | 언제 |
|---|---|
| 200 | 모든 문장 성공 |
| 400 | SQL 오류 (`DbError.kind == DB_ERROR_SQL` : 문법 · 이름 · 타입 · 결과 16 MiB 초과), 잘못된 HTTP (요청줄 · 헤더 · `Content-Length` 없음 · `Transfer-Encoding` · CR 없이 LF 만으로 끝낸 줄 — 이것은 2초를 기다리지 않고 바로 400), 본문에 NUL |
| 404 · 405 | 모르는 경로 · 경로에 맞지 않는 메서드 |
| 408 | 받기 시한 (2초) 안에 요청이 다 오지 않음 |
| 413 | 본문이 1 MiB 를 넘음 (헤더의 `Content-Length` 만 보고도 거절) |
| 500 | `DbError.kind == DB_ERROR_INTERNAL` (파일 I/O · 메모리 · 락 · 저장 데이터 손상 · 응답 만들기 실패 · INSERT 결과 불확정) |
| 503 | 큐 가득, 또는 큐에서 기다린 시간이 전체 시한을 넘김 |

오류 본문은 `{ok:false, error:{statement, line, col, message}, committed:n}` (SQL 실행 결과) 또는 `{ok:false, error:{message}}` (HTTP 단계) 이다. 여러 문장 요청은 첫 오류에서 멈추고 `committed` 가 앞서 성공한 문장 수다.

### 시한

받은 시각(accept) 기준이다.

- 요청 받기 : accept 로부터 2초. 느린 클라이언트는 워커 하나를 최대 2초 붙잡고 408 로 끝난다. 큐에서 늦게 꺼내져 이미 2초가 지났어도, 그때 소켓에 도착해 있는 데이터는 읽는다.
- 전체 : accept 로부터 5초. 큐에서 꺼냈을 때, 그리고 요청을 다 읽은 직후 이 시한이 지났으면 실행하지 않고 503 을 보낸다. 이미 시작한 SQL 은 취소하지 않는다. 그래서 SQL 이 끝난 뒤의 시한은 보지 않는다 (INSERT 가 저장됐는데 503 을 주는 모순을 피함).
- 보내기 : 2초 (`http_send` 한 번).

### 락 규칙과 교착 없음

- 테이블마다 `pthread_rwlock` 하나. SELECT = 읽기 락, INSERT = 쓰기 락. 한 문장은 테이블 하나만 잡고, 여러 문장은 앞 문장이 락을 풀어야 다음 문장이 락을 잡는다. 한 스레드가 락을 둘 이상 동시에 들지 않으므로 락 사이 순환 대기가 생길 수 없다.
- 락 안쪽에서 잡는 다른 락은 두 개뿐이다 : 쓰기 락 → 쓰기 대기 시간 기록용 mutex (`WaitStats`), 인덱스 · 파일은 락 없이 쓰기 락이 보호한다. `/stats` 는 이 mutex 와 atomic 만 읽고 테이블 락은 잡지 않는다. 그래서 `/stats` 가 긴 탐색이나 INSERT 뒤에 막히지 않고, 락 순서가 항상 "테이블 락 → 기록 mutex" 한 방향이라 순환이 없다.
- 읽기는 위치 지정 읽기(`os_read_at`)만 쓰고 버퍼는 요청마다 따로다. 결과는 락 안에서 요청 소유 메모리로 모두 복사한 뒤 락을 풀고 네트워크로 보낸다. 느린 클라이언트가 테이블 락을 잡고 있을 수 없다.
- 행 수 · 쓴 행 수는 `_Atomic` 이다 (쓰기 락 안에서 증가, `/stats` 는 락 없이 읽음). 처리 · 거절 수는 서버의 atomic 카운터다. 큐 길이와 바쁜 워커 수는 스레드 풀의 atomic 이다.

#### 긴 탐색과 INSERT 대기

설계 2.10 은 "조회 부하 중 INSERT 락 대기 p99 가 100ms 를 넘으면 조치"라고 정했다. 처음 구현(탐색이 읽기 락을 끝까지 잡음)을 10만 행 이상 테이블에서 재 보니 넘었다 (`python tests/measure_lock_wait.py`, 15만 행, 읽기 6 · 쓰기 2 스레드, 워커 4, 8초).

| 방식 | INSERT 락 대기 p99 | 최대 | 8초 동안 끝난 INSERT |
|---|---|---|---|
| 탐색이 락을 끝까지 잡음 (`--sync always`) | 109.6 ms | 127.0 ms | 128 |
| 같음 (`--sync none`) | 106.6 ms | 110.6 ms | 131 |
| 탐색이 약 1 MiB 마다 읽기 락을 풀었다 다시 잡음 (`--sync always`) | 12.3 ms | 20.6 ms | 303 |
| 같음 (`--sync none`) | 12.9 ms | 32.9 ms | 291 |
| 같음, 40만 행 (`--sync always`) | 14.3 ms | 17.9 ms | 121 (10초) |

(측정 표본은 서버가 기록한 마지막 8192개 대기이며, 앞의 10만여 행을 채우는 INSERT 약 150개가 경합 없이 섞여 있다. 한 번의 탐색은 15만 행에서 약 53 ms, 40만 행에서 약 141 ms 걸린다.)

고른 방식 : **블록 단위로 락을 풀기** (`table_scan_yielding`). 도착 순서 gate 는 쓰기 대기가 "지금 진행 중인 탐색 하나가 끝날 때까지"로 줄 뿐이라, 탐색 시간(테이블 크기에 비례)이 그대로 대기가 된다. 15만 행에서도 이미 한계 근처이고 100만 행이면 넘는다. 블록 단위로 풀면 락 대기가 한 블록 분량(약 1 MiB 를 읽고 거르는 시간)으로 줄어 테이블 크기와 무관하다 (15만 행과 40만 행의 p99 가 비슷함). 단, "테이블 크기와 무관" 은 **락 대기** 에만 해당한다. INSERT 의 끝-끝 지연은 아래 "끝-끝 지연" 에 따로 적었다.

- 탐색은 시작할 때의 확정된 끝 위치(`end`)까지만 본다. 파일은 추가만 하고 확정된 끝 앞의 바이트는 바뀌지 않으므로, 락을 푼 사이 INSERT 가 들어와도 그 SELECT 는 시작 시점에 확정된 행들의 일관된 앞부분만 본다 (끝 위치 스냅샷). 이번 SELECT 에 보이지 않는 행은 다음 SELECT 에 보인다. `rows_examined` 도 그 앞부분의 행 수다.
- 인덱스 조회(`WHERE id = ?`)는 한 번의 점 읽기라 락을 끝까지 잡아도 짧다. 풀지 않는다.
- 읽기 락을 다시 잡지 못하면 (`pthread_rwlock_rdlock` 실패) 그 SELECT 는 내부 오류(500)로 끝나고 executor 는 풀지 않은 락을 풀지 않는다 (`lock_lost`).
- 한계 : 쓰기 락 대기자가 있을 때 새 읽기 락 요청을 뒤로 미루는 것은 rwlock 구현에 달렸다. winpthreads (이 환경) 에서는 측정으로 확인했다. 읽기 우선인 구현 (예 : glibc 기본값) 에서는 읽기가 끊이지 않으면 쓰기가 굶을 수 있어, 그때는 도착 순서 gate 를 더해야 한다. POSIX 빌드는 이 환경에서 확인하지 못했다.

#### 끝-끝 지연 : 락 대기와 큐 대기는 다르다

`tests/measure_lock_wait.py` 는 서버가 기록한 락 대기 p99 와 함께 클라이언트가 잰 INSERT · SELECT 의 응답 지연 (중앙값 · p99 · 최대) 과 끝난 개수를 출력한다. 아래는 이 PC 에서 `--sync always`, 읽기 6 · 쓰기 2 스레드, 워커 4 (표의 마지막 두 줄은 워커 · 읽기 스레드 수만 표대로 바꿨다), 8 ~ 10초로 잰 값이다 (한 번씩 잰 값이라 실행마다 20 ~ 40% 흔들린다).

| 행 수 · 워커 · 읽기 | 한 번의 탐색 | INSERT 락 대기 p99 | INSERT 끝-끝 중앙값 | INSERT 끝-끝 p99 | 최대 | 끝난 INSERT |
|---|---|---|---|---|---|---|
| 15만 · 4 · 6 | 73 ms | 15.9 ms | 80.7 ms | 135.9 ms | 176.0 ms | 205 (8초) |
| 100만 · 4 · 6 | 401 ms | 14.4 ms | 606.4 ms | 836.5 ms | 836.5 ms | 35 (10초) |
| 100만 · 32 · 32 | 395 ms | 106.2 ms | 121.5 ms | 1760.0 ms | 1760.0 ms | 99 (10초) |
| 100만 · 64 · 64 | 377 ms | 212.7 ms | 85.0 ms | 2997.5 ms | 2997.5 ms | 73 (10초) |

- 락 대기는 100만 행에서도 14 ms 다. 그러나 끝-끝 지연은 탐색 시간만큼 늘었다. 워커 4 개가 모두 탐색에 묶이면 INSERT 는 락이 아니라 **큐에서** 기다린다 (워커가 비는 것은 탐색 하나가 끝날 때다). 100만 행에서 INSERT 중앙값이 한 번의 탐색 시간 (401 ms) 을 넘는다. 설계의 100 ms 는 락 대기 기준이며 끝-끝 지연의 약속이 아니다.
- 한계 : 락 대기 p99 100 ms 는 **읽는 스레드가 워커 수 이상으로 많을 때** 넘는다. 100만 행에서 워커 32 · 읽기 32 는 106 ms (경계), 워커 64 · 읽기 64 는 213 ms 였다. 워커 수만큼의 탐색이 한꺼번에 읽기 락을 번갈아 잡으면 쓰기 락 대기자가 한 블록을 기다리는 일이 반복돼 쌓인다. 기본 설정 (워커 4) 에서는 100 ms 안이다.
- 측정 도구 주의 : 스레드 100여 개를 시작하는 데 몇 초가 걸려 시계가 먼저 시작하면 쓰기 스레드가 한 번도 못 돈다. 이제 모든 스레드를 시작한 뒤 시계를 시작한다.

**시도하고 버린 개선 : 전체 탐색 동시 실행 상한 (워커 수 − 1).** 탐색 문장이 읽기 락을 잡기 전에 슬롯 (워커 수 − 1 개) 을 얻고, 없으면 기다리게 해 보았다 (100만 행, 워커 4, 읽기 6 · 쓰기 2, 10초, 같은 도구 이전 판).

| | INSERT 끝-끝 중앙값 | p99 | 끝난 INSERT | 끝난 SELECT |
|---|---|---|---|---|
| 상한 없음 | 404.3 ms | 462.5 ms | 55 | 98 |
| 상한 3 | 418.1 ms | 451.7 ms | 48 | 75 |

효과가 없었고 (중앙값은 같고 p99 는 오차 안, 끝난 INSERT · SELECT 는 오히려 줄었다) 코드를 되돌렸다. 이유 : 슬롯을 기다리는 동안에도 그 워커가 붙잡혀 있다. 큐 앞쪽이 탐색 요청이면 남은 워커 하나가 슬롯 대기로 묶이고, 뒤의 INSERT 는 여전히 큐에 있다. 효과를 보려면 요청을 읽어 탐색인지 알아낸 뒤 슬롯이 없을 때 워커를 놓고 연결을 큐 뒤로 돌려보내야 하는데, 큐 순서 · 시한 · 연결 소유를 바꾸는 큰 설계 변경이라 이번에는 하지 않았다. 쓰기 지연이 중요하면 워커 수를 늘리는 것 (`--threads`) 이 지금 쓸 수 있는 수단이다 (표의 32 · 64 줄 : 끝-끝 중앙값 85 ~ 120 ms, 대신 락 대기 p99 가 한계에 닿는다).

#### 큰 INSERT 와 쓰기 락

문장 단위 원자성 때문에 한 INSERT 문장이 쓰기 락을 잡는 시간은 그 문장이 쓰는 바이트에 비례한다. 서버의 본문 상한 1 MiB 가 문장 하나의 크기를 막는다 (본문 = SQL 텍스트, 저장 레코드는 이보다 조금 크거나 작다). 실측 (`--sync always`, 이 PC) : 약 527 KiB 짜리 2만 행 INSERT 가 서버 안에서 25 ~ 29 ms, 약 950 KiB 짜리 (64 KB 가까운 TEXT 15행) 가 19 ms 였다. 그 시간만큼 다른 요청의 락 대기가 늘 수 있으나 100 ms 안이다. 본문 상한 1 MiB 보다 큰 일괄 입력은 요청을 나누어야 하며, 나눈 요청 사이에서는 원자성이 없다.

### SELECT 결과 상한

`EXECUTOR_MAX_RESULT_BYTES` = 16 MiB. 행마다 `열 수 × sizeof(Value)` 와 TEXT 바이트 (+1) 를 더해 넘으면 `result exceeds the 16 MiB limit; ...` SQL 오류로 문장을 거절한다 (400, CLI 는 `error at L:C`). 같은 executor 를 쓰므로 CLI 와 서버 규칙이 같다. 상한은 메모리 상한이고 JSON 글자 수가 아니다. 제어 문자가 많은 TEXT 는 JSON 에서 `\u00XX` 로 최대 6배가 된다.

### 종료

콘솔 Ctrl+C (Windows `SetConsoleCtrlHandler` 로 Ctrl+C · Ctrl+Break · 콘솔 닫기, POSIX 는 `sigaction` SIGINT · SIGTERM) → 처리기가 종료 플래그를 세우고 listen 소켓을 닫아 (POSIX 는 `shutdown`) accept 를 깨운다. accept 는 200 ms 마다 플래그를 확인하기도 해서 깨우기를 놓쳐도 멈춘다. Windows 에서 콘솔 닫기 (`CTRL_CLOSE_EVENT`) 처리기가 바로 돌아오면 시스템이 프로세스를 끝내므로, 처리기는 종료가 끝났다는 신호 (`os_interrupt_done`, `main` 이 파일을 닫은 뒤 보낸다) 를 최대 4초 기다린다 (Ctrl+C · Ctrl+Break 는 기다리지 않는다). 직접 시험하지는 못했다 (콘솔 창을 닫는 자동 시험이 없다). 코드와 이 문서가 근거의 전부다. 이어서 `tp_shutdown` 이 큐에 남은 연결을 모두 처리하고 (각 연결은 위 시한을 따름) 워커를 join 하고, 거절 전담 스레드를 같은 방식으로 끝낸 뒤 `db_close` 로 파일을 닫고 종료 코드 0 으로 끝난다. accept 가 연속 100번 넘게 실패해 멈추면 (종료 요청 때문이 아닐 때) 표준 오류에 `error: accept failed over 100 times in a row; stopping the server` 를 남기고 같은 정리를 한 뒤 종료 코드 1 로 끝난다 (자동 시험 없음 : accept 실패를 만들 방법이 없다). 큐에서 기다리던 요청은 응답을 받고, accept 하지 않은 연결 (backlog) 은 끊긴다. 종료 때 표준 오류에 처리 · 거절 수를 남긴다.

### 서버 테스트

`python tests/test_server.py` (`mingw32-make test-server`) 는 테스트마다 `build/` 아래 고유 데이터 폴더와 `--port 0` 서버를 띄우고 끝에 종료한다. 서버가 첫 줄에 `listening 127.0.0.1:<포트>` 를 출력하므로 포트 충돌이 없다. 종료 테스트는 Windows 에서 `CREATE_NEW_PROCESS_GROUP` 으로 띄운 서버에 `CTRL_BREAK_EVENT` 를, 그 밖에서 SIGINT 를 보내 실제 종료 처리기를 거친다. 서버 테스트는 약 30초 걸려 `mingw32-make test` 에 넣지 않았다. 10만 행 이상 락 대기 · 끝-끝 지연 측정은 `python tests/measure_lock_wait.py` (인자 : `--rows --seconds --readers --writers --threads --sync`) 로 따로 한다. `test_bare_lf_gets_400_at_once` 와 `test_body_longer_than_content_length_still_gets_its_answer` 가 LF 만 쓴 요청의 즉시 400 과 긴 본문 뒤의 정상 응답을 확인한다 (후자는 수정 전에도 통과해 이 PC 에서 리셋을 재현하지는 못했다. 회귀 방지용이다).

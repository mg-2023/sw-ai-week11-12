## 3회 실행 사이의 편차

측정 1은 실행마다 처리량이 달랐습니다.
연결 1개에서는 명령별로 약 16000에서 25000 req/s, 연결 8개에서는 약 23000에서 30000 req/s 였습니다.
지연의 p50 은 연결 1개에서 0.035에서 0.045ms, 연결 8개에서 0.23에서 0.31ms 로 안정적이었습니다.
max 는 한 번 4.277ms 까지 튀었습니다(2회차 SET, 연결 1개).

측정 2의 cache off 는 3회 모두 처리량 15.2에서 15.4 req/s, p50 62.5에서 62.7ms 로 거의 같았습니다.
cache on 은 편차가 컸습니다.
처리량은 102.8, 107.8, 316.2 req/s 였고 p50 은 13.745, 14.590, 0.940ms 였습니다.
세 번 모두 hit 199, miss 1, 적중률 99.5% 였습니다.
cache on 의 p50 이 두 부류(약 14ms 와 1ms 미만)로 갈린 이유는 확인하지 못했습니다.
세 번 모두 cache off 보다 빨랐습니다.
지연이 두 부류로 갈린 점은 이 환경(Windows, 루프백)의 영향일 수 있다는 추정일 뿐입니다.

적중률은 측정이 약 2초 안에 끝나 TTL 30초보다 짧았기 때문에 만료로 인한 miss 가 다시 생기지 않았습니다.
miss 1은 빈 캐시에서 시작한 첫 요청입니다.

## 읽는 법

캐시 적중이 빨라지는 이유는 50ms 가 걸리는 원본 작업을 건너뛰고 Mini Redis 에서 값을 바로 꺼내기 때문입니다.
cache on 의 지연에는 Mini Redis 조회 비용보다 HTTP 왕복(요청마다 새 연결)과 파이썬 클라이언트 비용이 더 크게 들어 있습니다.
cache off 의 지연은 고정 지연 50ms 에 같은 HTTP 비용을 더한 값입니다.
이 측정은 다른 PC, 네트워크 너머, 큰 데이터, 동시 요청이 많은 상황, 실제 원본 작업(DB 조회 등)에서의 차이를 말해 주지 않습니다.
원본 작업의 50ms 는 흉내 낸 값이라서, 캐시로 줄어드는 비율은 이 값에 직접 의존합니다.

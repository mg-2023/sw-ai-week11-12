## 1. 목표와 순서

1. Mini DBMS 가 요구사항 노트의 필수 28개를 모두 충족한다. **이것이 먼저다.**
2. 그 뒤 확장 : 오목 앱이 Mini DBMS 를 원본 저장소로, Mini Redis 를 캐시 · 순번 · 접속 확인으로 쓴다.
3. 오목 온라인 대전이 착수 · 차례 · 승패 · 기권 · 재접속까지 끝까지 동작한다.
4. 게임 화면과 인프라 로그를 분리한다. 인프라 패널에서 Redis · DBMS 작업을 실시간으로 본다.
5. Mini Redis 주기 만료를 실제 Redis 방식과 측정으로 비교해, 미리 정한 기준을 넘을 때만 바꾼다.

## 2. Mini DBMS

### 2.1 플랫폼

- MinGW-w64 gcc 13 (posix 스레드 모델, winpthreads) + Winsock. `-pthread` 로 빌드 확인함
- 이식층 `os.c` : 소켓 초기화 · 닫기, 위치 지정 읽기(`os_pread` : Windows 는 `ReadFile` + OVERLAPPED, 그 밖은 `pread`), 파일 동기화(`_commit` / `fsync`), 고해상도 단조 시계, 데이터 폴더 잠금 파일
- mini-redis `net.c` 의 `_WIN32` 분기 방식을 따른다 (복사, 링크 아님)

### 2.2 모듈 (요청 한 건의 흐름 순서)

| 모듈 | 책임 |
|---|---|
| `lexer.c` | SQL 문자열 → 토큰. 줄 · 칸을 토큰에 남긴다. `--` 주석을 건너뛴다 |
| `parser.c` | 토큰 → `Statement`. `;` 로 여러 문장 |
| `catalog.c` | `data/catalog.txt` 를 읽는다. 시작 뒤 읽기 전용 |
| `executor.c` | `Statement` 실행. `WHERE id = 정수` 면 인덱스, 아니면 선형 탐색 |
| `table.c` | 테이블 파일 추가 · 위치 지정 읽기 · 전체 훑기 · 시작 때 복구 검사 |
| `bptree.c` | 메모리 B+ 트리. 키 = id, 값 = 파일 오프셋 |
| `db.c` | **단일 진입점** `db_execute_sql(Db*, const char *sql, Result*)` = lexer → parser → executor |
| `cli.c` | `run <file.sql>` · `run -` (표준 입력), `bench`, `serve` |
| `threadpool.c` | 고정 워커 + 크기 제한 큐 |
| `http.c` | 최소 HTTP/1.1 파싱 · 응답 |
| `server.c` | accept 스레드 → 큐 → 워커가 `db_execute_sql` → JSON |

- CLI · bench · HTTP 모두 `db_execute_sql` 하나만 부른다 → "Phase 1 처리기를 그대로 사용" 을 코드 구조로 보장

### 2.3 카탈로그 형식

```
# 테이블 이름 : 컬럼 타입, ...   (id INT 는 모든 테이블의 첫 컬럼)
users : id INT, name TEXT, age INT
games : id INT, game_key TEXT, room INT, black TEXT, white TEXT, winner TEXT, moves INT, reason TEXT, ended_at TEXT
moves : id INT, game_key TEXT, seq INT, cell INT, color TEXT
```

### 2.4 SQL 범위

- `INSERT INTO t [(cols)] VALUES (v, ...)[, (v, ...)]`
	- `id` 는 자동 부여. 열 목록이 없으면 `id` 를 뺀 나머지 컬럼 순서로 값을 받는다
	- `id` 를 주면 에러
- `SELECT * | col, ... FROM t [WHERE col = literal] [LIMIT n]`
- 타입 : `INT` (int64), `TEXT` (작은따옴표, `''` 로 따옴표 표현, 최대 64KB)
- 범위 밖 : `CREATE TABLE`(요구사항 전제), `UPDATE`, `DELETE`, `JOIN`, `ORDER BY`, 집계
- 여러 문장 : 순서대로 실행, **첫 에러에서 멈춘다**. 앞 문장은 이미 기록됨을 결과에 밝힌다 (트랜잭션 없음)

### 2.5 CLI 출력

```
id | name     | age
---+----------+----
 7 | user_7   | 31
(1 row, plan=index, examined=1, 0.021 ms)
```

- 에러 : `error at 3:14: expected VALUES` 형식, 종료 코드 1

### 2.6 저장 형식과 내구성

- 테이블마다 이진 파일 `data/<table>.tbl`, 추가만 한다
- 레코드 = `[u32 길이][u32 길이 검사값][u32 CRC32][i64 id][필드들]` (CRC 범위 = id 부터 끝까지, 길이 상한 1MB, 길이 검사값 = 길이 4바이트의 CRC32 XOR 0x4D444231 · v2.1)
- INSERT 순서 (쓰기 락 안)
	1. 인덱스 노드 등 필요한 메모리를 먼저 확보
	2. 파일 끝에 쓰기
	3. 실패하면 이전 끝 위치로 잘라 되돌리고 500
	4. `fflush` + 동기화 → 성공이면 B+ 트리 등록, id 응답
- `--sync always` (기본) : 응답 = 디스크 반영 완료. `--sync none` : bench 용, 손실 범위를 출력에 표시
- 시작 때 복구
	- 끝 잘림 (쓰다 멈춤) → 그 자리에서 잘라 내고 표준 오류에 남긴다
		- 헤더(12바이트)보다 짧은 꼬리, 0 바이트로만 채워진 꼬리, 헤더는 맞는데 본문이 파일 끝을 넘는 경우 (단, 그 꼬리 안에 완전한 레코드가 있으면 손상)
	- 손상 → 시작 거부. `--repair` 로만 잘라 낸다
		- 길이 검사값 불일치 · 길이 0 · 상한 초과, 본문까지 있는데 CRC 오류
		- v2 는 길이 필드를 검사하지 않아, 중간 레코드 길이가 손상되면 끝 잘림으로 보고 뒤를 지웠다 (v2.1 에서 고침)
	- 한계 : 길이와 검사값이 서로 맞게 함께 바뀐 복합 손상은 끝 잘림과 구별하지 못한다. TEXT 안에 완전한 레코드 바이트가 든 채 쓰다 멈추면 거짓 양성으로 시작을 거부한다 (데이터는 지우지 않음). 자세한 것은 `docs/architecture.md`
- 데이터 폴더 잠금 파일 : CLI 와 서버가 같은 폴더를 동시에 열지 못한다

### 2.7 B+ 트리

- 차수 64. 내부 노드 = 키 + 자식, 잎 = 키 + 오프셋, 잎끼리 연결
- `bpt_insert`, `bpt_find`, 검사용 `bpt_check` (정렬 · 높이 같음 · 채움 비율)
- 시작 때는 id 가 늘어나는 순서이므로 일괄 구축(`bpt_bulk_load`)을 쓴다. 100만 건 시작 시간을 잰다

### 2.8 결과 메타데이터

- 모든 `SELECT` 결과에 `plan` (`index` | `scan`), `rows_examined`, `elapsed_us`
- 성능 비교와 인프라 패널이 이 값을 그대로 쓴다

### 2.9 Phase 2 성능 비교

- `mini-dbms bench --rows 1000000`
	- `users` 행을 SQL 텍스트(여러 행 `VALUES`, 1000행씩)로 만들어 `db_execute_sql` 로 넣는다
	- `name = 'user_<n>'` 이 유일해서 두 조회 모두 결과가 1행 → 같은 결과 건수로 비교
- 측정 : `WHERE id = ?` 와 `WHERE name = ?` 무작위 100번씩, 중앙값 · p99 · 최댓값
	- 첫 실행(파일이 OS 캐시에 없음)과 반복 실행을 따로 적는다
	- 삽입 총 시간, 시작(인덱스 재구축) 시간, 최대 메모리도 적는다
- 결과는 `docs/benchmark.md`

### 2.10 Phase 3 API 서버

- `POST /query` : 본문 = SQL
	- 200 : `{ok:true, results:[{columns, rows, plan, rows_examined, inserted_ids}], elapsed_us, worker}`
	- 400 : SQL 오류. `{ok:false, error:{statement, line, col, message}, committed:n}`
	- 413 : 본문 1MB 초과 · 500 : 파일 I/O 실패 · 503 : 큐 가득 참 또는 대기 시한 넘김
- `GET /health`, `GET /stats` (테이블별 행 수, 워커 수, 바쁜 워커, 큐 길이, 처리 · 거절 수, INSERT 락 대기 p99)
- `Connection: close`, 연결당 요청 하나, `Content-Length` 필수
- 시한 : 헤더 · 본문 받기 2초, 큐 대기 포함 전체 5초, 보내기 2초
- 스레드 풀 : 워커 기본 4 (`--threads`), 큐 기본 64 (`--queue`). 큐가 차면 accept 스레드가 짧은 503 을 보내고 바로 닫는다
- 동시성
	- 테이블마다 `pthread_rwlock` : SELECT = 읽기 락, INSERT = 쓰기 락
	- 읽기는 위치 지정 읽기(`os_pread`)라 워커끼리 파일 위치를 공유하지 않는다. 버퍼는 요청마다 따로
	- 결과를 락 안에서 모두 확보 → 락을 푼 뒤 네트워크로 보낸다
	- 한 문장은 테이블 하나만 잡는다 → 교착 없음
	- 통계는 `stdatomic`
	- 쓰기 굶주림 : 조회 부하 중 INSERT 락 대기 p99 · 최댓값을 잰다. 상한(100ms)을 넘으면 도착 순서 gate 를 추가한다
- 종료 : 콘솔 Ctrl+C 처리기 → 플래그 + 리슨 소켓 닫기로 accept 를 깨움 → 큐 비우기 → 파일 닫기

### 2.11 핵심 로직 설명 (필수 27 · 28)

- `docs/architecture.md` : 요청 흐름, 불변식(B+ 트리 · 파일 · 락), 실패 정책
- Phase 가 끝날 때마다 옵시디언 `미니DBMS/학습/` 에 설명 노트 + 사용자가 답할 질문 3개
- Phase 경계는 태그로 남긴다 : `v0.1.0` Phase 1, `v0.2.0` Phase 2, `v0.3.0` Phase 3

## 3. 오목 온라인 대전 (`mini-react-gomoku`)

### 3.1 상태 주인

| 상태 | 어디에 |
|---|---|
| 방 번호, 좌석 순번 | Mini Redis `INCR` (지금과 같음) |
| 진행 중 판 (판, 차례, `seq`, 상태 버전, 참가자 토큰) | 백엔드 메모리 |
| 대국 식별자 | 판이 시작될 때 백엔드가 만든 `game_key` (UUID) |
| 접속 표시 | Mini Redis `SET gomoku:presence:<방>:<색> 1 EX 15` (패널용) |
| 접속 끊김 판정 | 백엔드 메모리의 마지막 heartbeat 시각 (Redis 가 꺼져도 동작) |
| 수순 | Mini DBMS `moves` 에 착수마다 `INSERT` (`game_key` 로 묶음) |
| 끝난 판 | Mini DBMS `games` 에 한 번 `INSERT` |
| 최근 전적 요약 | Mini Redis 캐시 30초, 저장 뒤 `DEL` |

### 3.2 흐름

1. 입장 `POST /api/rooms/:id/join` → 좌석 `INCR` → 토큰 (방 · 좌석에 묶임)
	- 토큰은 탭별 `sessionStorage` → 두 탭이 서로 덮어쓰지 않는다
2. 재접속 `POST /api/rooms/:id/resume {token}` → `INCR` 하지 않고 같은 자리
3. 방 화면 `GET /api/rooms/:id/events` (SSE)
	- 연결하자마자 전체 상태 스냅샷, 그 뒤 변경마다 상태 버전과 함께
	- 15초마다 heartbeat 주석, 끊긴 구독자는 정리
	- 토큰은 공개 상태에 넣지 않는다
4. 착수 `POST /api/rooms/:id/moves {token, seq, cell}`
	- 방마다 처리 순서 큐 하나 : 착수 · 기권 · 끊김 판정이 이 큐로만 상태를 바꾼다 (`await` 사이에 끼어들기 없음)
	- 검사 : 대국 중인가, 그 사람 차례인가, `seq` 가 다음 번호인가, 빈칸인가
	- 같은 `seq` 재전송은 이전 결과를 그대로 돌려준다 (중복 방지)
5. 승패는 서버가 `findWin` 으로 판정 (`omok/game.js` 의 판정 함수를 Node 에서도 쓰게 분리)
6. 끝나는 경우 : 오목, 판 가득 참, 기권, 끊김 60초. 종료는 한 번만 확정
7. 끝나면 `games` `INSERT` → 요약 캐시 `DEL`
8. 관전자는 같은 SSE 로 본다. 착수는 403
9. 온라인 판 결과는 서버만 저장한다. 기존 `POST /api/games` 는 혼자 두기 모드 전용으로 남긴다

### 3.3 요약 캐시

- DBMS 는 정렬 · 집계가 없으므로 백엔드가 `SELECT * FROM games` 결과를 정렬 · 집계한다 (데이터량별 시간 측정)
- 캐시 경합 방지 : 저장할 때마다 메모리의 `summaryVersion` 을 올린다. 조회를 시작한 버전과 끝난 뒤 버전이 다르면 `SET` 하지 않는다
- DB 저장 성공 + Redis `DEL` 실패는 응답과 패널에 따로 표시

### 3.4 실패 처리

| 실패 | 처리 |
|---|---|
| Mini Redis 꺼짐 | 방 만들기 · 입장 503. 진행 중 판은 계속 |
| Mini DBMS 꺼짐 | 착수는 계속. 저장 못 한 수순은 메모리 목록에 두고 다시 시도. 끝날 때까지 못 넣으면 `reason` 에 `incomplete` |
| DBMS 동시 요청 | 백엔드는 DBMS 요청을 동시에 최대 8개로 제한 |
| SSE 끊김 | 브라우저가 다시 연결 → 스냅샷으로 맞춤 |
| 백엔드 재시작 | 진행 중 판은 사라진다 (메모리). README 한계에 적는다 |

## 5. Mini Redis 주기 만료 비교 (`mini-redis`, `main` 에서 `feat/adaptive-expire`)

- 실제 Redis (`expire.c`, unstable) : 커서 스캔, 한 번에 20개, 지운 비율 > 10% 면 반복, 시간 상한 = 주기의 25% (100ms 주기면 25ms), 시계는 16번마다
- 비교할 세 방식
	1. 지금 : 32개 고정
	2. 32개 + 적응 반복
	3. 20개 + 적응 반복
	- 시간 상한은 25ms(Redis 와 같은 비율)와 2.5ms 둘 다 잰다
- 측정 전 준비
	- 고해상도 단조 시계 (`QueryPerformanceCounter`). 지금 `GetTickCount64` 는 10 ~ 16ms 단위라 상한을 못 잰다
	- `rehash_step` 은 반복 루프 밖에서 한 번만
	- 삭제 경로별 카운터 (조회 시 만료 · 주기 정리)
	- 측정 중 로그 · AOF 끔, 같은 입력 부하
- 데이터 : 만료 키 10만 + TTL 없는 키 10만 / 긴 TTL 키 10만, TTL 배치는 무작위와 몰림 두 가지
- 지연 측정 `GET` 은 살아 있는 키만 대상
- 채택 기준 (측정 전에 고정)
	- 남은 만료 키가 절반이 되는 시간이 지금 방식의 0.5배 이하
	- `GET` p99 증가 10% 이내, 최대 정지 시간 ≤ 시간 상한, 처리량 · 오류율 차이 없음
	- 못 넘으면 지금 방식을 두고 측정 결과만 `docs/benchmark.md` 에 남긴다

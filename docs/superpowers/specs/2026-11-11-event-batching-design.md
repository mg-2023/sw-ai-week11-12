# 이벤트 배칭 — 짧은 설계

- 날짜 : 2026-11-11
- 브랜치 : `feat-Jongeume` (로컬, push 는 사용자가 "올려" 한 뒤)
- 대상 : `src/hooks.js`, `src/component.js`, `phase2/app.js`(측정 시나리오 하나), `phase2.html`(버튼 하나), 새 테스트

## 왜

- 과제 중점 포인트 : "여러 상태 변경을 한 번에 처리하는 방법은? (Batching, 선택 과제)"
- 지금 '추가' 클릭 한 번에 갱신이 2회 일어난다 (`setTodos` → 갱신 ①, `setText('')` → 갱신 ②, 11-11 jsdom 실행 확인)
- 사용자 우선순위 : 배칭 → 측정 → 타입 검사 적용 검토

## 목표 · 범위 밖 · 실패 기준

- 목표
	- 유효한 할 일을 '추가' 하면 항목 +1 · 입력칸 비움 · 클릭 뒤 갱신 **1회** (타이핑 중 갱신은 제외)
	- 같은 상태에 함수형 업데이트를 여러 번 요청하면 순서대로 누적
	- 측정 페이지에서 배칭 전후를 숫자로 비교
- 범위 밖
	- 마이크로태스크 비동기 배칭 · key 기반 재정렬 · `useHistoryState` · 오목
	- TypeScript 적용 (이 작업 뒤 별도 시험 — 아래 "다음")
	- Phase 1 파일 (`vdom.js` · `diff.js` · `patch.js` · `history.js`)
- 제약 (과제)
	- Hook · 상태는 루트에서만, 자식은 props 만 받는 순수 함수 — 그대로 유지
- 실패 기준
	- 기존 테스트 177개 중 하나라도 기대값을 바꿔야 한다
	- 갱신이 비동기가 된다 (클릭 직후 DOM 이 아직 안 바뀐 상태)
	- 핸들러 예외 뒤 배칭이 열린 채 남는다

## 접근 (고른 것 : 가)

| 안 | 내용 | 결과 |
| --- | --- | --- |
| 가. 이벤트 경계 | 엔진이 `on*` 핸들러를 감싸, 그 안의 setter 를 모았다가 핸들러가 끝날 때 한 번 갱신 | **사용자 선택** — 앱 코드 그대로, 갱신은 계속 동기, 기존 테스트 유지 예상 |
| 나. 직접 `batch()` | 앱의 `add` 안에서 감싼다 | 앱이 매번 기억해야 하고 엔진 개선이 아님 |
| 다. 마이크로태스크 | setter 는 예약만, 이번 작업 뒤 한 번에 | 모든 경로가 묶이지만 갱신이 비동기가 되어 테스트 · 예외 계약이 크게 바뀜 |

알고 고른 한계 : 엔진 이벤트 밖(시나리오 버튼 `app.js:174`, 타이머, 직접 호출)의 setter 는 묶이지 않는다. 그래서 `set10` 은 그대로 10회다.

## 설계

1. **배칭 상태 — `hooks.js`**
	- 모듈 변수 : 깊이 카운터, 갱신할 컴포넌트 목록(`Set`)
	- `batch(fn)` : 깊이 +1 → `fn()` → `finally` 에서 깊이 −1 → 바깥(깊이 0)일 때만 목록을 꺼내 비우고 처리
2. **setter 갈래 — `hooks.js` `makeSetter`** (순서 보존, 6 번만 새로)
	1. 렌더 중이면 예외
	2. 없어진 컴포넌트면 끝
	3. 같은 값이면 `resyncForms` 후 끝
	4. 값 저장 (함수형이면 지금 `hook.value` 로 계산 → 누적)
	5. 커밋 중이면 기존 줄 세우기 (`settle` 이 처리)
	6. **배칭 중이면 기존 줄 세우기와 같은 방식으로 `queued` 에 넣고, 갱신할 목록에 컴포넌트 추가**
	7. 아니면 지금처럼 `update(undo)`
3. **핸들러 감싸기 — `component.js` `expand`**
	- 펼친 노드의 `on*` 함수 props 를 `batch` 로 감싼 함수로 바꾼다
	- 원래 함수 → 감싼 함수를 WeakMap 으로 하나만 만든다 (같은 함수면 같은 감싼 함수 → Diff 결과가 지금과 같다)
4. **끝낼 때 — 기존 흐름 재사용**
	- 목록의 컴포넌트마다 `phase` 가 `idle` 이고 없어지지 않았으면 `settle([])`
		- `flushPending` 의 되돌리기(`restoreQueued`) · 50회 연쇄 제한 · effect 예외 모으기를 그대로 쓴다
	- 커밋 중인 컴포넌트는 건너뛴다 (바깥 `settle` 이 이미 처리 중)
5. **예외 처리**
	- 깊이는 `finally` 에서 반드시 되돌린다
	- 핸들러가 던져도 그 전에 저장된 상태는 반영한다 (React 와 같음)
	- 둘 다 던지면 **핸들러 예외가 이기고**, 반영 중 예외는 그 예외의 `heldErrors` 에 붙인다 (`settle` 의 관례)
	- 반영 중 예외만 있으면 그대로 던진다
6. **측정**
	- 시나리오 `addClick` 추가 : 진짜 '추가' 버튼을 엔진 이벤트 경로로 누른다
	- 입력칸 글자 넣기는 측정 밖에서 한다
	- 렌더 · 비교 수는 계산 비용, patch · DOM 변경 수는 실제 DOM 비용으로 따로 읽는다

알고 둔 한계 : 한 이벤트 안에서 A → B → A 로 되돌리면 patch 0 개인 렌더가 한 번 생긴다.

## 완료 조건

- 새 테스트 통과
	- '추가' 클릭 : 항목 +1 · 입력칸 `""` · 커밋 1회
	- 한 핸들러에서 `n => n + 1` 세 번 : 최종 +3 · 커밋 1회
	- 배칭된 클릭 → 그 커밋의 effect 가 setter : 후속 갱신 · 예외 계약 유지
	- 핸들러가 setter 뒤에 예외 : 예외가 밖으로 나오고 상태는 반영, 다음 클릭은 평소처럼
	- 중첩 핸들러 : 바깥이 끝날 때 한 번만 반영
- 기존 177개 기대값 무수정 통과
- 실제 브라우저에서 `addClick` 렌더 2 → 1
- 독립 검증은 Codex 몫 (요청문만 준비)

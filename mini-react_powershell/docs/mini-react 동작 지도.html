              5. 페이지 1: Diff 실험실의 실행 방향

              페이지를 열면 샘플을 실제 영역에 넣고 DOM을 읽어 첫 설계도를 만듭니다. Patch를 누르면 테스트 영역을 읽어 새 설계도를 만들고, 이전 설계도와 비교합니다. 달라진 곳만 연산으로 만들어 실제 DOM에 적용하고 새 버전을 저장합니다. 뒤로가기는 기록 위치를 옮긴 뒤 같은 비교와 반영을 거칩니다.

              6. 페이지 2: 집중 보드의 실행 방향

              상태 함수가 값을 바꾸면 렌더를 한 번 예약하고, 지금 작업이 끝난 직후 컴포넌트 함수를 다시 실행합니다. 새 설계도를 이전 설계도와 비교해 바뀐 곳만 반영한 뒤 effect를 실행합니다.

              7. 두 페이지의 연동과 부분 업데이트

              페이지 1은 사람이 Patch를 눌러서, 페이지 2는 상태가 바뀌어서 시작합니다. 새 설계도를 만드는 입구만 다르고, 뒤쪽의 diff와 applyPatches는 같은 함수입니다. 렌더 기록의 노드 지도도 두 페이지가 같은 recordTouch로 기록합니다.

              과제의 목표인 "필요한 부분만 업데이트"를 실제 앱에서 쟀습니다. mini-react.html을 Edge로 열고 MutationObserver로 DOM 변경 기록을 센 값입니다.

              8. 주요 로직

              • 주소: 연산은 자식 번호의 배열로 위치를 가리킵니다. 그래서 설계도가 실제 DOM과 1:1로 맞아야 하고, 처음에 들여쓰기 공백을 뺀 DOM을 다시 만듭니다.
              • Hook 규칙: 커서로 칸을 찾기 때문에 호출 순서가 바뀌면 안 됩니다. 순서나 개수가 어긋나거나 자식 컴포넌트에서 Hook을 부르면 오류를 냅니다.
              • effect: 렌더 중에는 예약만 하고 화면 반영이 끝난 뒤 실행합니다. 이전 정리 함수를 먼저 돌려서 타이머가 겹치지 않습니다.
              • 검색 렌더 규칙: 검색 결과가 1개가 되면 글자를 더 쳐도 상태로 올리지 않아서 렌더가 없습니다. 지워서 2개 이상이 되면 다시 렌더합니다. 맞는 일이 없어지거나 다른 일로 바뀌면 화면이 달라지므로 렌더합니다.
              • 실제 영역: 내용 길이를 막지 않습니다. 높이는 고정이라 길면 영역 안에서 스크롤하고, 참가 신청은 밀리지 않습니다.

              MutationObserver는 자식 추가와 삭제, 속성, 글자 변경을 지켜봅니다. 변경마다 바로 불리지 않고 기록을 모아 마이크로태스크로 전달합니다. 이 프로젝트는 app/inspector.ts:29에서 기록을 꺼내 화면의 "실제 DOM 변경" 숫자로 보여 줍니다. 코드가 낸 연산 수와 브라우저가 본 변경 수를 나란히 놓아서 비교할 수 있습니다. 입력칸의 글자 변경은 input 이벤트로 받습니다.

              실제 DOM이 느린 이유: Reflow와 Repaint

              브라우저는 스타일 계산, 레이아웃, 그리기 순서로 화면을 만듭니다. Reflow는 크기와 위치를 다시 계산하는 일입니다. 노드 추가나 너비 변경이 일으키고, 부모와 형제로 번질 수 있습니다. Repaint는 위치는 그대로 두고 색처럼 픽셀만 다시 칠하는 일입니다.

              느려지는 이유는 변경 한 번이 아니라 뒤따르는 계산입니다. 브라우저는 변경을 모아서 한 번에 계산하려 하지만, 변경 직후 offsetHeight 같은 값을 읽으면 그 자리에서 Reflow를 해야 합니다. 1,000줄 목록으로 잰 값입니다.

              10. Virtual DOM과 Diff

              구조

              Virtual DOM은 화면을 설명하는 일반 JavaScript 객체입니다. 요소와 글자 두 종류뿐입니다(phase1/types.ts:10).

              { kind: 'element', tag: 'li', props: { class: 'done' }, key: 'a',
  children: [{ kind: 'text', text: '보고서 쓰기' }] }

              필요한 이유

              화면을 상태로 전부 다시 설명하되, 브라우저 작업은 작게 유지하기 위해서입니다. 객체끼리 비교는 Reflow를 일으키지 않으므로, 바뀐 곳을 먼저 계산한 뒤 그만큼만 실제 DOM을 고칩니다. 개발자가 어디를 고칠지 직접 추적하지 않아도 됩니다.

              다만 Virtual DOM이 항상 더 빠른 것은 아닙니다. 고칠 곳을 정확히 안다면 DOM을 직접 고치는 쪽이 비교 비용만큼 더 빠릅니다.

              Diff 동작 방식

              두 트리를 위에서 아래로 내려가며 묻습니다. 같은 객체인지 먼저 보고, 글자 노드 비교, 종류와 태그와 key 비교, 속성 비교, 자식 비교 순서로 진행합니다. 결과는 바로 고치지 않고 연산 목록으로 돌려줍니다. 그래서 브라우저 없이 테스트할 수 있고, 화면에 연산 목록을 보여 줄 수 있습니다.

              최소 변경을 찾기 위한 5가지 케이스와 실제 DOM 반영

              케이스언제연산실제 DOM 반영
              추가새 자식이 생김INSERTcreateDom 뒤 insertBefore
              삭제자식이 사라짐REMOVEremove
              교체태그나 key가 다름, 글자와 요소가 바뀜REPLACEcreateDom 뒤 replaceWith
              속성 변경태그는 같고 속성이 다름PROPSsetAttribute, removeAttribute, value와 checked 프로퍼티
              글자 변경글자 내용이 다름TEXTnodeValue

              여기에 두 가지를 더했습니다. MOVE는 key가 같은 노드를 새로 만들지 않고 옮깁니다. 입력값과 포커스가 유지되는 이유입니다. phase1/diff.ts:120로 움직이지 않을 노드를 골라 이동 횟수를 줄입니다. LISTENERS는 이벤트 함수만 바꾸고 DOM은 건드리지 않습니다.

              applyPatches(phase1/patch.ts:128)는 연산을 순서대로 실행합니다. 경로를 따라 노드를 찾고, 위 표의 DOM API를 부릅니다. 노드 내부를 고치는 연산이 먼저, 자식 목록을 바꾸는 연산이 나중에 나오므로 옛 트리의 번호가 끝까지 유효합니다.

              11. 실제 React가 DOM을 바꾸는 과정

              • Render 단계: 컴포넌트 함수를 실행해 새 React 요소를 만들고, 이전 Fiber 트리와 비교해 바뀔 일을 표시합니다. DOM을 건드리지 않아서 중단했다가 다시 할 수 있습니다.
              • Commit 단계: 표시된 변경을 실제 DOM에 한 번에 반영합니다. 중단되지 않습니다. 이어서 useLayoutEffect가 돌고, useEffect는 보통 화면을 그린 뒤 실행됩니다.
              • 비교 규칙: 타입이 다르면 그 아래를 통째로 교체하고, 같으면 속성만 고치며, 목록은 key로 짝을 찾습니다. 이 구현의 REPLACE, PROPS, key 짝 찾기가 같은 규칙입니다.

              이 구현의 render와 diff는 Render 단계에, applyPatches는 Commit 단계에 해당합니다.

              12. Component와 State

              함수는 매번 새로 실행되는데, 상태는 어떻게 유지할까?

              13. setState와 Batching

              setState가 상태 변경 외에 하는 일

              값만 바꾸면 화면은 그대로입니다. setState는 네 가지를 합니다(phase2/hooks/use-state.ts:22).

              1. 새 값을 계산합니다. 함수를 받으면 이전 값으로 실행합니다.
              2. Object.is로 비교해 같으면 멈춥니다.
              3. 칸의 값을 바꿉니다.
              4. 다시 그리기를 예약합니다.

              setState 함수는 칸이 만들어질 때 한 번만 생기므로, 렌더가 반복돼도 같은 함수이고 언제 불러도 자기 칸을 찾아갑니다.

              여러 상태 변경을 한 번에 처리하는 방법

              예약 표시가 이미 켜져 있으면 다시 예약하지 않습니다. 첫 setState만 queueMicrotask로 렌더를 예약하고, 나머지는 칸의 값만 바꿉니다. 이벤트 처리가 끝난 직후 렌더가 한 번 돕니다.

              setTimeout(0)은 쓰지 않았습니다. 브라우저가 그 사이에 화면을 먼저 그려서 상태가 반만 바뀐 화면이 보일 수 있기 때문입니다. 마이크로태스크는 그리기 전에 실행됩니다.

              17. 다른 구현과 다른 점

              • LIS 기반 이동: 가장 긴 증가 부분 수열로 움직이지 않을 노드를 골라 이동을 줄입니다.
              • 브라우저 교차 검증: 연산 수와 MutationObserver가 본 변경 수를 나란히 보여 줍니다.
              • 노드 지도: 실제 DOM 노드마다 칸을 그려, 전체 중 어디가 바뀌었는지 보여 줍니다.
              • 렌더 줄이기: 검색 결과가 1개면 글자를 더 쳐도 렌더하지 않습니다.
              • 규칙 강제: 자식의 Hook 호출, 순서 변경, 무한 렌더를 조용히 넘기지 않고 알립니다.
              • 무작위 대조 테스트: 패치 결과를 새로 만든 DOM과 1,500쌍으로 비교합니다.
              • 화면 기능: 화면에서 바로 고치기, 지운 일 복원, 초과 시간 기록, 다크 모드가 있습니다.
              • 설치 없는 실행: 파일 하나를 더블클릭하면 서버 없이 열립니다.

              18. 파워셀 폴더의 추가 경로

              웹페이지는 Windows 기능을 직접 부를 수 없어서 notify-helper.ps1이 다리 역할을 합니다. 시간이 끝나면 페이지가 이 PC 안으로 요청을 보내고, 프로그램이 보낸 곳을 확인한 뒤 Windows 알림과 아이콘 깜빡임을 실행합니다. 페이지는 Chrome의 앱 모드 전용 창으로 열어서, 끌 때 다른 탭을 건드리지 않고 그 창만 닫습니다.

              19. 일부러 뺀 것과 한계

              • Fiber, 우선순위 스케줄링, 이벤트 위임, Fragment는 구현하지 않았습니다.
              • 상태가 루트에만 있어서 작은 변경에도 루트 함수 전체가 다시 실행됩니다.
              • 실험실의 입력 방어는 script, on 속성, javascript: 주소를 막는 최소 수준입니다. 실제 서비스라면 검증된 sanitizer를 써야 합니다.
              • 할 일은 이 브라우저의 localStorage에만 저장되어 다른 기기와 공유되지 않습니다.

# ADR 0001 : 저장소 해시를 키 있는 SipHash-2-4 로 바꾼다

## 상태

- 채택
- 날짜 : 2026-11-17

## 배경

- v1.0.0 의 `hash_key` 는 고정 상수를 쓰는 FNV-1a 입니다.
- 상수가 공개돼 있어서 누구나 같은 값을 계산할 수 있습니다.
- 공격자는 같은 버킷으로 몰리는 키 N개를 미리 만들어 SET 으로 보냅니다.
- 그러면 한 버킷의 체인 길이가 N 이 됩니다.
- 체인 끝까지 따라가며 비교해야 하므로 N개를 넣는 전체 비용이 O(N^2) 이 됩니다.
- 서버는 단일 스레드라서 그동안 모든 클라이언트가 멈춥니다.
- 이것이 해시 충돌 공격(hash flooding)입니다.

## 결정

- 서버 시작 때 운영체제 난수로 무작위 128비트 키를 한 번 뽑습니다.
- 그 키로 SipHash-2-4 를 계산해 버킷을 정합니다.
- 키는 프로세스 안에만 있고 파일에 저장하지 않습니다.
- 난수를 얻지 못하면 예측 가능한 키로 돌리지 않고 `store_init` 이 실패합니다.

## 알고리즘

### 무엇이 문제였나 : FNV-1a

- FNV-1a 는 64비트 값 하나를 상태로 둡니다.
- 시작값(offset basis)과 곱하는 수(prime)가 고정된 공개 상수입니다.
- 입력 바이트마다 `상태 = (상태 XOR 바이트) × prime` 을 반복합니다.
- 계산에 들어가는 값이 입력과 공개 상수뿐이라서, 서버 밖에서도 어떤 키가 어느 버킷에 갈지 그대로 계산됩니다.

### 무엇으로 바꿨나 : SipHash-2-4

- SipHash 는 **비밀 키를 입력으로 받는 해시 함수**(keyed hash)입니다.
- 덧셈, 비트 회전, XOR 세 연산만 씁니다(ARX 구조). 곱셈과 표 조회가 없습니다.
- 이름의 2-4 는 라운드 수입니다. 입력 블록마다 2라운드, 마무리에 4라운드를 돕니다.
- 입력은 키 바이트열과 128비트 키, 출력은 64비트 값입니다.

`siphash24` 의 계산 순서는 네 단계입니다.

1. 초기화
   - 64비트 상태 4개(`v0` ~ `v3`)를 고정 상수로 채웁니다.
   - 128비트 키를 64비트 둘(`k0`, `k1`)로 나눠 상태에 XOR 합니다.
   - 이 시점부터 상태 256비트 전체가 키에 따라 달라집니다.
2. 블록 처리
   - 입력을 8바이트씩 리틀 엔디언 64비트 값 `m` 으로 읽습니다.
   - 블록마다 `v3 ^= m` → SipRound 2번 → `v0 ^= m` 을 합니다.
3. 마지막 블록
   - 남은 0 ~ 7바이트를 아래쪽에 채우고, 맨 위 바이트에 입력 길이를 넣어 블록 하나를 만듭니다.
   - 길이가 들어가므로 `"ab"` 와 `"ab\0"` 처럼 끝만 다른 입력이 다른 블록이 됩니다.
   - 이 블록도 2번 방식으로 처리합니다.
4. 마무리
   - `v2 ^= 0xff` 뒤 SipRound 를 4번 돕니다.
   - `v0 ^ v1 ^ v2 ^ v3` 을 64비트 결과로 돌려줍니다.

SipRound 한 번은 상태 4개를 서로 섞는 연산 묶음입니다.

- 두 상태를 더합니다 (`v0 += v1`, `v2 += v3`).
- 한쪽을 정해진 비트 수(13, 16, 21, 17, 32)만큼 회전합니다.
- 회전한 값에 더한 결과를 XOR 합니다.
- 입력 한 비트의 변화가 몇 라운드 안에 상태 256비트 전체로 퍼집니다.

### 해시 키로 무엇을 보완했나

| 비교 | FNV-1a (v1.0.0) | SipHash-2-4 (지금) |
|---|---|---|
| 계산에 들어가는 값 | 입력, 공개 상수 | 입력, 공개 상수, 비밀 키 128비트 |
| 내부 상태 | 64비트 1개 | 64비트 4개 |
| 섞는 연산 | XOR 와 곱셈 1번씩 | 덧셈 · 회전 · XOR 를 블록마다 2라운드, 끝에 4라운드 |
| 서버 밖에서 버킷 번호 계산 | 됩니다 | 키를 모르면 안 됩니다 |
| 같은 버킷에 몰리는 키 미리 만들기 | 됩니다 | 키를 모르면 안 됩니다 |

- 버킷 번호는 `해시 % 버킷 수` 입니다. 공격에는 이 번호를 미리 아는 것이 필요합니다.
- SipHash 는 키를 모르는 쪽에게 출력이 무작위 값과 구별되지 않도록 설계됐습니다.
- 그래서 키가 비밀인 동안에는 어떤 입력들이 같은 버킷에 갈지 서버 밖에서 고를 수 없습니다.
- 서버는 해시 값을 응답으로 내보내지 않으므로, 응답을 보고 키를 거꾸로 추정할 재료도 주지 않습니다.

### 이 저장소에 적용한 흐름

1. `store_init` 이 `fill_random` 으로 16바이트를 얻습니다. Windows 는 `rand_s`, POSIX 는 `/dev/urandom` 입니다.
2. 그 16바이트를 `Store.hash_seed` 에 둡니다. 서버가 켜져 있는 동안 바뀌지 않습니다.
3. `hash_key` 가 `siphash24(키 바이트, 길이, hash_seed)` 를 계산합니다.
4. 결과를 `해시 % 버킷 수` 로 나눠 버킷을 정합니다.
5. 계산한 해시는 항목(`Entry.hash`)에 저장해 둡니다. 테이블을 넓혀 옮길 때 다시 계산하지 않습니다.

## 검토한 대안과 버린 이유

1. FNV-1a 에 무작위 시드만 섞기
   - 구현은 가장 쌉니다.
   - 하지만 시드와 무관하게 FNV 내부 상태가 같아지는 충돌 입력이 남을 수 있습니다.
   - 그런 입력은 시드를 몰라도 만들 수 있으므로 막는다는 근거가 약합니다.
2. SHA-256
   - 키가 없는 해시라서 공격자도 똑같이 계산할 수 있습니다.
   - 짧은 키 하나에 쓰기에는 느립니다.
3. 체인 대신 다른 충돌 처리 방식
   - 저장소 구조 전체를 바꾸는 일이라 이번 범위 밖입니다.

## 결과

얻는 것

- 키를 모르는 공격자가 같은 버킷으로 몰리는 키를 미리 계산할 수 없습니다.
- 테스트로 입증할 수 있는 근거가 생겼습니다 (아래 검증).

내주는 것

- 짧은 키에서는 FNV-1a 보다 느립니다.
- 벤더링한 소스 파일 `src/siphash.c` 하나가 늘었습니다.
- 서버가 시작될 때마다 버킷 배치가 달라져 순회 순서(스냅샷 저장 순서)가 실행마다 달라집니다.

공개 API 변화

- `store_init_with_key(Store *, const uint8_t key[16])` 추가 : 테스트가 키를 직접 줍니다.
- `store_longest_chain(const Store *)` 추가 : 가장 긴 체인 길이를 돌려주는 진단 함수입니다.
- `store_init` 의 시그니처는 그대로입니다.

저장 형식

- 스냅샷과 AOF 는 해시 값을 저장하지 않으므로 형식이 바뀌지 않습니다.
- 기존 파일은 그대로 읽힙니다.

## 검증

- `tests/test_siphash.c`
  - 참조 저장소의 공식 테스트 벡터 64개(길이 0부터 63)와 `siphash24` 출력을 대조합니다.
  - 구현이 SipHash-2-4 와 같다는 것을 증명합니다.
- `tests/test_store.c` 의 `test_old_collision_keys_spread`
  - 옛 FNV-1a 의 하위 12비트가 모두 0 인 키 1000개를 모읍니다.
  - 옛 해시에서는 전부 같은 버킷이므로 체인 길이가 1000 이었습니다.
  - 같은 키를 SipHash 저장소에 넣었을 때 측정한 가장 긴 체인은 4 였습니다.
  - 1000개 모두 GET 으로 조회됩니다.
- `tests/test_store.c` 의 `test_hash_key_changes_bucket_layout`
  - 키가 다른 두 저장소는 같은 문자열을 다른 버킷에 넣습니다.
  - 같은 키로 만든 저장소는 같은 버킷에 넣습니다.
- 증명하지 못한 것
  - SipHash 의 암호학적 강도는 이 테스트로 증명하지 않습니다. 참조 구현과 공개된 분석을 믿습니다.

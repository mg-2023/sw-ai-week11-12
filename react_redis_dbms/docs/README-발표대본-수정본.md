# 끝말잇기로 보는 Mini Redis — 말하는 부분만 (수정본)

> 굵은 글씨 [화면] 은 화면 넘기기 표시라 읽지 않습니다.
> 예상 시간: 대본 약 3:09~3:27 + 시연 10~20초 = 약 3:19~3:47 (4분 안)

## 0:00–0:20 | 시작  ·  📍 README 맨 위 · 🎯 레디스 기능 = 게임 규칙 (표)

**[화면: 레디스 기능 = 게임 규칙 표]**

1. 안녕하세요.
2. 저는 Node.js로 Mini Redis를 만들었습니다.
3. 해시 테이블, TTL, 잠금, 캐시, AOF 기능을 구현하고,
4. 그 기능들로 끝말잇기 게임을 만들어 보았습니다.

## 0:20–0:45 | 구조  ·  📍 README 맨 위 · 🎯 아래 구조 그림

**[화면: 브라우저 → 게임 서버 → Mini Redis / Mini DBMS 그림]**

1. 브라우저가 요청을 보내면, 서버는 데이터를 보관 기간에 따라 두 저장소에 나눠 저장합니다.
2. 단어 사전이나 끝난 게임 기록은 Mini DBMS에 오래 보관하고,
3. 진행 중인 판의 상태는 Mini Redis에 잠깐 둡니다.

> 시간 부족 시 2~3번 대신: "오래 둘 건 DBMS, 잠깐 둘 건 Redis에 저장합니다."

## 0:45–1:25 | 해시 테이블  ·  📍 2절 해시 테이블

**[화면: 버킷 배열과 연결 리스트 그림]**

1. 저장소의 중심은 직접 만든 해시 테이블입니다.
2. 키를 FNV-1a 해시값으로 바꾸고, 그 값으로 버킷을 고릅니다.
3. 충돌이 일어나면 연결 리스트로 이어 둡니다.
4. 적재율이 75%를 넘으면 버킷을 두 배로 늘리고 데이터를 다시 배치합니다.
5. 평소 조회와 저장은 평균 O(1)이지만, 버킷을 늘리는 순간에는 모든 데이터를 한 번에 옮겨서 후속 명령이 잠시 대기합니다.

## 1:25–1:55 | TTL  ·  📍 3절 TTL

**[화면: TTL 시퀀스 그림]**

1. 10초 제한 시간은 브라우저 시계가 아니라, 서버에 저장된 턴 키의 만료 여부로 판정합니다.
2. 차례가 시작되면 TTL을 최대 10초로 설정하고, 다음 요청에서 만료 여부를 확인해 시간 초과와 목숨 차감을 처리합니다.
3. 만료된 키는 조회할 때 지우는 지연 삭제와, 0.1초마다 정리하는 주기 삭제를 함께 씁니다.

## 1:55–2:25 | 캐시와 무효화  ·  📍 4절 캐시와 무효화

**[화면: 첫 조회는 DBMS, 다음 조회는 캐시 적중으로 바뀌는 과정 캡처]**

1. 사전 조회는 캐시 어사이드 방식입니다.
2. 캐시를 먼저 보고, 없으면 DBMS에서 읽어 60초 동안 캐시에 둡니다.
3. 일반적인 순차 요청에서는 단어가 바뀌면 관련 캐시 키를 바로 지웁니다.
4. 다만 진행 중인 조회가 무효화 뒤에 옛 결과를 다시 쓰면, 그때부터 60초 동안 낡은 값이 남을 수 있는 한계가 있습니다.

## 2:25–3:00 | 동시성  ·  📍 6절 동시성

**[화면: 동시성 표]**

1. Mini Redis의 각 명령은 처리 도중 다른 명령이 끼어들지 않습니다. *(시간 부족 시 생략, 약 -7초)*
2. 판 번호는 INCR로 발급하고, 같은 판의 동시 입력은 NX 조건의 5초 잠금으로 제어합니다.
3. 다만 작업이 5초를 넘기면 잠금이 만료되어 요청이 중복 처리될 수 있습니다.

## 3:00–3:25 | AOF 복구  ·  📍 8절 AOF

**[화면: AOF 기록 예시]**

1. 서버가 꺼졌을 때를 대비해 AOF 방식을 썼습니다.
2. 데이터 변경 내역을 프로젝트 전용 JSON 형식으로 파일 끝에 기록하고, 재시작할 때 다시 적용합니다.
3. 기본 설정은 약 1초 간격으로 디스크 반영을 요청해서, 강제 종료 때는 최근 기록 일부가 유실될 수 있습니다.

## 3:25–3:45 | 성능  ·  📍 9절 성능 (실측)

**[화면: 성능 표]**

1. 캐시 효과를 확인하려고, 20만 단어 데이터에서 단어 100개를 3번씩 조회해 봤습니다.
2. 캐시를 쓰니 DBMS 조회는 300회에서 100회로 줄었고,
3. 평균 응답 시간은 56밀리초에서 16밀리초로 줄었습니다.

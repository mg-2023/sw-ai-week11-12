### 0:20–0:45 | 구조  ·  📍 README 맨 위 · 🎯 레디스 기능 = 게임 규칙 (아래 구조 그림)

**[화면: 브라우저 → 게임 서버 → Mini Redis / Mini DBMS 그림]**

> 브라우저가 요청을 보내면 게임 서버는 데이터를 보관 기간에 따라 두 저장소에 나눠 저장합니다.
> 단어 사전이나 끝난 게임 기록은 Mini DBMS에 오래 보관하고, 진행 중인 판의 상태는 Mini Redis에 잠깐 둡니다.
> Mini Redis는 실제 Redis 프로토콜 호환이 아니라, HTTP와 JSON으로 통신하는 학습용 구현입니다.

> [!TIP]
> **저장소를 데이터를 얼마나 오래 둘지로 나눴다**
> - 오래 둘 원본(사전, 끝난 판) → DBMS / 잠깐 쓸 상태(진행 중인 판) → 레디스
> - 같이 말할 한계: 실제 Redis 프로토콜(RESP)이 아니라 HTTP + JSON

### 0:45–1:25 | 해시 테이블  ·  📍 2절 해시 테이블 — 모든 키가 들어가는 곳

**[화면: 버킷 배열과 연결 리스트 그림]**

> 저장소의 중심은 직접 만든 해시 테이블입니다. 키를 FNV-1a 해시값으로 바꾸고, 그 값으로 버킷을 선택합니다.
> 충돌은 연결 리스트로 이어 둡니다.
> 적재율이 75%를 넘으면 버킷을 두 배로 늘리고 데이터를 다시 배치합니다. 평소 조회와 저장은 평균 O(1)이지만, 버킷을 늘리는 순간에는 모든 데이터를 한 번에 옮겨 후속 명령이 잠시 대기합니다.

> [!TIP]
> **Map / Object 없이 버킷 배열 + 연결 리스트로 직접 만들었다**
> - 짚을 곳: 그림의 [5]번 칸 (word:기차 와 game:7:turn 이 같은 칸에 연결 리스트로 이어진 모습)
> - 흐름: FNV-1a로 숫자 → 버킷 고르기 → 충돌은 연결 → 75% 넘으면 2배 → 리스트가 짧게 유지돼서 평균 O(1)
> - 
> - FNV-1a 해시값: 키 문자열을 숫자 하나(32비트)로 바꾼 값. 정해진 시작값에서 출발해 글자마다 "XOR로 섞고 → 소수 16777619를 곱하기"를 반복해서 만듦. 같은 키는 항상 같은 값, 한 글자만 달라도 값이 크게 달라져서 키가 버킷에 고르게 흩어짐 (예: 버킷 16칸일 때 `game:7` → 0번 칸, `game:8` → 13번 칸)
> - 
> - 버킷: 키를 담는 칸. 해시 테이블은 번호 붙은 칸(버킷)이 늘어선 배열이고, 해시값으로 몇 번 칸에 넣을지 정함 → 찾을 때 전체를 훑지 않고 그 칸 하나만 보면 돼서 빠름. 같은 칸에 키가 여러 개 오면(충돌) 칸 안에서 연결 리스트로 이음 (그림의 [0], [1], [2] … 가 버킷, capacity = 버킷 개수)
> - 같이 말할 한계: 늘리는 순간 전부 옮기느라 다른 명령이 잠깐 기다림

### 1:25–1:55 | TTL  ·  📍 3절 TTL — 10초 제한 시간

**[화면: TTL 시퀀스 그림]**

> 10초 제한 시간은 브라우저 시계가 아니라 서버에 저장된 턴 키의 만료 여부로 판정합니다. 차례가 시작되면 TTL을 최대 10초로 설정하고, 다음 요청에서 만료 여부를 확인해 시간 초과와 목숨 차감을 처리합니다.
> 만료된 키는 조회 시점에 지우는 지연 삭제와, 0.1초마다 정리하는 주기 삭제를 함께 씁니다.

> [!TIP]
> **제한 시간을 화면 시계가 아니라 서버의 키 만료로 판정한다 → 브라우저를 조작해도 시간을 못 늘림**
> - 짚을 곳: 시퀀스 그림의 갈림길 (남은 ms면 계속, -2면 시간 초과)
> - 덧붙일 점: 지연 삭제(만료된 값은 절대 안 돌려줌) + 주기 삭제(안 찾는 키도 정리)
> - "최대"인 이유: 라운드 시간(10~150초, 끄투 선택지)도 같은 키로 잰다. TTL = min(10초, 라운드 남은 시간) → 키 하나로 제한 시간 두 개 (질문 나오면 Q3)

### 1:55–2:25 | 캐시와 무효화  ·  📍 4절 캐시와 무효화 — 사전 확인

**[화면: 첫 조회는 DBMS, 다음 조회는 캐시 적중으로 바뀌는 과정 캡처]**

> 사전 조회는 캐시 어사이드(Cache-Aside) 방식입니다. 캐시를 먼저 보고, 없으면 DBMS에서 읽어 60초 동안 캐시에 둡니다.
> 일반적인 순차 요청에서는 단어가 변경되면 관련 캐시 키를 바로 지웁니다.
> 다만 진행 중인 조회가 무효화 뒤에 옛 결과를 다시 쓰면, 그때부터 60초 동안 낡은 값이 남을 수 있는 한계가 있습니다.

> [!TIP]
> **34만 줄을 매번 훑지 않도록 결과를 60초 캐시한다 (Cache-Aside)**
> - 짚을 곳: 캡처에서 첫 조회 DBMS → 두 번째 레디스
> - 무효화가 꼭 필요한 이유: "없는 단어"도 캐시해서, 안 지우면 방금 등록한 단어가 60초 동안 거절됨
> - 같이 말할 한계: 조회와 등록이 겹치면 옛 값이 60초 남을 수 있음
> - 대본엔 없지만 짚을 만한 점: 새 라운드마다 `delByPrefix game:<번호>:used:` 로 나온 단어를 한꺼번에 비움 (키 이름을 접두사로 묶어 둔 덕분)

### 2:25–3:00 | 동시성  ·  📍 6절 동시성 — 잠금과 incr

**[화면: 동시성 표]**

> Mini Redis의 각 명령은 처리 도중 다른 명령이 끼어들지 않습니다.
> 판 번호는 INCR로 발급하고, 같은 판의 동시 입력은 NX 조건의 5초 잠금으로 제어합니다.
> 작업이 5초를 넘기면 잠금이 만료돼 요청이 중복 처리될 수 있습니다.

> [!TIP]
> **명령 하나는 중간에 끼어들 수 없게 만들고, "읽고-계산하고-쓰기"를 명령 하나(INCR, NX)로 묶었다**
> - 짚을 곳: 표의 결과 칸 (동시 8번 → 1번만 처리, 500번 → 정확히 500)
> - 같이 말할 한계: 처리가 5초를 넘기면 잠금이 풀려 중복 처리될 수 있음
> - 대본엔 없지만 보여 줄 수 있는 점: "같이 하기"(같은 와이파이, 2~4명)도 방마다 `room:<번호>:lock` nx 로 같은 방식. 시연에서 폰 두 대로 같은 방에 들어가면 사람 둘이 실제로 동시에 요청함 (`npm run room`, 📍 6절 아래 "같이 하기 — 여럿이 한 방에서" 소절의 키 대응표 · 그림)

### 3:00–3:25 | AOF 복구  ·  📍 8절 AOF — 서버가 꺼져도

**[화면: AOF 기록 예시]**

> 서버가 꺼졌을 때를 대비해 AOF 방식을 썼습니다. 데이터 변경 내역을 프로젝트 전용 JSON 형식으로 파일 끝에 기록하고, 재시작할 때 다시 적용합니다.
> 기본 설정은 약 1초 간격으로 디스크 반영을 요청하며, 강제 종료 때 최근 기록 일부가 유실될 수 있습니다.

> [!TIP]
> **바뀐 명령을 파일 끝에 한 줄씩 적고, 다시 켤 때 처음부터 재실행한다**
> - 짚을 곳: 기록 예시 세 줄 (set, set, del)
> - 같이 말할 한계: 약 1초마다 디스크에 반영해서, 강제 종료 땐 최근 기록을 잃을 수 있음
> - 대본엔 없지만 짚을 만한 점: 만료를 "10초 뒤"가 아니라 "끝나는 시각"으로 적어서 꺼져 있던 시간도 그대로 지나간 것으로 처리됨

### 3:25–3:45 | 성능  ·  📍 9절 성능 (실측)

## 질문 대비 (발표 중에는 읽지 않기)

> 기본 정의보다 "구현이 맞게 동작하는지, 어디까지 보장하는지"를 묻는 질문만 남겼습니다. 정의는 바로 아래 용어 줄에, 설계 이유는 맨 아래 표에 따로 두었습니다.
> 테스트로 확인한 내용은 "테스트 코드가 있다"와 "실행해서 통과했다"를 나눠 말합니다. 2026-11-18 에 레디스 59개 · 게임 112개 · DBMS 86개를 실행해 모두 통과했습니다. 벤치마크는 이날 다시 돌리지 않았습니다 (README 9장의 값).
> 난이도: 🟢 하 · 🟡 중 · 🔴 상

**용어 (한 줄씩)**
- **Cache-Aside**: 앱이 캐시를 먼저 보고, 없으면 원본(DBMS)에서 읽어 캐시에 넣는 방식
- **AOF** (Append Only File): 데이터를 바꾼 명령을 파일 끝에 한 줄씩 덧붙인 기록. 다시 켤 때 처음부터 다시 실행해 복구
- **TTL 응답**: `-1` = 키는 있고 만료가 없음, `-2` = 키가 없음 (만료돼 지워진 것 포함). 실제 Redis 와 같은 규칙
- **기록 탭의 조회 성공 / 실패**: 미니 레디스 `GET` 에서 키가 있었던 / 없었던 횟수. 틀린 답의 수가 아님 ("없는 단어"라는 캐시 값은 성공, 아직 안 나온 단어 확인은 실패로 셈)

### Q2. 해시 테이블  ·  📍 2절

- 🟢 **충돌은 어떻게 해결하고, 적재율에 따라 테이블을 언제 늘리거나 줄이나요?**
  → 분리 연결법입니다. 같은 버킷에 온 노드를 `next` 로 잇고, 찾을 때 키를 직접 비교합니다. 버킷 16개로 시작해서 키 수가 버킷 수의 0.75배를 넘으면 2배로 늘리고, 0.125배 아래로 내려가면 절반으로 줄입니다. 16개 아래로는 줄이지 않습니다.
- 🟡 **`해시 & (capacity - 1)` 로 버킷을 정하려면 어떤 조건이 필요한가요?**
  → capacity 가 2의 거듭제곱이어야 합니다. 그래야 `capacity - 1` 의 아래쪽 비트가 전부 1이 되어, AND 결과가 `해시 % capacity` 와 같아집니다. 그래서 크기를 바꿀 때도 2배 또는 절반으로만 바꿉니다.
- 🔴 **키가 많을 때 리사이즈가 다른 명령에 주는 영향은요? 지연 시간은 쟀나요?**
  → 리사이즈는 동기 함수라서 모든 노드를 한 번에 옮기는 동안 다른 명령은 줄을 서서 기다립니다. 키 수에 비례하는 O(n) 작업입니다. 그 지연 시간은 재지 않았습니다 (테스트는 10만 개를 넣고 모두 조회되는지만 확인합니다). 실제 Redis 는 테이블 두 개를 두고 조금씩 옮기는 점진적 rehash 로 이 멈춤을 줄입니다.

### Q3. TTL · 만료  ·  📍 3절

- 🟡 **만료 시각이 지난 뒤 서버는 시간 초과를 언제 반영하나요? 요청이 안 오면요?**
  → 키가 사라져도 서버가 먼저 움직이지는 않습니다. 단어를 낼 때, 또는 화면 시계가 0 이 되어 판 상태를 물을 때 `TTL` 이 -2 인 것을 보고 그때 목숨을 뺍니다. 판정은 서버가 요청을 처리하는 순간 기준이라, 9.9초에 보냈어도 처리될 때 10초가 지났으면 시간 초과입니다. 요청이 아예 오지 않으면(창을 닫음) 목숨은 빠지지 않고, 판 상태 키가 30분 뒤 만료돼 판 기록 없이 사라집니다. 상대의 생각 시간도 같은 차례 키라서, 상대의 단어도 키가 사라진 뒤 첫 요청에서 나옵니다.
- 🟡 **지연 삭제와 주기 삭제를 왜 같이 쓰나요?**
  → 지연 삭제는 그 키를 쓰는 명령이 올 때 만료를 보므로 만료된 값을 돌려주지 않습니다. 하지만 다시 찾지 않는 키(창을 닫고 떠난 판의 키 등)는 메모리에 남습니다. 그래서 0.1초마다 키를 20개 이상 훑어 지우는 주기 삭제를 같이 씁니다 (1/4 넘게 만료였으면 바로 다시, 한 번에 최대 10번). 전체를 한 번에 훑지 않는 이유는 그동안 다른 명령이 멈추기 때문입니다.
- 🟡 **라운드 시간과 차례 제한 시간을 키 하나로 어떻게 처리하나요?**
  → 차례 키의 TTL 을 `min(10초, 라운드 남은 시간)` 으로 겁니다. 단어를 받으면 이번 차례에 쓴 시간(건 TTL − 남은 TTL)을 라운드 시간에서 빼고, 라운드 시간 때문에 키가 먼저 사라졌으면 `round-time` 으로 목숨을 뺍니다. 상대 차례에는 같은 키에 상대의 생각 시간(0.1~1초)을 걸고, 생각한 시간도 라운드 시간에서 뺍니다. 화면의 차례 막대는 매 차례 10초로 다시 차지만, 실제 마감은 짧은 쪽입니다.

### Q4. 캐시 · 무효화  ·  📍 4절

- 🟡 **"없는 단어"도 캐시하는 이유는요? 등록과 조회가 겹치면 어떤 문제가 생기나요?**
  → 없는 단어를 반복해서 내면 매번 약 34만 줄을 끝까지 훑어야 해서, "없음"이라는 결과도 60초 캐시합니다. 그래서 단어를 등록하면 그 캐시를 바로 지웁니다 (무효화). 문제는 순서가 겹칠 때입니다: ① 조회 A 가 캐시에 없어서 DBMS 를 읽기 시작 → ② 등록 B 가 DBMS 에 넣고 캐시를 지움 → ③ A 가 등록 전에 읽은 "없음"을 캐시에 씀. 그러면 최대 60초 동안 방금 등록한 단어가 거절됩니다. 고치려면 키마다 세대 번호를 두고, 조회를 시작할 때와 번호가 다르면 저장하지 않게 하면 됩니다 (구현하지 않았습니다).
- 🟡 **같은 캐시 키에 MISS 가 동시에 나면 DBMS 조회를 어떻게 줄이나요?**
  → 게임 서버 안에 "지금 원본을 읽는 중인 키 → Promise" 표(`loading` Map)를 둡니다. 같은 키를 놓친 요청은 새로 읽지 않고 먼저 시작한 Promise 를 같이 기다려서, DBMS 는 한 번만 읽습니다 (`redis/src/cache.js`). 이 동작만 따로 검사하는 자동 테스트는 없습니다. 표는 프로세스 안에만 있어서, 게임 서버가 여러 대면 서버마다 한 번씩 읽습니다.
- 🔴 **미니 레디스가 멈추면 계속되는 경로와 멈추는 경로는요?**
  → 캐시는 레디스 오류를 무시하고 DBMS 에서 읽도록 되어 있어서 단어 확인 · 후보 찾기 · 순위는 느려질 뿐 동작합니다. 판 상태 · 차례 시간 · 잠금 · 판 번호 · 로그인 세션 · 같이 하기 방은 레디스에만 있어서 판 진행과 로그인은 멈춥니다. 캐시 쪽만 장애에 대비돼 있고, 상태 저장소로서는 단일 장애 지점입니다.

### Q6. 동시성 · 같이 하기  ·  📍 6절 (같이 하기는 6절 아래 소절)

- 🟡 **저장소 명령 하나의 원자성과 한 차례 처리 전체의 트랜잭션은 어떻게 다른가요?**
  → 명령 하나는 중간에 `await` 가 없는 동기 함수라서 다른 명령이 끼어들 수 없습니다. 네트워크로 받고 보내는 부분은 겹치지만, 본문을 다 받은 뒤 명령을 실행하는 부분은 동기 호출 한 번입니다. 그래서 `INCR` 은 읽고 더하고 쓰기가 쪼개지지 않습니다 (동시 `incr` 500번 → 500: `redis/src/__tests__/api.test.js` 에 테스트가 있고, 2026-11-18 실행해 통과). 하지만 한 차례에 쓰는 여러 명령(나온 단어 표시, 판 상태, 차례 키)과 판이 끝날 때의 DBMS 기록은 하나로 묶이지 않아서, 중간에 실패하면 일부만 반영될 수 있습니다. 같은 판은 잠금으로 한 번에 한 요청만 처리해서 요청끼리 섞이지는 않습니다 (동시 제출 8번 → 1번만 처리: `game/__tests__/service.test.js`, 같은 날 실행해 통과).
- 🔴 **잠금 처리가 5초보다 오래 걸리면요? 잠금을 풀 때 소유자를 확인하나요?**
  → 확인하지 않습니다. 처리가 5초를 넘기면 잠금이 먼저 만료돼 같은 판에 다음 요청이 들어올 수 있고, 첫 요청이 끝나면서 `DEL` 로 두 번째 요청의 잠금까지 지울 수 있습니다. 고치려면 요청마다 다른 값을 잠금에 넣고 "내 값일 때만 지우기"를 명령 하나로 만들어야 합니다. 한 차례 처리 시간을 잰 값은 없어서, 이 일이 얼마나 자주 생기는지는 말할 수 없습니다.
- 🟡 **방 상태를 왜 폴링으로 전하나요? 방 요청은 어떻게 한 번에 하나씩 처리하나요?**
  → 미니 레디스에 Pub/Sub 같은 알림이 없어서, 화면이 0.5초마다 방 상태를 묻습니다. 4명이면 한 방에서 1초에 최대 8번이고, 바뀐 내용은 0.5초 안팎 늦게 보입니다. 방 요청(들어가기 · 시작 · 단어 · 나가기)은 `room:<번호>:lock` 을 nx 로 잡아 한 번에 하나씩 처리하고, 차례가 아닌 사람의 단어는 거절합니다. 방 상태 조회는 시간 초과를 반영할 때만 잠금을 잡고, 이미 잠겨 있으면 409 대신 지금 상태를 돌려줍니다. 실제 Redis 의 Pub/Sub 을 써도 브라우저까지 밀어 주려면 WebSocket 같은 연결이 따로 필요합니다.

### Q8. AOF  ·  📍 8절

- 🟡 **everysec 에서 강제 종료하면 기록이 얼마나 사라질 수 있나요?**
  → 기록은 바뀔 때마다 한 줄씩 바로 파일에 씁니다(`writeSync`). 그래서 프로세스만 강제로 죽으면 이미 쓴 줄은 운영체제에 넘어가 있어 남습니다. 사라질 수 있는 것은 운영체제가 멈추거나 전원이 나갈 때, 마지막 `fsync` 이후의 기록입니다. `fsync` 를 1초마다 부르므로 보통 최근 약 1초 분량인데, 1초는 상한이 아닙니다 (이벤트 루프가 바쁘면 타이머가 늦어지고, 저장 장치의 쓰기 캐시에도 영향을 받습니다). 강제 종료(`SIGKILL`) 뒤 복구 테스트는 `aof.test.js` 에 있고 같은 날 실행해 통과했지만, 이 테스트는 `fsync: 'always'` 로 돌리고 전원 차단은 시험하지 않았습니다.
- 🟡 **만료를 왜 "끝나는 시각"으로 남기나요? 손상된 AOF 는 어디까지 복구하나요?**
  → "10초 뒤"로 적으면 다시 켤 때마다 10초가 새로 시작됩니다. 끝나는 시각을 적으면 꺼져 있던 시간도 지나간 것으로 계산하고, 이미 지난 키는 복구하지 않습니다. 손상: 줄 단위로 읽다가 해석되지 않는 줄을 만나면 거기서 멈추고 그 앞까지만 복구합니다. 보통 쓰다 잘린 마지막 줄만 빠지지만, 파일 중간이 깨지면 그 뒤의 멀쩡한 기록까지 버립니다. 잘린 줄 테스트는 있고(같은 날 통과), 중간 손상 테스트는 없습니다.

### Q9. 성능  ·  📍 9절

- 🔴 **벤치마크의 데이터와 반복 조건은요? 실제 사전이나 실제 Redis 성능으로 일반화할 수 있나요?**
  → `bench/word-cache.js` 가 만든 3음절 가짜 단어 20만 개에서, 단어 100개를 3번씩 모두 300번 차례로 확인했습니다 (캐시 없는 실행을 먼저, 캐시 있는 실행을 그다음에). 결과는 DBMS 읽기 300번 → 100번, 평균 56 ms → 16 ms 입니다. 같은 단어를 3번씩 보는, 캐시에 유리한 조건이고 실행 순서를 바꿔 재지 않아서 3.5배는 이 조건에서 나온 값입니다. 실제 사전(약 34만 단어) · 실제 게임 · 실제 Redis 와는 비교하지 않았으므로 일반화할 수 없습니다. 이 수치는 README 9장의 값이고, 2026-11-18 에 다시 돌리지는 않았습니다.

### Q11. 없는 기능 · 커질 때의 병목  ·  📍 11절

- 🔴 **전체 구현에 없는 기능과, 커지면 병목이 되는 곳은요?**
  → 없는 것: RESP 프로토콜(HTTP + JSON 만), List · Hash · Set 같은 자료형(키 하나에 JSON 값 하나), 메모리 상한과 키 내보내기 정책, Pub/Sub, 트랜잭션(MULTI/EXEC), 점진적 리사이즈, 실행 중 AOF 줄이기. 병목이 될 곳: ① 단어를 낼 때마다 `keys('…:used:')` 로 전체 키를 훑는 O(n) 동기 작업 (방 목록도 `keys('room:')`), ② 한 번에 모두 옮기는 리사이즈, ③ `word` 열에 인덱스가 없어 캐시 MISS 때 DBMS 를 끝까지 훑는 것, ④ 같이 하기 폴링(사람 수만큼 요청). 지금 규모에서 이것들의 시간을 잰 적은 없습니다. ①은 라운드마다 나온 단어를 키 하나(JSON 배열)로 모으면 피할 수 있습니다.

### 설계 이유 (질문으로 두지 않고, 물으면 한두 문장으로)

| 구현 선택 | 설명할 이유 |
|---|---|
| HTTP + JSON | 어떤 언어에서든 호출하기 쉬운 API. 클라이언트는 연결을 최대 32개까지 다시 써서 연결 비용을 줄임. 요청마다 헤더가 붙어 RESP 보다 무거움. "과제 요구사항이라서"라고 말하려면 과제 안내서에서 먼저 확인 |
| DBMS 와 미니 레디스 분리 | 오래 둘 원본(단어 사전, 끝난 판 기록)은 DBMS, 진행 중인 상태 · 캐시 · 세션은 미니 레디스에서 빠르게 조회 |
| 해시 테이블 직접 구현 | 버킷 · 충돌 체인 · 크기 조절이 코드에 드러나고, `stats()` 로 capacity · 적재율 · 가장 긴 체인을 보여 줄 수 있음. "학습 목적"은 만든 사람의 의도로 말하기 |
| 시작 16 · 늘림 0.75 · 줄임 0.125 | 체인 길이와 메모리 사이의 절충. 실험으로 고른 값이 아니므로 "최적값"이라고 하지 않기 |
| 새 노드를 체인 맨 앞에 | 끝까지 가지 않아도 되어 넣기가 O(1). 같은 키가 있는지는 먼저 한 번 훑으므로 중복은 생기지 않음 |
| 지연 삭제 + 주기 삭제 | 만료된 값은 돌려주지 않으면서, 다시 찾지 않는 만료 키도 회수 |
| 캐시 TTL 60초 · 없는 단어도 캐시 | 같은 없는 단어를 반복해서 훑는 일을 줄이고, 무효화를 놓쳐도 낡은 값이 60초 안에 사라지게. 60초는 재서 고른 값이 아님 |
| 읽는 중인 Promise 공유 | 같은 키를 동시에 놓친 요청이 DBMS 를 한 번만 읽게 함 |
| NX 잠금 + 5초 TTL | 한 판을 한 요청씩 처리하고, 처리 중 프로세스가 죽어도 잠금이 영원히 남지 않게. 단 5초를 넘기면 소유자 확인 없는 `DEL` 로 남의 잠금을 지울 수 있음 (Q6) |
| AOF + 끝나는 시각 | 다시 켤 때 기록을 다시 실행하고, 꺼져 있던 시간도 만료 계산에 넣음. 1초마다 `fsync` 는 디스크 쓰기 비용과 최근 기록 손실 사이의 절충 |
| 같이 하기 폴링 | 미니 레디스에 Pub/Sub 이 없어서. 0.5초마다, 4명이면 1초에 최대 8번, 갱신은 0.5초 안팎 늦음 |

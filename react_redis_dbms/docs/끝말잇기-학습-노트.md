## 1. 전체 그림 — 책임과 원본

**한 줄 답**: 화면은 Mini React가 그리고, 진행 중인 판은 Mini Redis가 메모리에 들고, 단어 사전과 기록은 Mini DBMS가 파일에 남긴다. 게임 서버가 이 셋을 순서대로 호출한다.

### 1-2. 계층별 책임

| 계층 | 맡는 일 | 맡지 않는 일 |
|---|---|---|
| 화면 (`web/`, `mini-react/`) | 화면 상태 보관, 화면 계산, DOM 반영 | 서버 데이터의 원본 보관 |
| 게임 규칙 (`game/`) | 두음법칙, 등급, 목숨, 턴 판정, 로그인 | 저장 방식, 인덱스 구현 |
| 단기 상태 (`redis/`) | 판 상태, 턴 타이머, 잠금, 세션, 캐시 | 단어 사전 전체 보관 |
| 장기 저장 (`dbms/`) | 단어 사전, 끝난 판 기록, id 조회 | 진행 중인 판의 짧은 상태 |

**무엇의 원본(source of truth)인가**: 같은 저장소라도 데이터마다 원본이 다르다.

| 데이터                       | 원본         | 다른 쪽의 역할                          |
| ------------------------- | ---------- | --------------------------------- |
| 진행 중인 판 (목숨, 점수, 낸 단어 기록) | Mini Redis | DBMS는 이 상태를 모른다                   |
| 단어 사전                     | Mini DBMS  | Redis는 60초 캐시 (`word:`, `first:`) |
| 끝난 판 기록, 순위               | Mini DBMS  | Redis는 순위를 5초 캐시                  |

판 상태의 원본이 Redis이므로 DBMS 기록이 실패해도 진행 중인 판이 깨지지는 않는다. 다만 DBMS는 선택 사항이 아니다. 캐시에 없는 단어 확인과 시작 단어 뽑기가 DBMS를 부르고, `cache.js`는 Redis 오류만 삼키기 때문이다. DBMS가 멈췄을 때의 실제 동작은 실행해서 확인하지 않았다(코드 읽기에서 도출).

### 1-4. 호출할 때 기억할 것

- 화면 state를 바꾸는 코드는 UI 재계산만 요청한다. 서버에 저장하려면 `/api/...`를 따로 불러야 한다.
- Redis 명령은 키 하나를 빠르게 읽고 쓴다. 원본이 바뀌면 해당 캐시를 직접 지워야 하고, 안 지우면 TTL(60초)이 끝날 때까지 옛 값이 남을 수 있다.
- DBMS 질의는 조건에 따라 id 인덱스 경로와 전체 스캔 경로로 갈린다. 응답에 어느 계획을 탔는지가 들어 있다.
- 한 요청에서 셋을 함께 쓸 때 순서와 책임은 게임 서버가 조정한다. 세 저장소가 자동으로 하나의 트랜잭션으로 묶이지는 않는다.
- 문제가 생기면 먼저 볼 곳: 화면이 안 바뀐다 → setter · VNode · 패치 / 반복 조회가 느리다 → Redis HIT/MISS와 TTL / SQL이 느리다 → 응답의 계획이 `FULL_SCAN`인지.

### 1-7. 확인 질문
- 진행 중인 판의 상태는 어느 서버의 어느 저장 공간에 있는가?
- 단어가 사전에 있는지 묻는 요청이 DBMS까지 가지 않는 경우는 언제인가?

## 2. 화면 계층 — Mini React

**한 줄 답**: 상태가 바뀌면 화면 전체를 가벼운 객체(VNode)로 다시 계산하고, 이전 객체와 비교해서 달라진 DOM만 고친다.

### 2-1. 구조

```
mini-react/
├── vdom.js       # DOM ↔ VNode 변환
├── compo.js      # h() 요소 생성, 함수 컴포넌트 펼치기
├── diff.js       # 이전 VNode와 새 VNode 비교 → 패치 목록 (DOM을 건드리지 않음)
├── patch.js      # 패치 목록을 실제 DOM에 적용
├── component.js  # FunctionComponent (hooks 배열 보관)
├── hooks.js      # useState, useEffect, useMemo, batch
├── events.js     # 루트 컨테이너 한 곳에서 click 처리
└── root.js       # createRoot (마운트, 재렌더, 언마운트)
```

VNode는 문자열(텍스트 노드)이거나 `{ type, props, children, events }` 객체다.

### 2-2. 원리 ① — 함수는 매번 새로 실행되는데 상태는 어떻게 남는가

함수 컴포넌트의 지역 변수는 함수가 끝나면 사라진다. 그래서 상태를 함수 바깥에 둔다.

- `FunctionComponent` 객체가 `hooks` 배열을 가진다. 이 배열은 렌더 사이에 유지된다.
- 렌더를 시작할 때 커서를 0으로 되돌린다. `useState`를 부를 때마다 커서가 1씩 늘어난다.
- 같은 순서로 부르면 같은 칸을 읽는다. 훅을 조건문 안에서 부르면 안 되는 이유가 이 호출 순서 의존이다.

```javascript
// component.js (요지)
export class FunctionComponent {
  constructor(fn, props = null) {
    this.fn = fn;      // 렌더 함수 (예: App)
    this.hooks = [];   // 상태 칸 배열 — 렌더 사이에 유지된다
    this.vdom = null;  // 마지막 렌더 결과
  }
}
```

| 훅 | 칸에 저장하는 것 | 동작 |
|---|---|---|
| `useState(initial)` | `{ value }` | setter가 `Object.is`로 이전 값과 비교하고, 다를 때만 재렌더를 요청한다 |
| `useMemo(factory, deps)` | `{ value, deps }` | deps가 이전과 같으면 저장한 값을 돌려주고, 다르면 다시 계산한다 |
| `useEffect(effect, deps)` | deps와 cleanup | deps가 바뀐 effect를 대기열에 넣고, DOM 반영이 끝난 뒤 이전 cleanup → 새 effect 순서로 실행한다 |
| `batch(fn)` | 없음 | `fn` 안의 setter 여러 개를 모아 재렌더를 한 번만 한다 |

### 2-4. 원리 ③ — 리스너 하나로 모든 클릭을 처리한다

- 루트 컨테이너에 click 리스너를 하나만 단다(`events.js`의 `delegate`).
- 클릭된 DOM 노드에서 루트까지 올라가며 `childNodes` 인덱스 경로를 만든다.
- 같은 경로를 현재 VNode 트리에서 따라가 `events.click` 핸들러를 찾는다. DOM에 남은 오래된 함수가 아니라 루트가 들고 있는 최신 VNode의 핸들러를 쓴다.
- 찾은 핸들러를 `batch()` 안에서 실행한다.

DOM 노드마다 리스너를 달지 않으므로, 노드를 교체해도 핸들러를 다시 연결할 필요가 없다. 위임하는 이벤트는 click 하나다. Enter 키 입력은 `web/app.js`가 `useEffect`로 직접 연결한다.

### 2-5. 첫 마운트 (클릭 뒤 흐름은 흐름 html ③)

**첫 마운트**: 기존 DOM을 VNode로 읽음 → `App` 실행(훅 커서 0으로) → `h()`로 VNode 생성 → 이전 VNode와 비교 → DOM 패치 → 패치된 DOM을 다시 VNode로 읽어 검증 → 커밋 알림 → effect 실행.

### 2-6. 없으면 생기는 일

| 빠진 것 | 결과 |
|---|---|
| VNode 비교 | 상태가 바뀔 때마다 DOM 전체를 다시 만들어 입력 포커스와 스크롤 위치가 사라진다 |
| `hooks` 배열 | 재렌더마다 `useState`가 초기값을 돌려줘서 화면이 처음 상태로 돌아간다 |
| `batch()` | setter 세 번에 렌더가 세 번 일어난다 |
| 뒤에서부터 삭제 | 인덱스가 밀려 남겨야 할 노드를 지운다 |
| `Object.is` 비교 | 같은 값을 넣어도 재렌더가 일어난다 |

### 2-7. 한계

- 훅 저장소와 재렌더 콜백이 모듈 전역이다. 루트를 두 개 마운트하면 두 번째가 첫 번째의 훅 상태를 덮어쓴다.
- 자식을 key 없이 위치로 비교한다. 목록 맨 앞에 항목을 넣으면 뒤 항목이 모두 바뀐 것으로 판정된다.
- 패치 뒤에 화면 전체를 다시 읽어 검증한다. 바뀐 노드가 하나여도 검증 비용은 전체 노드 수에 비례한다.
- 훅은 루트 `App`에서만 쓴다. 자식 컴포넌트는 props만 받는 함수다.

### 2-8. 실제 React와 다른 점

이 프로젝트는 React 패키지를 쓰지 않고, 요소 생성 · 함수 컴포넌트 · 훅 · VDOM 비교 · 배칭의 개념만 직접 구현했다. 구현하지 않은 것은 JSX 변환기, key/ref, Fiber 스케줄러, concurrent 기능, Suspense, 컴포넌트별 독립 훅 저장소, `useLayoutEffect`, 넓은 이벤트 API다.

**핵심 차이 세 줄**
1. 상태가 루트 `App` 한 곳에만 있다. React는 컴포넌트마다 상태를 가진다.
2. 자식 목록을 위치로 비교한다. React는 key로 같은 항목을 추적한다.
3. 상태가 바뀌면 그 자리에서 동기적으로 다시 그린다. React는 스케줄러가 우선순위를 정해 나눠 처리한다.

| 항목 | Mini React | 실제 React |
|---|---|---|
| setter | 렌더마다 새 함수가 만들어진다 | identity가 안정적이다. 미니 setter를 effect deps나 자식 props에 쓰면 불필요한 effect 재실행이 생긴다 |
| effect 시점 | 커밋 직후 동기 실행 | 렌더/페인트 타이밍이 따로 있고, 개발 모드(Strict Mode)에서는 setup-cleanup을 한 번 더 돌린다 |
| 이벤트 | click만 위임 | 넓은 이벤트 API와 호환 계층 |
| `batch()` 효과 | setter m개가 VNode 생성 1회로 합쳐진다. 비교·패치·검증은 그대로 한 번씩 든다 | 업데이트 큐와 우선순위로 처리 |

**한 번 갱신하는 비용** (이전 문서의 정적 분석 기록): VNode 생성 O(V+Q) → 비교 O(VH+Q) → 패치 O(PH+…) → 검증 O(V+Q). V는 노드 수, H는 최대 깊이, Q는 비교한 props 수, P는 패치 수다. 비교에 H가 곱해지는 이유는 자식으로 내려갈 때마다 `[...path, i]`로 경로 배열을 새로 복사하기 때문이다. 깊이가 제한되면 O(V+Q)이고, 한쪽으로 깊게 치우친 트리는 O(V²+Q)까지 간다. 검증이 전체 트리를 읽으므로 바뀐 노드가 적어도 갱신 비용은 패치 수만으로 정해지지 않는다.

### 2-9. 확인 질문

- 0.2초마다 시계 상태가 바뀌는데도 단어 목록 변환이 다시 실행되지 않는 이유는 무엇인가?

## 3. 단기 상태 계층 — Mini Redis

**한 줄 답**: 키 하나로 값을 평균 O(1)에 찾는 메모리 저장소다. 키마다 만료 시각을 두고, 쓰기 명령을 파일에 한 줄씩 남겨 재시작 때 되살린다.

### 3-1. 구조

```
redis/src/
├── hash-table.js # FNV-1a 해시, 분리 연결법, 크기 조절
├── store.js      # 명령(get, set, incr, del), 만료 처리
├── aof.js        # 쓰기 기록 파일, 복구, 재작성
├── api.js        # HTTP API
├── client.js     # HTTP 클라이언트
└── cache.js      # Cache-Aside, 동시 미스 합치기
```

이 프로젝트에서 Mini Redis가 맡는 키:

| 키 | 용도 | 보관 시간 |
|---|---|---|
| `game:<번호>` | 진행 중인 판 상태 | 30분 (끝난 판은 10분) |
| `game:<번호>:turn` | 플레이어 차례. 사라지면 시간 초과 | 10초 |
| `game:<번호>:lock` | 한 판을 한 번에 한 요청만 다루는 잠금 (`nx`) | 5초 |
| `game:<번호>:used:<단어>` | 이번 판에 나온 단어 | 30분 |
| `session:<토큰>` | 제작자 로그인 상태 | 30분 |
| `login:fail:<접속 주소>` | 로그인 실패 횟수 | 1분 |
| 단어 캐시 | 사전 조회 결과 | 60초 |

### 3-5 · 3-7. html에 없는 세부

- 크기 조절은 요청을 처리하는 같은 실행 흐름에서 동기로 일어나서, 그동안 다른 명령이 기다린다.
- `incr`는 "1 더하기"가 아니라 계산이 끝난 값을 기록한다. 재생할 때 더하기를 다시 하지 않는다.
- SET 입력 검사: 키 512자 이하, 양수 TTL.
- TTL 없이 덮어쓰면 이전 만료 시각이 지워지고, `incr`는 기존 TTL을 유지한다.

### 3-8. 없으면 생기는 일

| 빠진 것 | 결과 |
|---|---|
| 크기 조절 | 키가 늘수록 버킷의 연결 리스트가 길어져 조회가 O(N)에 가까워진다 |
| 지연 삭제 | 10초가 지난 턴 타이머 키가 살아 있는 것으로 읽혀 시간 초과 판정이 틀린다 |
| 주기 삭제 | 끝난 판의 키가 메모리에 계속 쌓인다 |
| `nx` 잠금 | 같은 판에 두 요청이 동시에 들어와 단어 두 개가 한 차례에 처리된다 |
| 절대 시각 기록 | 재시작할 때마다 만료 시간이 처음부터 다시 흐른다 |
| 동시 미스 합치기 | 같은 단어의 미스 N개가 DBMS 전체 탐색 N번으로 이어진다 |

### 3-9. 한계와 실패 경로

- **메모리와 파일이 어긋날 수 있다**: `set`은 메모리를 먼저 바꾸고 AOF에 쓴다. 파일 쓰기가 실패하면 500을 응답하지만 메모리 값은 되돌리지 않는다.
- **fsync 1초는 목표값이다**: 타이머는 이벤트 루프가 한가할 때 실행된다. 긴 동기 작업이 있으면 1초보다 늦어진다.
- **깨진 기록 뒤는 읽지 않는다**: 복구 중 JSON 해석에 실패한 줄에서 멈춘다. 그 뒤의 멀쩡한 줄도 복구되지 않는다.
- **복구 비용이 로그 크기에 비례한다**: 파일 전체를 한 번에 읽어 줄 배열 → 기록 배열로 만든다(스트리밍 아님). 로그가 크면 시작 시간과 최대 메모리가 늘고, 재작성은 시작할 때만 한다(백그라운드 정리 없음). 만료 시각이 이미 지난 SET 기록은 복구에서 건너뛴다.
- **`nx`와 `xx`를 함께 주면 항상 거부된다**: 조건식이 `(nx && exists) || (xx && !exists)`이기 때문이다.
- **합치기는 한 프로세스 안에서만 된다**: `loading` Map은 프로세스마다 따로 있다.
- **접두사 삭제는 전체를 훑는다**: 키 배열 전체를 만든 뒤 걸러서 지운다. 그동안 다른 명령이 기다린다.
- **용량 한도가 없다**: TTL이 없는 키는 지울 때까지 남는다.

### 3-10. 실제 Redis와 다른 점

**핵심 차이 세 줄**
1. 통신이 HTTP + JSON이다. Redis는 전용 프로토콜(RESP)을 쓴다. Redis 클라이언트 드라이버로는 붙지 않는다.
2. 값이 JSON 한 종류다. Redis는 Hash · List · Set 등 자료형마다 명령이 있다.
3. 파일 쓰기와 재작성이 명령과 같은 스레드에서 동기로 실행된다. Redis는 fsync와 재작성을 백그라운드에서 처리한다.

| 항목 | Mini Redis | 실제 Redis |
|---|---|---|
| 트랜잭션 | 없다. 단일 명령(`incr`, `nx` 저장)만 섞이지 않는다 | MULTI/EXEC/WATCH로 여러 명령을 묶는다 |
| 키 순회 | `keys(prefix)`가 전체 키 배열을 한 번에 만든다 | SCAN이 커서로 나눠 조금씩 돌려준다 |
| 용량 | 한도와 eviction이 없다. TTL 만료만 있다 | maxmemory와 LRU/LFU 등 eviction. 만료(TTL)와 eviction은 다른 동작이다 |
| 영속화 | JSON AOF 하나. RDB · 복제가 없다. AOF도 명령 형식이 아니라 JSON 기록이다 | AOF + RDB, 백그라운드 rewrite, 복제 |

### 3-11. 확인 질문
- 보관 기간이 지난 키를 요청하면 어느 함수에서 무슨 일이 일어나는가?
- 여러 요청이 동시에 와도 `incr` 결과가 빠지지 않는 이유는 무엇인가?
- 서버가 5분 동안 꺼져 있었다면, TTL 10분으로 저장한 키는 재시작 뒤 몇 분 남는가?
- AOF 쓰기가 실패하면 메모리의 값과 파일의 기록은 각각 어떤 상태인가?
- 같은 키의 캐시 미스 5개가 동시에 오면 원본 조회는 몇 번인가? 서버 프로세스가 2개라면?

## 4. 장기 저장 계층 — Mini DBMS

**한 줄 답**: 행을 파일 끝에 한 줄씩 붙여 저장하고, `id → 파일 위치`를 메모리 B+ 트리에 둔다. id로 찾으면 한 줄만 읽고, 다른 컬럼으로 찾으면 파일 전체를 읽는다.

### 4-1. 구조

```
dbms/src/
├── tokenizer.js  # SQL 문자열 → 토큰
├── parser.js     # 토큰 → AST
├── engine.js     # 검증, 실행 계획 선택, 실행
├── table.js      # JSONL 파일 읽기 · 쓰기, 바이트 위치 추적
├── bplus-tree.js # 차수 64 메모리 B+ 트리
├── rw-lock.js    # SharedArrayBuffer + Atomics 읽기-쓰기 잠금
├── thread-pool.js# 워커 스레드 풀
├── db-worker.js  # 워커 한 개의 실행 루프
└── api.js        # HTTP API (/query)
```

### 4-2. 원리 ① — SQL 문자열이 실행되기까지

```
SQL 문자열 → [tokenizer] → 토큰 → [parser] → AST → [engine] 검증 → 실행 계획 → 파일 · 인덱스
```

`SELECT id FROM words WHERE word = '기차'`의 AST:

```json
{
  "type": "select",
  "table": "words",
  "columns": ["id"],
  "where": [{ "column": "word", "op": "=", "value": "기차" }],
  "orderBy": null,
  "limit": null
}
```

지원하는 문장은 `INSERT`와 `SELECT`다. `SELECT`는 `AND`로 이은 `WHERE`, `ORDER BY`, `LIMIT`, `COUNT(*)`를 받는다. tokenizer는 세미콜론으로 문장을 나누되, 문자열이나 주석 안의 세미콜론은 경계로 보지 않는다.

### 4-8. 요청 형식과 오류 (html에 없는 것만)

- 요청 형식: JSON이면 `sql` 필드, `text/plain`이면 본문 전체를 SQL로 읽는다. 빈 SQL이나 잘못된 JSON은 워커에 가기 전에 오류다.
- `LIMIT`만 있으면 상한에 닿는 즉시 멈출 수 있지만, `COUNT`나 `ORDER BY`가 있으면 후보를 모두 읽는다.

| 상황 | 처리 | 응답 |
|---|---|---|
| 문법 · 테이블 · 컬럼 · 타입 오류 | 파일을 바꾸기 전에 멈춘다 | 400 |
| 워커가 모두 바쁨, 대기열에 자리 있음 | 대기열에서 기다린 뒤 처리 | 정상 응답 |
| 대기열이 가득 참 (기본 1,000개) | `PoolBusyError` | 503 |
| 잠금을 10초 안에 못 잡음 | `LockTimeoutError` | 503 |
| 요청 본문이 8MB 초과 | 요청 거부 | 413 |

### 4-9. 없으면 생기는 일

| 빠진 것 | 결과 |
|---|---|
| B+ 트리 | 시작 단어 한 개를 뽑을 때마다 34만 줄을 처음부터 읽는다 |
| 리프의 `next` | 범위 조회에서 줄마다 루트부터 다시 내려간다 |
| 쓰기 잠금 | 두 워커가 같은 id를 부여하거나 줄이 섞여 기록된다 |
| 쓰기 대기 표시 | 읽기 요청이 끊이지 않으면 `INSERT`가 계속 밀린다 |
| `catchUp()` | 다른 워커가 넣은 행이 이 워커의 조회에서 보이지 않는다 |
| 쓰기 전 검증 | 타입이 틀린 행이 파일에 남는다 |

### 4-10. 한계

- 인덱스는 `id` 하나뿐이다. `word`로 찾으면 항상 `FULL_SCAN`이다.
- 인덱스가 메모리에만 있다. 서버를 켤 때 워커마다 파일 전체를 읽어 다시 만든다.
- `INSERT`는 `fs.writeSync`로 붙이고 fsync를 부르지 않는다. 시작할 때 `repairTableFile()`이 마지막 줄바꿈 뒤의 덜 쓰인 꼬리를 잘라낸다.
- `BEGIN`, `COMMIT`, `ROLLBACK`이 없다. 문장 하나가 쓰기 잠금 안에서 실행된다는 것까지가 보장 범위다.
- `ORDER BY`는 조건에 맞는 행을 모두 모아 메모리에서 정렬한다. `LIMIT 10`이어도 후보 전체를 읽는다.
- 워커 수 기본값은 `min(4, CPU 병렬 수)`이고 `THREADS` 환경 변수로 바꾼다.

### 4-11. 실제 DBMS(PostgreSQL 18 기준)와 다른 점

PostgreSQL은 이 프로젝트의 의존성이 아니라, 같은 문제를 범용 DBMS가 어떻게 푸는지 견주는 기준이다.

**핵심 차이 세 줄**
1. 인덱스가 `id` 하나이고 메모리에만 있다. PostgreSQL은 여러 인덱스를 디스크에 둔다.
2. 실행 계획을 규칙 세 개로 고른다. PostgreSQL은 통계로 비용을 추정해 고른다.
3. 잠금 단위가 테이블 전체다. PostgreSQL은 MVCC와 행 단위 잠금을 쓴다.

| 항목 | Mini DBMS | PostgreSQL |
|---|---|---|
| SQL 범위 | `INSERT`, `SELECT`. DDL · `UPDATE` · `DELETE` · `JOIN` · `OR` · 서브쿼리 없음 | 범용 SQL |
| `ORDER BY` | 후보를 모아 `Array.sort`. 인덱스 순서를 재사용하지 않는다 | 인덱스 순서로 읽거나, 비용을 비교해 정렬을 고른다 |
| 동시성 | 테이블 전체 읽기-쓰기 잠금. `INSERT`가 도는 동안 `SELECT`도 기다린다 | MVCC 스냅샷 + 행 잠금 |
| 내구성 | `writeSync`만. fsync · WAL · rollback이 없고, 시작 때 덜 쓰인 꼬리만 정리한다 | WAL로 crash recovery(REDO). `synchronous_commit` 기본값 `on`이면 로컬 WAL flush 뒤에 성공을 돌려주고, `off`면 최근 커밋 일부를 잃을 수 있다 |

꼬리 정리를 커밋 내구성 보장으로 읽으면 안 된다. 행 경계를 맞춰 줄 뿐, 여러 문장을 묶어 되돌리거나 시점 복구를 하지는 못한다.

**조회 경로별 비용** (B = 차수 64, N = 행 수, K = 범위 안 후보 수, M = 정렬 대상 행 수. 자료구조 경로의 비교이고 실제 시간에는 HTTP · 직렬화 · 디스크 · 캐시가 더해진다):

| SQL | 경로 | 비용 |
|---|---|---|
| `WHERE id = x` | `INDEX_POINT` | O(log_B N) + 한 줄 읽기 |
| `WHERE id` 범위 | `INDEX_RANGE` | O(log_B N + K) |
| `WHERE word = x` (비-id) | `FULL_SCAN` | 최악 O(N) |
| `COUNT(*)` + 비-id 조건 | `FULL_SCAN` | O(N). 일치 행을 모두 세야 한다 |
| `ORDER BY` 비-id + `LIMIT 10` | `FULL_SCAN` + 정렬 | O(N + M log M). 10개만 돌려줘도 후보 전체를 모은다 |
| `INSERT` R행 | 파일 끝 추가 + 트리 R회 삽입 | O(R log_B N) + 쓴 바이트 |

### 4-12. 확인 질문
- `WHERE id = 42`와 `WHERE word = '기차'`는 각각 파일을 몇 줄 읽는가?
- B+ 트리가 행 내용이 아니라 바이트 위치를 가지는 이유는 무엇인가?
- 워커 A가 행을 넣은 직후 워커 B가 그 id를 조회하면, B는 어느 단계에서 그 행을 알게 되는가?
- `ORDER BY word LIMIT 10`이 10줄만 읽고 끝나지 못하는 이유는 무엇인가?
- `INSERT`가 실행되는 동안 같은 테이블의 `SELECT`는 어떻게 되는가?
- 서버가 `INSERT` 도중에 꺼지면 재시작 때 무엇이 복구되고 무엇이 복구되지 않는가?

## 5. 게임 규칙 계층 — game

**한 줄 답**: 규칙은 `rules.js`가 계산하고, 판의 진행은 `service.js`가 Mini Redis의 키로 관리한다. 시간 초과는 서버가 키의 만료로 판정한다.

### 5-1. 단어 규칙 (`rules.js`)

- **형식**: 한글 음절 2자 이상. 정규식 `^[가-힣]{2,}$`.
- **두음법칙**: 한글 음절 코드는 `0xAC00 + (초성 × 21 + 중성) × 28 + 종성`이다. 이 식을 거꾸로 풀어 초성 · 중성 · 종성을 얻은 다음 이을 수 있는 첫 글자를 계산한다.
  - ㄹ → ㅇ: 중성이 ㅑ, ㅕ, ㅖ, ㅛ, ㅠ, ㅣ일 때 (예: '리' → '이')
  - ㄹ → ㄴ: 중성이 ㅏ, ㅐ, ㅗ, ㅚ, ㅜ, ㅡ일 때 (예: '래' → '내')
  - ㄴ → ㅇ: 중성이 ㅕ, ㅛ, ㅠ, ㅣ일 때 (예: '녀' → '여')

### 5-2. 등급과 점수

낸 단어의 끝 글자로 이을 수 있는 단어 수에 따라 등급이 정해진다. 이을 단어가 적을수록 점수가 높다.

| 등급 | 이을 수 있는 단어 수 | 점수 | 의미 |
|---|---|---:|---|
| 한방 (`kill`) | 0개 | 2,000 | 상대가 이을 단어가 없다 |
| 공격 (`attack`) | 1 ~ 10개 | 1,000 | 상대의 선택지가 매우 적다 |
| 까다로움 (`tricky`) | 11 ~ 100개 | 500 | 상대가 실수하기 쉽다 |
| 보통 (`normal`) | 101 ~ 1,000개 | 250 | 일반 단어 |
| 넉넉 (`easy`) | 1,001개 이상 | 100 | 안전하지만 점수가 낮다 |

**글자 수 추가 점수**: 위 표의 점수는 기본 점수이고, 낸 단어의 글자 수에 따라 점수가 더해진다. 받는 점수 = 등급 점수 + `letterPoints(글자 수)`.

| 글자 수 | 더해지는 점수 | 이유 |
|---|---:|---|
| 2 ~ 9 | 300 × (글자 수 ÷ 10)² (2글자 12, 3글자 27, 5글자 75, 9글자 243) | 짧은 단어는 아주 적게, 길수록 가파르게 |
| 10 | 300 | 기준점. 긴 단어는 드물어서 크게 준다 |
| 11 이상 | 300 + (글자 수 − 10) × 60 (11글자 360, 12글자 420) | 한 글자 늘 때마다 +60 |

예: 2글자 공격 단어는 1,000 + 12 = 1,012점, 10글자 공격 단어는 1,000 + 300 = 1,300점이다. 9글자(243)에서 10글자(300)로 넘어갈 때는 끊김 없이 이어진다. 제곱 비율이라 글자 수가 늘수록 한 글자당 늘어나는 점수가 커지고(8→9글자 +51, 9→10글자 +57), 11글자부터는 고정 +60이라 증가폭이 10글자 직전(+57)보다 크다. 시작 단어(`start`)는 0점이고, 컴퓨터가 낸 단어에도 같은 식이 적용된다(`rules.js`의 `letterPoints`, `service.js`의 `entry`, 2026-11-16 적용).

### 5-3. 컴퓨터 난이도

컴퓨터는 낼 수 있는 후보 중에 한방 단어가 있을 때, 난이도별 확률로 그것을 낸다.

| 난이도 | 한방 단어를 낼 확률 |
|---|---:|
| `easy` | 0% |
| `mild` | 25% |
| `normal` (기본) | 50% |
| `tough` | 75% |
| `hard` | 100% |

### 5-4. 판 진행 (html에 없는 것만)

- **목숨**: 플레이어와 컴퓨터가 각각 목숨을 가진다(기본 3개). 시간 초과이거나 이을 단어가 없으면 1개 줄어든다. 목숨이 줄어도 이번 판에 나온 단어 목록은 유지하고, 새 시작 단어를 뽑아 이어간다. 한쪽이 0이 되면 판이 끝난다.
- **시작 단어를 못 찾을 때**: 30번 안에 못 찾으면 플레이어가 아무 단어로 시작한다.

### 5-5. 처리 순서 중 html에 없는 경로

단어 제출(A) · 판 시작(B) · 단어 등록과 삭제(F)는 흐름 html ② ③ ④ 에 있어서 뺐다. 원본의 C · D · E 는 그대로 둔다.

#### C. 목숨을 잃는 경로 — `loseLife(state, who, reason)`

`lives[who]`를 1 줄이고 `history`에 기록한다. 0보다 크면 `openRound`로 새 시작 단어를 뽑아 이어 간다(나온 단어 목록은 그대로). 0 이하이면 `finish`로 간다. 이유는 `timeout`(시간 초과), `no-word`(플레이어가 이을 단어 없음), `computer-stuck`(컴퓨터가 이을 단어 없음) 세 가지다.

#### D. 판 종료 — `finish(state, result, reason)`

`games` 테이블에 `INSERT`(DBMS) → `game:<번호>:turn` 삭제 → `game:<번호>:used:` 접두사 키 일괄 삭제 → `ranking` 캐시 무효화 → `INCR stats:games` → `SET game:<번호>` (끝난 판 10분). 포기(`giveUp`)도 같은 `finish`를 쓴다.

#### E. 시간 초과가 판정되는 시점

서버에는 시간을 재는 반복 작업이 없다. `turn` 키가 만료돼 사라졌는지는 **요청이 올 때** 확인한다. 단어 제출(`play`)과 상태 조회(`get`)가 이 확인을 한다. 그래서 브라우저가 상태를 조회하지 않고 단어도 보내지 않으면, 목숨은 다음 요청이 올 때까지 줄지 않는다. 정상 화면에서는 브라우저의 0.2초 타이머가 시간이 다 되면(`deadline + 150ms`를 넘으면) 스스로 `api.getGame`으로 상태를 조회하므로 시간 초과가 제때 반영된다(`web/app.js`, 2026-11-16 확인). 서버가 시간을 재는 것이 아니라 브라우저 타이머가 조회를 보내는 구조다.

### 5-6. 제작자 인증 (`auth.js`)

- 단어 등록과 삭제는 로그인이 필요하다.
- 비밀번호 원문은 저장하지 않는다. `crypto.scryptSync(비밀번호, salt, 32)`의 결과를 `admin.json`에 둔다.
- 비교는 `crypto.timingSafeEqual`로 한다. 비교에 걸리는 시간이 일치한 글자 수에 따라 달라지지 않게 하려는 것이다.
- 로그인에 성공하면 32바이트 난수 토큰을 만들어 `session:<토큰>`으로 30분 동안 저장한다.
- 같은 접속 주소에서 5번 틀리면 1분 동안 429를 응답한다.

### 5-7. 없으면 생기는 일

| 빠진 것 | 결과 |
|---|---|
| 서버 쪽 턴 판정 | 브라우저 타이머를 멈추면 시간 제한이 사라진다 |
| 판 잠금 | 버튼을 두 번 누르면 한 차례에 단어 두 개가 처리된다 |
| 두음법칙 계산 | '리'로 끝난 단어 뒤에 '이'로 시작하는 단어를 잇지 못한다 |
| 실패 횟수 제한 | 비밀번호를 횟수 제한 없이 시도할 수 있다 |

## 6. 화면 앱과 단어 사전 — web, words

### 6-1. 화면 앱 (`web/app.js`)

**한 줄 답**: 상태는 모두 루트 `App`에 있고, 나머지 컴포넌트는 props를 받아 그리기만 한다.

- `App`이 `tab`, `level`, `game`, `deadline`, `now`, `notice`, `trace`, `admin`을 포함한 상태를 `useState`로 선언한다.
- **0.2초 시계**: `useEffect`가 200ms 간격 타이머로 `now`를 갱신한다. 렌더마다 화면 전체를 다시 계산하지만, 비교 결과 달라진 것은 게이지 너비와 남은 시간 글자뿐이다. 시간이 다 되면(`deadline + 150ms`) 서버에 판 상태를 조회해 시간 초과를 반영한다(5-5 E).
- **`useMemo`**: 나온 단어 목록을 화면용 모양으로 바꾸는 계산은 `[history]`에 묶여 있다. 시계가 갈 때는 다시 계산하지 않는다.
- **추적 패널**: 서버 응답의 `trace` 배열을 그린다. 값이 어디서 왔는지(`cache`, `db`, `redis`), 어떤 계획을 탔는지(`INDEX_POINT`, `FULL_SCAN`, `INSERT`), 몇 ms 걸렸는지 보여 준다.

## 8. 상용 시스템과 다른 점 — 한눈에

계층별 상세는 2-8, 3-10, 4-11에 있다. 여기서는 가로로 견준다.

### 8-1. 항목별 차이

| 항목 | 이 프로젝트 | 상용 시스템 |
|---|---|---|
| VNode 비교 | 자식을 인덱스로 비교, key 없음 | React는 key로 같은 항목을 추적한다 |
| 훅 범위 | 루트 컴포넌트 하나 | React는 컴포넌트마다 상태를 가진다 |
| Redis 통신 | HTTP + JSON | Redis는 전용 프로토콜(RESP)을 쓴다 |
| 해시 크기 조절 | 한 번에 전부 다시 배치 | Redis는 여러 번에 나눠 옮긴다 |
| 인덱스 보관 | 메모리. 시작할 때 다시 만든다 | DBMS는 인덱스도 디스크에 둔다 |
| 트랜잭션 | 없음 | PostgreSQL은 WAL과 MVCC로 여러 문장을 묶는다 |
| SQL 범위 | `INSERT`, `SELECT` | `UPDATE`, `DELETE`, `JOIN`, 서브쿼리 |
| 삭제 | `removed = 1` 행을 덧붙임 | 행을 지우고 공간을 회수한다 |

### 8-2. 세 계층을 같은 질문으로 비교

| 질문 | Mini React | Mini Redis | Mini DBMS |
|---|---|---|---|
| 무엇을 줄이려 하나 | 바뀐 DOM 수(패치) | 평균 해시 조회 비용 | id 인덱스 경로 |
| 데이터는 어디에 | 브라우저 메모리 | 메모리 + AOF 파일 | JSONL 파일 + 메모리 인덱스 |
| 커지면 느려지는 곳 | VNode 수에 비례한 생성 · 비교 · 검증 | prefix 전체 순회, 크기 조절, 긴 동기 명령 | 비-id 전체 탐색, 정렬, 시작 때 인덱스 재구성 |
| 동시 요청 | `batch()` | 동기 명령이라 섞이지 않음 | 워커 풀 + 테이블 읽기-쓰기 잠금 |
| 복구 | 없음 (앱이 떠 있는 동안만) | AOF 재생 | 행 파일을 읽어 인덱스 재구성 |

### 10-2. 스스로 확인 — 정답

1. 훅을 `if` 안에서 부르면 어느 칸이 어긋나는가? → 호출 순서로 칸을 찾으므로, 건너뛴 뒤의 훅이 앞 칸의 값을 읽는다.
2. 서버가 5분 꺼졌다면 TTL 10분 키는 재시작 뒤 몇 분 남는가? → 약 5분. 만료를 절대 시각으로 기록하기 때문이다.
3. `WHERE word = '기차'`는 왜 항상 `FULL_SCAN`인가? → 인덱스가 `id` 하나뿐이라 `word`로 위치를 찾을 수 없다.
4. 워커 A가 넣은 행을 워커 B가 보는 시점은? → B가 쿼리를 실행하기 직전 `catchUp()`으로 파일 뒷부분을 읽을 때.
5. 11초 만에 보낸 단어를 서버는 무엇으로 시간 초과로 보는가? → `game:<번호>:turn` 키의 TTL이 `-2`(없는 키)인 것.
6. 이을 단어가 7개인 단어는 몇 점인가? → 1~10개 구간이므로 공격 1,000점(여기에 글자 수에 따른 점수가 따로 더해진다. 5-2 참고).

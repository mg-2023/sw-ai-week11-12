역할

설계 의도와 자료구조를 고른 이유

B+ 트리 인덱스와 테이블 파일

인덱스는 레코드를 담는 것이 아니라 id → 파일 위치(offset)를 담고, 찾은 위치의 한 줄만 읽는다.

역할
테이블 하나 = 파일 하나 + 그 파일을 가리키는 메모리 B+ 트리다. id 로 찾을 때 파일 전체를 읽지 않게 한다.
설계 의도와 자료구조를 고른 이유
  • 인덱스에 id → 그 줄의 시작 바이트 위치(offset)를 넣고, 찾을 때는 그 위치의 한 줄만 읽는다 (table.js:11-14)
  • 레코드를 JSON 배열 한 줄로 저장한다. 줄바꿈·따옴표가 든 문자열도 한 줄에 들어가서 '한 줄 = 레코드 하나'가 지켜진다 (table.js:8, dbms/README.md:92)
  • 리프를 next 로 이어서 범위 검색은 리프만 따라가게 한다 (bplus-tree.js:10)
  • order 64 를 고른 근거는 소스에 없다 → 미확인

스레드 풀과 읽기 · 쓰기 잠금

워커들이 B+ 트리 하나를 함께 쓰는 것이 아니라, 각자 인덱스를 갖고 테이블 파일과 잠금 상태(SharedArrayBuffer)만 함께 쓴다.

역할
Phase 3 API 서버의 병렬 처리. 메인 스레드는 HTTP 만 다루고, SQL 실행은 워커 스레드들이 나눠 맡는다.
설계 의도와 자료구조를 고른 이유

# 끝말잇기 핵심 로직 지도

word-chain 의 핵심 로직 13개를 한 흐름씩 묶었다. 단계를 누르면 원본 코드와 그 단계 뒤의 상태가 열린다.

- 기준 소스: 사용자 컴퓨터의 word-chain 폴더 (2026-11-17 에 읽음). 코드 발췌는 그 파일에서 줄 번호로 그대로 옮겼다.
- 실행 관측: 2026-11-17 에 같은 폴더의 복사본에서 npm run test:redis, test:dbms, test 를 실행했다 (Node.js v22.23.4).
- 기존 기록값: README.md 와 dbms/README.md 에 적힌 벤치 수치는 출처를 붙여 그대로 옮겼고, 이번에 다시 재지 않았다.

**색과 표시의 뜻**

- **입력**: 요청이나 데이터가 들어오는 단계
- **제한·상수**: TTL, 적재율, 잠금 시간처럼 정해 둔 값이 판단을 가르는 단계
- **실행·관측**: 코드가 실행되거나 상태를 읽는 단계
- **계산 결과**: 응답, 고른 번호, 바뀐 상태처럼 계산이 끝나 나온 값
- **분기**: 정상 흐름에서 갈라지는 경우 (예외, 오류, 다른 경우)

## 0. 단어 '기차' 하나를 낼 때의 전체 흐름

> 단어 하나를 내는 일은 서버 한 곳의 함수 호출이 아니라, 브라우저 → 게임 서버 → 미니 레디스·미니 DBMS 를 HTTP 로 오가는 왕복 여러 번이다.

| 순서 | 보내는 쪽 → 받는 쪽 | 종류 | 단계 | 무엇을 하나 | 위치 |
|---:|---|---|---|---|---|
| 1 | 브라우저 → 게임 서버 | 입력 | `e_submit` 단어 제출 | 입력창의 play(word) 가 api.playWord 를 부른다 (web/app.js:372). | `web/api.js:21` |
| 2 | 게임 서버 → 게임 서버 | 실행·관측 | `e_route` 주소를 보고 판 진행 함수로 | 게임 서버가 주소와 메서드를 보고 service.play 를 부른다. | `game/server.js:90` |
| 3 | 게임 서버 → 미니 레디스 | 제한·상수 | `e_lock` 판 잠금 SET nx · 5초 | 같은 판을 한 번에 한 요청만 다루게 잠금 키를 nx 로 만든다. | `redis/src/api.js:89-91` |

| 5 | 게임 서버 → 미니 레디스 | 실행·관측 | `e_cache` 사전 캐시 GET word:기차 | 형식, 시작 글자, 중복을 통과한 단어만 사전을 찾는다. 먼저 캐시를 본다. | `redis/src/cache.js:29` |
| 6 | 게임 서버 → 미니 DBMS | 실행·관측 | `e_db` 캐시에 없으면 DBMS 에 SQL | SELECT id, finisher, removed FROM words WHERE word = '기차' 를 보낸다. | `game/db.js:42-44` |
| 7 | 미니 DBMS → 미니 DBMS | 실행·관측 | `e_scan` 워커가 파일 전체를 읽음 | word 열에는 인덱스가 없어 plan 이 FULL_SCAN 이 된다. | `dbms/src/engine.js:190-191` |
| 8 | 게임 서버 → 미니 레디스 | 제한·상수 | `e_fill` 결과를 60초 캐시 | 가져온 사전 확인 결과를 word:기차 키에 60초 ttl 로 넣는다. | `redis/src/cache.js:36` |
| 9 | 게임 서버 → 미니 레디스 | 제한·상수 | `e_save` 판 상태 30분 · turn 10초 저장 | 상대 단어까지 고른 뒤 새 판 상태와 새 차례 키를 쓰고, finally 에서 잠금을 지운다. | `game/service.js:313-314` |
| 10 | 게임 서버 → 브라우저 | 계산 결과 | `e_resp` JSON 응답 | { accepted, reject, computer, game, trace } 를 돌려준다. trace 에는 단계마다 값을 어디서 가져왔는지가 담긴다. | `game/server.js:144-146` |
| 11 | 브라우저 → 브라우저 | 계산 결과 | `e_render` 화면 한 번에 갱신 | show(res) 가 batch 로 setState 여러 개를 묶어 리렌더를 한 번만 한다. | `web/app.js:381-382` |

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 처음 보는 단어 (캐시 MISS) | e_submit → e_route → e_lock → e_state → e_cache → e_db → e_scan → e_fill → e_save → e_resp → e_render | DBMS 선형 탐색 1번을 거쳐 응답. 같은 단어의 다음 확인은 캐시에서 끝난다. |
| 다시 나온 단어 (캐시 HIT) | e_submit → e_route → e_lock → e_state → e_cache → e_save → e_resp → e_render | DBMS 를 부르지 않는다. trace 의 출처가 'cache' 로 찍힌다. |

잠금 실패(409), 없는 판(404), 시간 초과, 거절 같은 갈림길은 카드 G1 에서 같은 그림 안의 분기로 다룬다.

**결과** 응답 하나에 판 상태, 남은 시간, 상대 단어, trace 가 함께 실려 와서 화면이 한 번에 바뀐다.

**코드에서 확인한 사실**

- 게임 서버는 미니 레디스와 미니 DBMS 를 엔진 함수로 부르지 않고 HTTP 로 부른다 (server.js:9)
- 레디스 클라이언트는 연결을 최대 32개까지 재사용한다 (redis/src/client.js:18, 23)

**코드에서 도출한 예상**

- 단어 하나를 낼 때 레디스로 가는 HTTP 요청은 한 번이 아니라 여러 번이다: 잠금, 상태, 시간, 나온 단어, 캐시, 저장, 잠금 해제

**실행 관측과 기존 기록값**

- 2026-11-17 이번 실행: 게임 테스트 85개 통과, 실패 0, 건너뜀 0. 판 진행 테스트는 레디스·DBMS 서버를 실제로 띄워 실행한다 (README.md:326)

**미실행 · 미확인**

- 브라우저에서 단어 하나의 왕복 시간: 측정하지 않음

## R. 미니 레디스 (`redis/src/`)

메모리에 잠깐 두는 키-값 저장소. 진행 중인 판, 10초 제한 시간, 사전 캐시, 잠금이 여기에 있다. 포트 6380 의 HTTP API 로만 쓴다.

### R1. 해시 테이블: 저장 · 찾기 · 늘리기

`redis/src/hash-table.js`

> 키를 찾을 때 전체를 훑는 것이 아니라, 해시값으로 버킷 하나를 골라 그 버킷의 연결 리스트만 따라간다.

**역할** 미니 레디스의 모든 키가 들어가는 저장 구조다. store.js 가 값용(data)과 만료 시각용(expires) 두 개를 만든다 (redis/src/store.js:49-50).

**설계 의도와 자료구조를 고른 이유**

- 충돌은 같은 버킷의 노드를 next 로 이어 해결한다 (hash-table.js:13)
- 적재율이 0.75 를 넘으면 2배로 늘려 연결 리스트를 짧게 두고, 그래서 평균 O(1) 이 유지된다 (hash-table.js:14-15)
- capacity 를 2의 거듭제곱으로 두는 이유: & 연산 결과가 나머지 연산과 같아진다 (hash-table.js:10)
- Map / Object 를 저장소로 쓰지 않는다는 사실은 소스에 있지만 (hash-table.js:18), 그렇게 정한 이유는 소스에서 찾지 못했다 → 미확인
- 분리 연결법을 열린 주소법 대신 고른 이유는 소스에 적혀 있지 않다 → 미확인

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 해시 함수(Hash Function) | hashString, FNV-1a (hash-table.js:26-33) |
| 분리 연결법(Separate Chaining) | 버킷 배열과 node.next (hash-table.js:41, 63) |
| 적재율(Load Factor)과 재해싱(Rehashing) | set 의 크기 비교 (hash-table.js:65), resize (101-114) |
| 비트 마스크로 구하는 나머지 | bucketIndex (hash-table.js:46-48) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `r1_in` **키와 값이 들어온다**: store.set 이 data.set(key, value) 를 부른다. 같은 키가 이미 있는지부터 찾는다. (`redis/src/hash-table.js:59-61`)
    - 분기 [계산 결과] `r1_b_same` **같은 키가 이미 있음**: 값만 바꾸고 false 를 돌려준다. 노드 수와 버킷 배치는 그대로다. → size 그대로, 값만 교체 (`redis/src/hash-table.js:61`)
2. [실행·관측] `r1_hash` **FNV-1a 로 해시값 계산**: 글자(UTF-16 코드 단위)마다 XOR 로 섞고 소수 16777619 를 곱해 32비트 정수를 만든다. (`redis/src/hash-table.js:26-33`)
3. [계산 결과] `r1_idx` **버킷 번호 = 해시값 & (capacity − 1)**: capacity 가 16 이면 아래 4비트만 남긴다. (`redis/src/hash-table.js:46-48`)
4. [실행·관측] `r1_insert` **버킷 맨 앞에 노드를 끼운다**: 새 노드의 next 가 기존 머리를 가리키고, 버킷은 새 노드를 가리킨다. (`redis/src/hash-table.js:62-64`)
    - 분기 [계산 결과] `r1_b_collide` **다른 키와 같은 버킷 (충돌)**: 원본 함수로 계산하면 'game:7:turn' 과 'word:기차' 는 capacity 16 에서 둘 다 5번 버킷이다. → 5번 버킷: word:기차 → game:7:turn → null (`redis/src/hash-table.js:63`)
5. [제한·상수] `r1_load` **적재율 0.75 검사**: 노드 수가 capacity × 0.75(GROW_AT, hash-table.js:22)를 넘는지 본다. (`redis/src/hash-table.js:65-66`)
    - 분기 [실행·관측] `r1_b_grow` **적재율 초과 → resize(capacity × 2)**: 모든 노드의 버킷 번호를 새 capacity 로 다시 계산해 옮긴다. → 13번째 키에서 16 × 0.75 = 12 를 넘어 32칸으로 늘어난다 (`redis/src/hash-table.js:101-114`)
6. [계산 결과] `r1_get` **조회는 버킷 한 칸만 따라간다**: get 은 findNode 로 그 키의 버킷 리스트만 본다. (`redis/src/hash-table.js:51-56`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 새 키 넣기 (game:7) | r1_in → r1_hash → r1_idx → r1_insert → r1_load → r1_get | 0번 버킷에 노드 1개. 조회는 버킷 한 칸만 본다. |
| 같은 키 다시 넣기 | r1_in → r1_b_same | 값만 바뀌고 size 는 그대로. |
| 충돌 (game:7:turn 다음 word:기차) | r1_in → r1_hash → r1_idx → r1_insert → r1_b_collide → r1_load | 5번 버킷에 노드 2개가 연결 리스트로 이어진다. |
| 13번째 키 (늘리기) | r1_in → r1_hash → r1_idx → r1_insert → r1_load → r1_b_grow | capacity 16 → 32, 모든 노드가 새 번호로 옮겨진다. |

**결과** 키 하나가 버킷 하나의 연결 리스트 노드가 된다. 조회 · 저장 · 삭제는 해시값으로 고른 버킷 한 칸만 본다.

**코드에서 확인한 사실**

- 해시 함수는 charCodeAt 으로 UTF-16 코드 단위를 섞는다 (hash-table.js:29)
- 새 노드는 버킷 맨 앞에 들어간다 (hash-table.js:63)
- 지워서 적재율이 0.125 아래로 내려가면 capacity 를 절반으로 줄인다. 최소 16 (hash-table.js:23, 88)

**코드에서 도출한 예상**

- resize 는 동기 함수라 실행하는 동안 같은 프로세스의 다른 저장소 명령이 기다린다. 키 수에 비례하는 작업이다
- README 그림의 [1]번 칸 충돌은 예시 번호다. 원본 함수로 계산하면 같은 두 키가 capacity 16 에서 5번 칸에 함께 들어간다

### R2. 만료: 지연 삭제와 주기 삭제

`redis/src/store.js`

> 만료된 값을 지우는 시점은 하나가 아니라 둘이다. 키를 꺼낼 때(지연 삭제)와 0.1초마다 표본을 훑을 때(주기 삭제).

**역할** 보관 기간이 지난 값을 처리한다. 게임의 10초 제한 시간(turn 키), 사전 캐시 60초, 판 잠금 5초가 모두 이 만료로 움직인다.

**설계 의도와 자료구조를 고른 이유**

- 만료 시각을 '몇 초 뒤'가 아니라 절대 시각(ms)으로 저장한다 (store.js:6). 꺼져 있던 시간만큼 보관 기간이 늘어나지 않게 하려는 것이다 (aof.js:9)
- 두 방식을 함께 쓰는 이유: 지연 삭제만 있으면 아무도 찾지 않는 키가 메모리에 남고, 주기 삭제만 있으면 청소 전까지 만료된 값이 보인다 (README.md:159)
- 표본 중 1/4 넘게 만료돼 있으면 한 번 더 훑는다: 만료 키가 많이 쌓였다는 뜻이기 때문이다 (store.js:184)
- 표본 20개, 최대 10라운드, 주기 0.1초를 고른 근거는 소스에 없다 → 미확인

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 지연 삭제(Lazy Expiration) | removeIfExpired, alive (store.js:63-74) |
| 주기 삭제(Active Expiration) | sweepExpired, startSweeper (store.js:187-198, 240-244) |
| 커서로 나눠 훑기(Incremental Scan) | HashTable.scan (hash-table.js:134-142) |
| 타이머와 이벤트 루프(Event Loop) | setInterval 과 unref (store.js:241-242) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `r2_set` **ttl 과 함께 저장**: set(key, value, { ttl }) 이 만료 시각을 계산해 expires 테이블에 넣는다. (`redis/src/store.js:87-89`)
2. [실행·관측] `r2_access` **키에 접근하면 만료부터 확인**: get, ttl, incr, set, del 이 모두 alive 를 먼저 부른다. (`redis/src/store.js:72-74`)
3. [제한·상수] `r2_check` **만료 시각과 지금 시각 비교**: 만료 시각이 지금보다 크면 살아 있다. (`redis/src/store.js:63-69`)
    - 분기 [계산 결과] `r2_b_expired` **만료 시각이 지남 → 없음**: 그 자리에서 지우고 '없음'으로 답한다. → get → null, ttl → -2, 메모리에서도 빠짐 (`redis/src/store.js:97`)
    - 분기 [계산 결과] `r2_b_game` **게임: turn 키 -2 → 시간 초과**: 단어를 낼 때 turn 키가 이미 만료돼 있으면 낸 단어를 받지 않고 목숨을 뺀다. → loseLife('player', 'timeout') 로 이어진다 (카드 G1) (`game/service.js:276`)
4. [계산 결과] `r2_alive` **살아 있으면 남은 시간**: ttl 명령은 만료 시각 − 지금을 돌려준다. (`redis/src/store.js:140-145`)
    - 분기 [계산 결과] `r2_b_none` **만료가 없는 키 → -1**: expires 에 없는 키는 영구 보관이다. → game:seq 처럼 만료를 걸지 않은 키 (`redis/src/store.js:144`)

*타이머로 시작하는 두 번째 흐름*

5. [실행·관측] `r2_timer` **0.1초마다 주기 삭제**: 서버를 켤 때 startSweeper 가 타이머를 건다 (server.js:45). (`redis/src/store.js:240-244`)
6. [실행·관측] `r2_scan` **expires 를 20개씩 훑기**: 커서 위치부터 표본을 읽어 지연 삭제와 같은 함수로 지운다. (`redis/src/store.js:187-194`)
7. [제한·상수] `r2_ratio` **1/4 기준으로 멈출지 결정**: 지운 비율이 1/4 이하면 이번 주기는 끝낸다. (`redis/src/store.js:195-197`)
    - 분기 [실행·관측] `r2_b_more` **1/4 넘게 만료 → 다음 20개 더**: 같은 주기 안에서 최대 10라운드까지 이어 훑는다. → 만료 키가 쌓였을 때 한 주기에 더 많이 치운다 (`redis/src/store.js:195`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 만료 전에 조회 | r2_set → r2_access → r2_check → r2_alive | 값과 남은 시간을 돌려준다. |
| 만료 뒤에 조회 (지연 삭제) | r2_set → r2_access → r2_check → r2_b_expired | 그 자리에서 지우고 null / -2. |
| 게임의 10초 제한 | r2_set → r2_access → r2_check → r2_b_expired → r2_b_game | turn 키가 -2 → 시간 초과로 목숨 -1. |
| 아무도 안 찾는 키 (주기 삭제) | r2_set → r2_timer → r2_scan → r2_ratio | 0.1초마다 표본을 훑어 메모리에서 뺀다. |
| 만료를 걸지 않은 키 | r2_access → r2_check → r2_alive → r2_b_none | ttl → -1, 영구 보관. |
| 만료 키가 많이 쌓임 | r2_timer → r2_scan → r2_ratio → r2_b_more | 한 주기에 최대 10라운드까지 이어 지운다. |

**결과** 만료된 키는 어떤 명령으로 접근해도 '없음'(null, -2)이 되고, 아무도 찾지 않는 키도 0.1초 단위 청소로 메모리에서 빠진다.

**코드에서 확인한 사실**

- ttl 없이 set 하면 걸려 있던 만료가 사라진다 (store.js:79, 89)
- incr 는 만료 시각을 바꾸지 않는다 (store.js:154)
- 게임은 단어를 낼 때 turn 키의 ttl 이 -2 인지로 시간 초과를 판정한다 (game/service.js:276)

**코드에서 도출한 예상**

### R3. 끼어들 수 없는 명령: incr · set nx

`redis/src/store.js, redis/src/api.js`

> 동시성을 잠금 장치로 막는 것이 아니라, 명령 하나를 중간에 await 가 없는 동기 함수 한 번으로 실행해서 막는다.

**역할** 판 번호 발급(INCR game:seq), 판 잠금(SET … nx), 로그인 실패 횟수처럼 여러 요청이 같은 키를 동시에 바꾸는 일을 처리한다.

**설계 의도와 자료구조를 고른 이유**

- 모든 저장소 명령은 중간에 await 가 없는 동기 함수다. Node.js 는 자바스크립트를 스레드 하나로 실행하므로 명령 하나가 끝나기 전에 다른 명령이 끼어들 수 없다 (store.js:15-17)
- '읽고 → 계산하고 → 쓰기'는 요청 두 번으로 나누지 않고 incr, set 의 nx 처럼 명령 하나로 제공한다 (store.js:18)
- API 서버는 본문을 다 읽은 뒤 명령을 동기 함수 호출 한 번으로 실행한다 (api.js:18-19)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 원자성(Atomicity) | 동기 함수 한 번이 끼어들 수 없는 단위 (store.js:148-157) |
| 경쟁 조건(Race Condition) | GET 뒤 SET 으로 나누면 생기는 틈을 incr 로 없앤다 |
| 이벤트 루프(Event Loop) | await 지점(api.js:112)에서만 다른 요청으로 넘어간다 |
| 상호 배제(Mutual Exclusion) | 게임 판 잠금 SET nx + TTL (game/service.js:175-179) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `r3_req` **클라이언트가 명령을 HTTP 로 보낸다**: set 은 PUT, incr 는 POST /keys/<키>/incr 한 번이다. (`redis/src/client.js:51-56`)
2. [실행·관측] `r3_body` **본문 읽기까지만 비동기**: 요청끼리 겹치는 구간은 본문을 받는 await 하나뿐이다. (`redis/src/api.js:108-113`)
3. [실행·관측] `r3_exec` **execute 가 명령 하나로 바꿔 실행**: 주소가 /keys/<키>/incr 이고 POST 면 store.incr 를 부른다. (`redis/src/api.js:97`)
    - 분기 [계산 결과] `r3_b_nx` **SET nx 인데 키가 이미 있음 → 409**: store.set 이 false 를 돌려주면 API 가 409 로 답한다 (api.js:91). → 값은 그대로, 응답 409 (`redis/src/store.js:85-86`)
4. [실행·관측] `r3_incr` **읽고 → 더하고 → 쓰기를 한 함수 안에서**: 중간에 await 가 없어 다른 요청이 끼어들 틈이 없다. (`redis/src/store.js:148-156`)
    - 분기 [계산 결과] `r3_b_err` **정수가 아닌 값 → 400**: 명령이 던진 CommandError 를 API 가 400 으로 바꾼다. → 값은 그대로, 응답 400 (`redis/src/api.js:114-118`)
5. [계산 결과] `r3_out` **응답 { value }**: 두 요청이 겹쳐도 하나는 7, 다른 하나는 8 을 받는다. (`redis/src/api.js:120-122`)
    - 분기 [실행·관측] `r3_b_lock` **게임의 판 잠금**: 게임 서버는 SET nx 를 판 잠금으로 쓴다. 성공한 요청만 진행한다. → 같은 판의 두 번째 요청은 r3_b_nx 경로로 409 (`game/service.js:175-179`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| INCR 두 요청이 겹침 | r3_req → r3_body → r3_exec → r3_incr → r3_out | 본문 읽기는 겹쳐도 incr 실행은 하나씩: 6→7, 7→8. |
| 같은 판에 동시 제출 (SET nx) | r3_b_lock → r3_req → r3_body → r3_exec → r3_b_nx | 먼저 잠금을 만든 요청만 진행, 나머지는 409. |
| 정수가 아닌 값 증가 | r3_req → r3_body → r3_exec → r3_incr → r3_b_err | 400, 저장된 값은 그대로. |

**결과** 같은 키를 동시에 바꾸는 요청이 몰려도 명령은 하나씩 차례로 실행되고, 숫자가 빠지거나 잠금이 두 번 잡히지 않는다.

**코드에서 확인한 사실**

- 판 잠금은 finally 에서 지워서, 오류로 끝나도 잠금이 남지 않는다 (game/service.js:178)
- 잠금을 지울 때 자기가 만든 잠금인지 확인하지 않는다 (game/service.js:178 의 del)

**코드에서 도출한 예상**

- 처리가 5초를 넘기면 잠금이 먼저 만료돼 같은 판 요청이 하나 더 들어올 수 있고, 첫 요청의 finally 가 두 번째 요청의 잠금을 지울 수 있다

### R4. 캐시 getOrLoad: 사전 확인

`redis/src/cache.js, game/service.js`

> 캐시는 원본을 대신하는 저장소가 아니라 원본 앞에 둔 보조 수단이다. 없으면 원본을 읽어 채우고, 캐시가 죽어도 원본으로 동작한다.

**역할** 단어 하나를 확인할 때마다 사전 파일 전체를 훑는 비용을, 같은 단어의 두 번째 확인부터 없앤다.

**설계 의도와 자료구조를 고른 이유**

- 앱(게임 서버)이 캐시를 먼저 보고, 없으면 원본에서 읽어 캐시에 넣는다 (cache.js:4-7)
- 같은 키를 여러 요청이 동시에 놓치면 원본 조회를 요청 수만큼 하지 않고 먼저 시작한 조회 하나를 함께 기다린다 (cache.js:9)
- 캐시는 없어도 동작해야 하는 보조 수단이라 캐시 오류는 삼키고 원본에서 가져온다 (cache.js:10)
- 단어 캐시 60초, 순위 캐시 5초로 정한 근거는 소스에 없다 → 미확인

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 캐시 어사이드(Cache-Aside) | getOrLoad (cache.js:28-42) |
| 요청 합치기(Request Coalescing) | loading Map (cache.js:16, 33-41) |
| 장애 시 기능 축소(Graceful Degradation) | safely (cache.js:20-22) |
| 캐시 무효화(Cache Invalidation) | invalidate (cache.js:45-47) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `r4_call` **사전 확인 요청 word:기차**: 판정 단계가 lookup(word) 를 부른다. (`game/service.js:90-91`)
2. [실행·관측] `r4_get` **캐시에서 먼저 찾기**: 레디스에 GET 한 번. 오류가 나도 예외가 아니라 null 로 받는다. (`redis/src/cache.js:28-30`)
    - 분기 [계산 결과] `r4_b_hit` **적중 → 원본을 읽지 않음**: 같은 단어를 60초 안에 다시 확인하면 여기서 끝난다. → DBMS 호출 0번, trace source 'cache' (`redis/src/cache.js:30`)
    - 분기 [계산 결과] `r4_b_down` **레디스 오류 → 원본으로**: 캐시 명령이 실패하면 fallback 값을 써서 놓침으로 처리한다. → 느려지지만 사전 확인은 계속된다 (`redis/src/cache.js:20-22`)
3. [실행·관측] `r4_miss` **놓침: 같은 키가 이미 원본을 읽는 중인지**: loading Map 에 같은 키의 작업이 없을 때만 새로 만든다. (`redis/src/cache.js:31-33`)
    - 분기 [실행·관측] `r4_b_join` **같은 키를 동시에 놓침 → 하나를 같이 기다림**: 두 번째 요청부터는 새 원본 조회를 만들지 않는다. → DBMS 호출 1번, 응답은 요청 수만큼 (`redis/src/cache.js:41`)
4. [실행·관측] `r4_load` **원본 조회 작업 하나**: 작업이 끝나면 결과를 캐시에 넣고 '진행 중' 표시를 지운다. (`redis/src/cache.js:34-39`)
5. [실행·관측] `r4_db` **DBMS 선형 탐색**: word 열에는 인덱스가 없어 FULL_SCAN 이 된다. (`game/service.js:83-87`)
6. [제한·상수] `r4_ttl` **캐시 보관 60초**: 게임 서비스가 캐시를 만들 때 ttl 을 정한다. (`game/service.js:59-60`)
    - 분기 [실행·관측] `r4_b_inval` **원본이 바뀌면 지운다 (무효화)**: 단어를 등록하거나 지우면 게임 서버가 invalidate 를 부른다 (카드 G2). → word:기차 삭제 → 다음 확인은 다시 MISS (`redis/src/cache.js:44-47`)
7. [계산 결과] `r4_out` **결과와 출처를 trace 에**: 적중이면 'cache', 원본이면 'db' 로 걸린 시간과 함께 남긴다. (`game/service.js:78-79`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 처음 확인 (MISS) | r4_call → r4_get → r4_miss → r4_load → r4_db → r4_ttl → r4_out | DBMS 선형 탐색 1번, 결과를 60초 캐시, trace 'db'. |
| 다시 확인 (HIT) | r4_call → r4_get → r4_b_hit | DBMS 를 읽지 않는다. trace 'cache'. |
| 같은 단어를 동시에 놓침 | r4_call → r4_get → r4_miss → r4_b_join | 원본은 1번만 읽고 나머지는 같은 결과를 받는다. |
| 레디스가 꺼져 있음 | r4_call → r4_get → r4_b_down → r4_miss → r4_load → r4_db → r4_out | 캐시 없이 원본으로 동작한다. |
| 단어 등록 직후 | r4_b_inval → r4_call → r4_get → r4_miss → r4_load → r4_db | 지운 뒤 첫 확인은 원본을 다시 읽는다. |

**결과** 같은 단어를 다시 확인하면 DBMS 를 읽지 않고 캐시에서 꺼낸다. 원본이 바뀌면 그 키를 지워 다음 조회가 원본을 다시 읽게 한다.

**코드에서 확인한 사실**

- '없는 단어' 결과 { known: false } 도 null 이 아니라서 캐시에 들어간다 (cache.js:36, game/service.js:87)
- loader 가 끝난 뒤에 set 하고, 무효화는 따로 del 한다 (cache.js:36, 46)

**코드에서 도출한 예상**

- 조회가 DBMS 를 읽는 도중에 무효화가 먼저 끝나면, 조회가 옛 결과를 캐시에 다시 쓸 수 있다. 그러면 60초 동안 낡은 값이 남는다 (README.md:195 와 같은 결론)

**실행 관측과 기존 기록값**

- 기존 기록값 (README.md:316-320, Windows 11 · Node.js 26): 단어 20만 개, 100개 × 3번 확인에서 평균 56.04 ms → 16.00 ms, DBMS 읽기 300 → 100번. 이번에 다시 재지 않았다
- 2026-11-17 이번 실행: '캐시: 처음에는 DBMS 를 선형 탐색하고, 다음부터는 레디스에서 꺼낸다' 통과 (game/__tests__/service.test.js:212)

### R5. AOF: 기록 → 복구 → 줄이기

`redis/src/aof.js, redis/src/store.js`

> 메모리 상태를 통째로 저장하는 것이 아니라, 상태를 바꾼 명령을 순서대로 적어 두고 다시 실행해서 되살린다.

**역할** 메모리에만 있는 레디스 데이터를 프로세스가 꺼져도 되살린다. 기록 파일은 data/redis.aof (server.js:6).

**설계 의도와 자료구조를 고른 이유**

- 데이터를 바꾼 명령을 한 줄씩 파일 끝에 이어 쓰고, 다시 켜면 처음부터 같은 명령을 순서대로 실행한다 (aof.js:4-7)
- 만료는 만료 시각으로 적는다. 꺼져 있던 시간만큼 보관 기간이 늘어나지 않게 하려는 것이다 (aof.js:9)
- 새 파일을 다 쓴 뒤에 이름을 바꾸므로 도중에 꺼져도 원래 파일이 남는다 (aof.js:16-18)
- 스냅샷 대신 AOF 를 고른 이유: 스냅샷은 마지막 저장 이후 변경을 모두 잃지만 AOF 는 보통 최근 약 1초 분량만 위험하다 (README.md:304)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 추가 전용 로그(Append-Only Log) | append (aof.js:48-51) |
| 재실행 복구(Replay) | store.apply (store.js:211-229) |
| fsync 와 내구성(Durability) | flush 와 everysec 타이머 (aof.js:41-44) |
| 이름 바꾸기로 하는 교체(Atomic Rename) | rewrite (aof.js:54-62) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `r5_open` **서버 시작: 기록 파일 열기**: npm start 가 레디스 저장소를 기록 파일에서 복구하며 연다. (`server.js:43-45`)
2. [실행·관측] `r5_read` **줄 단위로 읽기**: 한 줄이 명령 하나다. 해석이 안 되는 줄을 만나면 거기서 멈춘다. (`redis/src/aof.js:28-36`)
    - 분기 [계산 결과] `r5_b_broken` **해석 안 되는 줄 → 거기서 멈춤**: 쓰다가 꺼져 마지막 줄이 잘린 경우를 위한 처리다. → 복구는 깨진 줄 앞까지 (`redis/src/aof.js:33`)
3. [실행·관측] `r5_apply` **기록을 순서대로 다시 실행**: 복구하는 동안에는 aof 가 null 이라 같은 명령이 다시 기록되지 않는다. (`redis/src/aof.js:84-87`)
4. [제한·상수] `r5_expired` **이미 지난 만료는 건너뜀**: 만료 시각이 지금보다 이르면 넣지 않는다. (`redis/src/store.js:213-216`)
5. [실행·관측] `r5_compact` **살아 있는 키만 새 파일로 교체**: 기록이 있었으면 복구 직후 파일을 줄인다 (aof.js:91). (`redis/src/aof.js:54-62`)

*서버가 켜져 있는 동안*

6. [실행·관측] `r5_append` **쓰기 명령마다 한 줄**: set, del, expire, persist, flush 가 onWrite 로 기록을 넘긴다. (`redis/src/aof.js:48-51`)
    - 분기 [실행·관측] `r5_b_always` **fsync = always**: FSYNC=always 로 켜면 줄마다 디스크를 기다린다. → 손실 범위는 줄고 쓰기는 느려진다 (`redis/src/aof.js:50`)
7. [제한·상수] `r5_fsync` **1초마다 디스크 반영 (everysec)**: 기본 정책은 everysec 이다 (aof.js:39). (`redis/src/aof.js:41-44`)
    - 분기 [계산 결과] `r5_b_kill` **강제 종료 → 최대 1초 분량 손실**: flush 전에 프로세스가 죽으면 마지막 fsync 이후 기록이 디스크에 없을 수 있다. → 마지막 fsync 이후의 기록을 잃을 수 있다 (`redis/src/aof.js:13`)
8. [계산 결과] `r5_close` **정상 종료 때 마지막 반영**: Ctrl+C(SIGINT)나 SIGTERM 이면 close 가 남은 기록을 flush 한다. (`server.js:72-76`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 다시 켜기 (복구) | r5_open → r5_read → r5_apply → r5_expired → r5_compact | 꺼지기 직전 상태 + 그동안 지난 만료 반영, 파일은 살아 있는 키만. |
| 켜져 있는 동안 쓰기 | r5_append → r5_fsync → r5_close | 명령마다 한 줄, 1초마다 디스크, 종료 때 마지막 반영. |
| 강제 종료 뒤 다시 켜기 | r5_append → r5_fsync → r5_b_kill → r5_open → r5_read → r5_apply | 마지막 fsync 이후 기록은 잃을 수 있고 나머지는 복구. |
| fsync = always 로 켬 | r5_append → r5_b_always | 줄마다 디스크에 반영: 손실 범위는 줄고 쓰기는 느려진다. |
| 마지막 줄이 잘림 | r5_open → r5_read → r5_b_broken → r5_apply | 깨진 줄 앞까지 복구. |

**결과** 다시 켜면 기록 파일의 명령을 순서대로 다시 실행해 꺼지기 직전 상태가 되고, 파일은 살아 있는 키만 남도록 줄어든다.

**코드에서 확인한 사실**

- 서버가 켜져 있는 동안에는 파일을 줄이지 않는다. compact 는 복구 직후에만 부른다 (aof.js:91)
- 정상 종료(SIGINT, SIGTERM) 때 close 가 마지막 flush 를 한다 (aof.js:68-74, server.js:65-76)

**코드에서 도출한 예상**

- 중간 줄이 깨지면 그 뒤의 멀쩡한 기록도 복구하지 않는다 (aof.js:33 에서 바로 반환)
- 한 차례에 쓰는 여러 명령은 각자 한 줄이라, 강제 종료 시점에 따라 한 차례의 일부만 복구될 수 있다

**실행 관측과 기존 기록값**

- 2026-11-17 이번 실행: '강제 종료: … 정리 없이 죽어도(SIGKILL) 이미 쓴 기록으로 복구된다' 를 포함한 aof.test.js 8개 통과 (aof.test.js:47)

**미실행 · 미확인**

## G. 게임 서버 (`game/`)

끝말잇기 규칙을 실행하는 곳. 미니 레디스와 미니 DBMS 를 외부 클라이언트처럼 HTTP 로 부른다. 포트 3000.

<a id="card-g1"></a>

### G1. 단어 내기 play: 잠금 → 시간 → 판정 → 상대 → 새 차례

`game/service.js`

> 한 차례는 레디스 명령 하나가 아니라 여러 명령의 묶음이고, 그 묶음을 판마다 nx 잠금으로 한 번에 하나씩만 실행한다.

**역할** 게임 서버의 중심이다. 단어 하나를 낼 때 미니 레디스(판 상태, 시간, 잠금, 캐시)와 미니 DBMS(사전)를 함께 쓴다.

**설계 의도와 자료구조를 고른 이유**

- 한 판을 한 번에 한 요청만 다루게 한다. 잠금 키를 nx 로 만든 요청만 들어간다 (service.js:174)
- 차례 키가 만료돼 사라졌으면 시간 초과다. 목숨을 잃고, 지금 낸 단어는 받지 않는다 (service.js:275)
- 사전은 다른 조건을 통과한 단어만 찾아본다 (service.js:284)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 임계 구역(Critical Section) | withLock 안의 run (service.js:175-179) |
| 상태 기계(State Machine) | status playing → over, 목숨 감소 (service.js:182-200, 245-251) |
| TTL 로 만든 타임아웃(Timeout) | turn 키 (service.js:237, 276, 314) |
| try/finally 로 하는 자원 해제 | 잠금 삭제 (service.js:178) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `g1_req` **POST /api/games/:id/words { word }**: 게임 서버 라우터가 service.play 를 부른다 (game/server.js:90). (`game/service.js:267-268`)
2. [제한·상수] `g1_lock` **판 잠금: SET game:7:lock nx · 5초**: LOCK_TTL = 5,000ms (service.js:46). (`game/service.js:176-177`)
    - 분기 [계산 결과] `g1_b_busy` **잠금 실패 → 409**: 같은 판의 앞선 요청이 처리 중이다. run 은 실행하지 않는다. → 아무것도 읽거나 바꾸지 않는다 (`game/service.js:177`)
3. [실행·관측] `g1_load` **판 상태 읽기: GET game:7**: 판이 없거나 끝났으면 여기서 오류로 끝난다. (`game/service.js:271-272`)
    - 분기 [계산 결과] `g1_b_gone` **판 없음 404 · 끝난 판 409**: 판 상태는 30분 보관이라 오래된 판은 없는 판이 된다. → 오류 응답, finally 에서 잠금 해제 (`game/service.js:162-166`)
4. [제한·상수] `g1_time` **시간 확인: turn 키의 ttl**: -2 면 만료로 사라진 것이다 (카드 R2). (`game/service.js:275-276`)

### G2. 단어 등록 · 삭제와 캐시 무효화

`game/service.js, game/server.js`

> 단어 삭제는 줄을 지우는 것이 아니라 removed = 1 인 줄을 하나 더 쓰는 것이고, 등록이든 삭제든 원본을 바꾼 뒤 캐시 키를 지운다.

**역할** 사전(원본)을 바꾸는 경로다. 제작자 로그인이 있어야 하고, 원본을 바꾼 뒤 관련 캐시를 지워 다음 조회가 새 원본을 읽게 한다.

**설계 의도와 자료구조를 고른 이유**

- 등록을 한 줄로 세운다. '있는지 확인 → INSERT' 사이에 다른 등록이 끼어들지 않게 하려는 것이다 (service.js:61)
- 미니 DBMS 에는 DELETE 가 없어서 같은 단어를 removed = 1 로 한 줄 더 넣는다 (service.js:16-17)
- 원본이 바뀌었으니 옛 캐시를 지운다 (service.js:128)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 직렬화 대기열(Serialization Queue) | Promise 체인 registering (service.js:61, 117, 137) |
| 삭제 표시 줄(Tombstone) | removed = 1 인 줄 INSERT (service.js:148-149) |
| 쓰기 뒤 무효화(Invalidate on Write) | service.js:127-128 |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `g2_req` **POST · DELETE /api/words (제작자 로그인)**: 토큰이 없거나 만료됐으면 401 로 끝난다. (`game/server.js:95-102`)
2. [실행·관측] `g2_queue` **등록 요청을 한 줄로 세움**: 앞선 등록·삭제 작업이 끝난 뒤에 이어서 실행한다. (`game/service.js:116-117`)

## D. 미니 DBMS (`dbms/src/`)

단어 사전과 끝난 판 기록의 원본을 파일에 오래 보관한다. SQL 처리기, B+ 트리 인덱스, 스레드 풀 API 서버의 세 단계로 만들었다. 포트 4000.

<a id="card-d1"></a>

### D1. SQL 실행: 파싱 → 읽는 방법 고르기 → 실행

`dbms/src/engine.js, dbms/src/api.js`

> SELECT 가 늘 파일 전체를 읽는 것이 아니라, WHERE 조건을 보고 읽는 방법(plan)을 먼저 고른다.

**역할** Phase 1 SQL 처리기와 Phase 2 인덱스를 묶은 엔진이다. 워커 스레드마다 하나씩 있다 (db-worker.js:4).

**설계 의도와 자료구조를 고른 이유**

- 처리 흐름: SQL 텍스트 → 문장 나누기 → 파싱 → 실행 → 파일 저장 / 읽기 (engine.js:4)
- id = 은 INDEX_POINT, id 범위는 INDEX_RANGE, 그 밖의 조건은 FULL_SCAN 으로 읽는다 (engine.js:7-10)
- 검사를 모두 통과한 뒤에만 파일에 쓴다 (engine.js:153)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 구문 분석(Parsing)과 AST | parse (parser.js:27), AST 모양 (parser.js:11-14) |
| 실행 계획(Query Plan) | choosePlan (engine.js:76-90) |
| 선형 탐색(Linear Scan) | table.scan (table.js:137-149) |
| 공유 잠금(Shared Lock) | SELECT 는 읽기 잠금 (engine.js:183) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `d1_req` **POST /query { sql }**: 메인 스레드는 SQL 을 꺼내 스레드 풀에 넘기기만 한다. (`dbms/src/api.js:84-87`)
2. [실행·관측] `d1_split` **문장 나누기 → 파싱 → 실행**: 세미콜론으로 나눈 문장마다 AST 를 만들어 run 한다. (`dbms/src/engine.js:236-240`)
3. [실행·관측] `d1_check` **테이블 · 컬럼 · 타입 확인**: 파서는 문법만 보고, 실제 테이블과 타입은 엔진이 확인한다 (parser.js:16). (`dbms/src/engine.js:159-167`)
    - 분기 [실행·관측] `d1_b_insert` **INSERT: 검사 뒤 쓰기 잠금**: 타입 검사를 모두 통과해야 파일에 쓴다. → { type: 'insert', rowCount: 1, firstId: <새 id> } (`dbms/src/engine.js:153-154`)
    - 분기 [계산 결과] `d1_b_err` **SQL 오류 → 400, 그 문장에서 멈춤**: 앞 문장은 이미 실행된 상태로 남는다. → 워커가 kind 'sql' 로 알리고 API 가 400 으로 답한다 (`dbms/src/engine.js:241-243`)
4. [계산 결과] `d1_plan` **읽는 방법 고르기**: id 컬럼(0번)에 = 조건이 있으면 INDEX_POINT. (`dbms/src/engine.js:76-79`)
    - 분기 [계산 결과] `d1_b_scan` **id 범위 → INDEX_RANGE, 그 밖 → FULL_SCAN**: word = '기차' 처럼 id 가 아닌 조건은 파일 전체를 읽는다. → WHERE word = '기차' → FULL_SCAN (`dbms/src/engine.js:88-89`)
5. [실행·관측] `d1_read` **읽기 잠금 → 따라잡기 → 읽기**: plan 에 따라 트리로 한 줄, 트리 범위, 파일 전체 중 하나를 읽는다. (`dbms/src/engine.js:183-193`)
6. [계산 결과] `d1_out` **결과: plan, columns, rows**: plan 값이 게임 화면의 'DBMS 인덱스 / 전체 탐색' 표시가 된다. (`dbms/src/engine.js:211-215`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| WHERE id = 163947 (시작 단어 뽑기) | d1_req → d1_split → d1_check → d1_plan → d1_read → d1_out | plan INDEX_POINT, 한 줄만 읽는다. |
| WHERE word = '기차' (사전 확인) | d1_req → d1_split → d1_check → d1_plan → d1_b_scan → d1_read → d1_out | plan FULL_SCAN, 파일 전체를 읽는다. |
| INSERT INTO words … | d1_req → d1_split → d1_check → d1_b_insert | id 자동 부여, 파일 끝에 한 줄. |
| 없는 컬럼 | d1_req → d1_split → d1_check → d1_b_err | 400. 앞 문장까지만 실행된 상태. |

**결과** SELECT 는 plan 과 함께 컬럼 · 레코드를 돌려주고, INSERT 는 붙인 id 를 돌려준다.

### D2. B+ 트리 인덱스와 테이블 파일

`dbms/src/bplus-tree.js, dbms/src/table.js`

> 인덱스는 레코드를 담는 것이 아니라 id → 파일 위치(offset)를 담고, 찾은 위치의 한 줄만 읽는다.

**역할** 테이블 하나 = 파일 하나 + 그 파일을 가리키는 메모리 B+ 트리다. id 로 찾을 때 파일 전체를 읽지 않게 한다.

**설계 의도와 자료구조를 고른 이유**

- 인덱스에 id → 그 줄의 시작 바이트 위치(offset)를 넣고, 찾을 때는 그 위치의 한 줄만 읽는다 (table.js:11-14)
- 레코드를 JSON 배열 한 줄로 저장한다. 줄바꿈·따옴표가 든 문자열도 한 줄에 들어가서 '한 줄 = 레코드 하나'가 지켜진다 (table.js:8, dbms/README.md:92)
- 리프를 next 로 이어서 범위 검색은 리프만 따라가게 한다 (bplus-tree.js:10)
- order 64 를 고른 근거는 소스에 없다 → 미확인

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| B+ 트리(B+ Tree) | insertInto, splitLeaf, splitInternal (bplus-tree.js:80-112) |
| 이진 탐색(Binary Search) | lowerBound, childIndex (bplus-tree.js:22-40) |
| 레코드 위치 인덱스(Offset Index) | appendRows, findById (table.js:93-127) |
| 추가 전용 파일(Append-Only File) | 'a+' 로 열고 끝에만 쓴다 (table.js:53) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `d2_append` **INSERT: id 붙이기**: 새 id 는 지금 가장 큰 id + 1 이다. (`dbms/src/table.js:93-101`)
    - 분기 [실행·관측] `d2_b_rebuild` **테이블을 열 때 파일에서 인덱스 재구성**: JSON 전체를 해석하지 않고 줄 앞의 id 숫자만 바이트에서 읽는다. → 인덱스는 파일에 저장하지 않고 열 때마다 만든다 (`dbms/src/table.js:73-77`)
2. [실행·관측] `d2_write` **파일 끝에 한 번에 쓰고 위치 등록**: 문장 하나의 줄들은 write 한 번으로 쓴다. (`dbms/src/table.js:102-108`)
3. [실행·관측] `d2_insert` **리프에 정렬을 지키며 끼우기**: 이진 탐색으로 자리를 찾아 splice 로 끼운다. (`dbms/src/bplus-tree.js:81-87`)
4. [제한·상수] `d2_split` **넘치면 반으로 쪼개기 (order 64)**: 오른쪽 리프의 첫 키를 부모로 복사해 올린다. (`dbms/src/bplus-tree.js:98-103`)
    - 분기 [실행·관측] `d2_b_internal` **내부 노드도 넘치면 가운데 키를 올림**: 내부 노드의 가운데 키는 복사가 아니라 이동이다. → 쪼개짐이 루트까지 올라가면 높이 +1 (`dbms/src/bplus-tree.js:106-112`)
5. [계산 결과] `d2_root` **루트가 쪼개지면 높이 +1**: 모든 리프의 깊이가 같이 늘어난다. (`dbms/src/bplus-tree.js:72-76`)

*조회*

6. [실행·관측] `d2_search` **SELECT … WHERE id = ? : 루트에서 리프까지**: 층마다 이진 탐색으로 자식을 골라 내려간다. (`dbms/src/bplus-tree.js:53-57`)
    - 분기 [실행·관측] `d2_b_range` **범위 검색: 리프의 next 를 따라감**: 시작 리프 하나만 트리로 찾고 나머지는 옆으로 이동한다. → WHERE id >= 10 AND id < 20 → 10~19 (`dbms/src/bplus-tree.js:118-124`)
7. [계산 결과] `d2_read` **offset 위치의 한 줄만 읽기**: 파일 전체가 아니라 그 위치에서 줄바꿈까지만 읽는다. (`dbms/src/table.js:124-127`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| INSERT 한 건 | d2_append → d2_write → d2_insert | 파일에 한 줄, 리프에 id 하나. |
| 리프가 가득 참 (64번째 키) | d2_append → d2_write → d2_insert → d2_split → d2_root | 리프가 둘로, 처음이면 새 루트 (높이 2). |
| 내부 노드도 가득 참 | d2_append → d2_write → d2_insert → d2_split → d2_b_internal → d2_root | 쪼개짐이 위로 올라가 루트까지 오면 높이 +1. |
| SELECT … WHERE id = 163947 | d2_search → d2_read | 트리 높이만큼 내려가 한 줄만 읽는다. |
| WHERE id >= 10 AND id < 20 | d2_search → d2_b_range | 리프를 옆으로 따라가며 10~19. |
| 서버 시작 | d2_b_rebuild | 파일을 한 번 훑어 인덱스를 다시 만든다. |

**결과** id 로 찾으면 트리 높이만큼 노드를 내려가 offset 을 얻고, 파일에서 그 한 줄만 읽는다.

**코드에서 확인한 사실**

- 인덱스는 파일에 저장하지 않고 테이블을 열 때 파일을 한 번 훑어 다시 만든다 (table.js:14, 62-87)
- 삭제는 구현하지 않았다 (bplus-tree.js:19)

**코드에서 도출한 예상**

- id 가 '가장 큰 id + 1' 이라, 잠금 없이 두 워커가 동시에 계산하면 같은 id 가 나온다. 그래서 쓰기 잠금 안에서 계산한다 (카드 D3)

**실행 관측과 기존 기록값**

- 기존 기록값 (dbms/README.md:135, 141): 100만 건에서 B+ 트리 높이 4, 인덱스 재구성 149 ms. 이번에 다시 재지 않았다
- 2026-11-17 이번 실행: bplus-tree.test.js 11개를 포함한 DBMS 테스트 86개 통과

**미실행 · 미확인**

- order 를 바꿨을 때의 성능 비교: 측정하지 않음

### D3. 스레드 풀과 읽기 · 쓰기 잠금

`dbms/src/thread-pool.js, dbms/src/rw-lock.js, dbms/src/db-worker.js`

> 워커들이 B+ 트리 하나를 함께 쓰는 것이 아니라, 각자 인덱스를 갖고 테이블 파일과 잠금 상태(SharedArrayBuffer)만 함께 쓴다.

**역할** Phase 3 API 서버의 병렬 처리. 메인 스레드는 HTTP 만 다루고, SQL 실행은 워커 스레드들이 나눠 맡는다.

**설계 의도와 자료구조를 고른 이유**

- 스레드를 요청마다 만들면 만드는 비용이 크고, 요청이 몰리면 스레드가 끝없이 늘어난다. 그래서 size 개를 미리 만들어 재사용한다 (thread-pool.js:4-5)
- 워커 스레드는 변수를 공유하지 않으므로 잠금 상태를 SharedArrayBuffer 에 둔다 (rw-lock.js:9)
- '읽고 → 비교하고 → 바꾸기' 사이에 다른 스레드가 끼어들면 두 스레드가 동시에 잠금을 잡으므로 Atomics.compareExchange 로 한 동작으로 만든다 (rw-lock.js:14-16)
- 기다리는 쓰기가 있으면 새 읽기가 양보한다. 읽기가 끊이지 않아 쓰기가 영영 못 들어가는 일을 막는다 (rw-lock.js:7)
- 워커 수 기본값 min(4, 코어 수) 를 고른 근거는 소스에 없다 → 미확인 (api.js:64)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 스레드 풀(Thread Pool) | createThreadPool (thread-pool.js:26-114) |
| 읽기·쓰기 잠금(Read-Write Lock) | createRwLock (rw-lock.js:32-81) |
| 비교 후 교환(Compare-And-Swap) | Atomics.compareExchange (rw-lock.js:40, 45) |
| 기아 방지(Starvation Prevention) | WAITING 카운터 (rw-lock.js:39, 68-71) |
| 공유 메모리(Shared Memory) | SharedArrayBuffer (rw-lock.js:24-26) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `d3_run` **pool.run({ sql })**: 메인 스레드가 일을 대기열에 넣는다. (`dbms/src/thread-pool.js:84-91`)
    - 분기 [계산 결과] `d3_b_busy` **대기열 초과 · 잠금 시간 초과 → 503**: API 서버가 오류 종류로 상태 코드를 고른다. → 요청 하나가 503 으로 거절된다 (`dbms/src/api.js:98-101`)
2. [실행·관측] `d3_dispatch` **쉬는 워커에게 배정**: 준비됐고 하는 일이 없는 워커에게 맨 앞의 일을 보낸다. (`dbms/src/thread-pool.js:34-41`)
3. [실행·관측] `d3_worker` **워커가 자기 엔진으로 실행**: 엔진은 Phase 1 + 2 코드 그대로다 (카드 D1). (`dbms/src/db-worker.js:19-23`)
4. [제한·상수] `d3_lock` **잠금 잡기: Atomics 비교 후 교환**: 상태 정수 하나: 0 아무도 없음, n 읽는 워커 n개, -1 쓰는 워커 1개 (rw-lock.js:11). (`dbms/src/rw-lock.js:37-46`)
    - 분기 [실행·관측] `d3_b_wait` **못 잡으면 잠들었다가 다시**: 상태가 바뀌거나 시간이 지날 때까지 Atomics.wait 로 잔다. → INSERT 가 쓰는 동안 SELECT 워커는 잠든다 (`dbms/src/rw-lock.js:49-56`)
5. [실행·관측] `d3_catch` **잠금 안에서 따라잡기**: 다른 워커가 파일에 이어 쓴 뒷부분만 내 인덱스에 넣고 실행한다. (`dbms/src/engine.js:122-132`)
6. [계산 결과] `d3_done` **결과를 돌려주고 다음 일**: 워커가 쉬는 상태가 되면 바로 dispatch 로 다음 일을 가져간다. (`dbms/src/thread-pool.js:56-61`)
    - 분기 [실행·관측] `d3_b_dead` **워커가 죽음 → 그 일만 실패, 새 워커**: 자리를 같은 번호의 새 워커로 채운다. → 다른 요청은 계속 처리된다 (`dbms/src/thread-pool.js:69-73`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| SELECT 한 건 (쉬는 워커 있음) | d3_run → d3_dispatch → d3_worker → d3_lock → d3_catch → d3_done | 워커 하나가 읽기 잠금으로 실행하고 응답. |
| INSERT 와 SELECT 가 겹침 | d3_run → d3_dispatch → d3_worker → d3_lock → d3_b_wait → d3_catch → d3_done | 쓰는 동안 읽기는 잠들었다가, 깨어나 새 줄까지 따라잡고 읽는다. |
| 요청 폭주 | d3_run → d3_b_busy | 대기열 1000개를 넘으면 503. |
| 워커가 죽음 | d3_run → d3_dispatch → d3_worker → d3_b_dead | 그 요청만 실패, 자리는 새 워커로. |

**결과** SQL 요청마다 워커 하나가 배정돼 실행하고, 같은 테이블의 읽기는 함께, 쓰기는 혼자 들어가서 id 가 겹치지 않는다.

**코드에서 확인한 사실**

- 쓰기 잠금 안에서 catchUp → 가장 큰 id + 1 계산 → 파일 쓰기를 하므로 id 가 겹치지 않는다 (engine.js:127, 153, table.js:94)
- 잠금을 10초 안에 못 잡으면 LockTimeoutError → 503 (rw-lock.js:32, 52, db-worker.js:25, api.js:99)

**코드에서 도출한 예상**

- 워커마다 인덱스를 따로 가져서 인덱스 메모리가 워커 수만큼 든다

**실행 관측과 기존 기록값**

- 기존 기록값 (dbms/README.md:228-230, CPU 코어 16개, 100만 건): 선형 탐색 16개 동시 요청이 워커 1개 3,124 ms, 4개 1,357 ms. 이번에 다시 재지 않았다
- 2026-11-17 이번 실행: '클라이언트 300개가 동시에 INSERT 해도 id 가 겹치거나 빠지지 않는다'(dbms/src/__tests__/api.test.js:57), thread-pool.test.js 13개 통과

**미실행 · 미확인**

- 워커 8개 이상에서의 비교: 측정하지 않음

## M. 미니 리액트 화면 (`mini-react/, web/`)

브라우저 화면. 서버 응답을 state 로 받아 새 가상 DOM 을 만들고, 이전과 다른 곳만 실제 DOM 에 고친다.

<a id="card-m1"></a>

### M1. 리렌더: setState → batch → diff → effect

`mini-react/hooks.js, mini-react/root.js, web/app.js`

> setState 가 화면을 직접 고치는 것이 아니라, 새 가상 DOM 을 만들어 이전 것과 비교한 차이만 실제 DOM 에 적용한다.

**역할** 서버 응답이 화면 변경으로 이어지는 경로다. 끝말잇기 화면은 state 와 훅을 루트 컴포넌트 App 에만 둔다 (README.md:436).

**설계 의도와 자료구조를 고른 이유**

- batch(fn) 안에서 부른 setState 들은 fn 이 끝난 뒤 한 번만 리렌더한다 (hooks.js:15)
- useEffect 는 화면 반영(커밋)이 끝난 뒤 실행한다 (hooks.js:83, root.js:28)
- generation 값으로 이전 마운트에서 만든 setter 가 새 저장소를 건드리지 못하게 한다 (hooks.js:22)

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 가상 DOM(Virtual DOM) | Component.update 가 만드는 새 VDOM (root.js:24) |
| 배칭(Batching) | batch (hooks.js:63-72) |
| 훅 슬롯과 커서(Hook Slot, Cursor) | hooks 배열과 cursor (hooks.js:19-20, 46) |
| 부수 효과 정리(Cleanup) | flushEffects, cleanupEffects (hooks.js:95-124) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `m1_show` **서버 응답 → show(res)**: 판 상태, 마감 시각, trace, 안내 문구를 한 batch 안에서 바꾼다. (`web/app.js:314-319`)
2. [실행·관측] `m1_set` **setState: 값이 같으면 무시**: batch 안이면 리렌더를 예약만 한다. (`mini-react/hooks.js:50-57`)
    - 분기 [계산 결과] `m1_b_same` **같은 값 → 리렌더 없음**: Object.is 로 같으면 슬롯도 그대로다. → 변화 없음 (`mini-react/hooks.js:54`)
3. [제한·상수] `m1_batch` **batch: 끝난 뒤 한 번만**: setState 가 여러 번 불려도 리렌더는 한 번이다. (`mini-react/hooks.js:63-71`)
4. [실행·관측] `m1_commit` **새 VDOM 만들고 차이만 적용**: App() 을 다시 실행해 새 VDOM 을 만들고 diff 결과만 DOM 에 반영한다 (카드 M2). (`mini-react/root.js:22-28`)
5. [계산 결과] `m1_effect` **effect: 이전 정리 → 새 실행**: deps 가 바뀐 effect 만 대기열에 들어 있다. (`mini-react/hooks.js:100-106`)
    - 분기 [실행·관측] `m1_b_effectset` **effect 안에서 setState → 끝나고 한 번 더**: effect 실행 중의 setState 는 모아 두었다가 한 번만 리렌더한다. → 리렌더 +1 (`mini-react/hooks.js:110`)
    - 분기 [실행·관측] `m1_b_timer` **게임 시계 effect**: deadline 이 바뀌면 이전 0.2초 타이머를 지우고 새로 건다. → 이전 타이머 해제 → 새 마감으로 타이머 다시 (`web/app.js:351-361`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 단어를 받아들인 응답 | m1_show → m1_set → m1_batch → m1_commit → m1_effect | setState 5번 → 리렌더 1번 → 바뀐 DOM 만 수정. |
| 같은 값으로 setState | m1_show → m1_set → m1_b_same | 리렌더 없음. |
| effect 안에서 setState | m1_commit → m1_effect → m1_b_effectset | effect 를 다 돌린 뒤 리렌더를 한 번 더 한다. |
| 마감이 바뀜 → 시계 다시 | m1_show → m1_set → m1_batch → m1_commit → m1_effect → m1_b_timer | 이전 타이머를 지우고 새 마감으로 다시 건다. |

**결과** 서버 응답 하나에 setState 가 여러 번 불려도 리렌더는 한 번이고, 그 한 번에서 바뀐 DOM 노드만 수정된다.

**코드에서 확인한 사실**

- 훅은 루트 컴포넌트에서만 호출한다는 전제다 (hooks.js:16)
- 화면 시계는 마감 + 150ms 뒤에 서버에 묻기만 하고, 시간 초과 판정은 서버가 한다 (app.js:356-358)
- word-chain 의 npm 테스트 스크립트에 미니 리액트 테스트는 없다 (package.json 의 test, test:redis, test:dbms)

**코드에서 도출한 예상**

- App 은 루트라 REMOVE 패치로 지워지지 않으므로, 끝말잇기 화면에서 하위 트리를 지울 때 돌려야 할 cleanup 은 없다

**실행 관측과 기존 기록값**

- 이번에 실행한 관측 없음

**미실행 · 미확인**

- 브라우저에서 리렌더 횟수를 직접 센 확인: 하지 않음

### M2. diff · patch: 다섯 가지 패치

`mini-react/diff.js, mini-react/patch.js`

> 트리를 통째로 다시 그리는 것이 아니라, 같은 위치끼리 비교해 CREATE · REMOVE · REPLACE · TEXT · PROPS 다섯 종류의 패치만 만든다.

**역할** 새 VDOM 과 이전 VDOM 의 차이를 패치 목록으로 만들고(diff.js), 그 목록만 실제 DOM 에 적용한다(patch.js).

**설계 의도와 자료구조를 고른 이유**

- 패치 종류는 CREATE | REMOVE | REPLACE | TEXT | PROPS (diff.js:4)
- key 없이 같은 위치끼리 비교한다 (diff.js:7)
- diff 는 DOM 을 건드리지 않는 순수 함수이고, 적용은 patch.js 가 맡는다 (diff.js:2, patch.js:2)
- key 를 쓰지 않기로 한 이유는 소스에 없다 → 미확인

| CS 개념 | 이 코드에서 놓인 곳 |
|---|---|
| 트리 비교(Tree Diff) | diff 재귀 (diff.js:18-39) |
| 재조정(Reconciliation) | patchToVdom (patch.js:150-153) |
| 경로 주소(Path) | childNodes 번호 배열 (diff.js:5, patch.js:67) |

**동작 흐름** (분기는 갈라지는 단계 아래에 들여 씀)

1. [입력] `m2_in` **diff(이전 VDOM, 새 VDOM)**: path 는 루트에서 그 노드까지의 자식 번호 배열이다. (`mini-react/diff.js:18-19`)
2. (아니면) [계산 결과] `m2_create` **이전 없음 → CREATE · 새것 없음 → REMOVE**: 그 위치의 노드를 하위 트리째 만들거나 지운다. (`mini-react/diff.js:20-21`)
3. (아니면) [계산 결과] `m2_text` **둘 다 텍스트 → 다르면 TEXT**: 글자가 같으면 패치를 만들지 않는다. (`mini-react/diff.js:22-25`)
4. (아니면) [계산 결과] `m2_replace` **태그가 다르면 REPLACE**: 자식은 비교하지 않고 통째로 바꾼다. (`mini-react/diff.js:26-29`)
5. (아니면) [실행·관측] `m2_props` **같은 태그 → 속성 비교 후 자식으로**: 같은 번호의 자식끼리 diff 를 재귀로 부른다. (`mini-react/diff.js:30-35`)
    - 분기 [계산 결과] `m2_b_key` **key 가 없어서 생기는 일**: 목록 맨 앞에 항목을 끼우면 같은 번호끼리 비교하므로 뒤 항목들이 모두 바뀐 것으로 나온다. → TEXT · PROPS 패치가 목록 길이만큼 생길 수 있다 (도출) (`mini-react/diff.js:7`)
6. [실행·관측] `m2_rest` **남는 자식 처리**: 새 자식이 남으면 앞에서부터 CREATE, 이전 자식이 남으면 뒤에서부터 REMOVE. (`mini-react/diff.js:36-38`)
7. [계산 결과] `m2_apply` **실제 DOM 에 적용**: CREATE · REPLACE 는 createDom 으로 하위 트리 전체를 만든다. (`mini-react/patch.js:47-53`)

| 시나리오 | 지나는 단계 | 결과 |
|---|---|---|
| 남은 시간 글자만 바뀜 | m2_in → m2_props → m2_text → m2_apply | TEXT 패치 1개, 노드 1개만 수정. |
| 목록 끝에 단어 하나 추가 | m2_in → m2_props → m2_rest → m2_apply | CREATE 패치 1개. |
| 태그가 바뀜 | m2_in → m2_replace → m2_apply | REPLACE 패치 1개, 하위 트리째 교체. |
| 한쪽이 없음 | m2_in → m2_create → m2_apply | CREATE 또는 REMOVE 1개, 이 위치에서 비교 끝. |
| 목록 맨 앞에 끼우기 | m2_in → m2_props → m2_b_key | 뒤 항목들이 한 칸씩 밀려 여러 패치가 생긴다. |

**결과** 바뀐 위치마다 패치 하나가 생기고, applyPatches 가 그 위치의 DOM 노드만 만들거나 지우거나 고친다.

**코드에서 확인한 사실**

- CREATE 와 REPLACE 는 createDom 재귀로 하위 트리 전체를 만든다 (patch.js:47-53)
- 적용 뒤 결과 DOM 이 목표 VDOM 과 같은지 검증한다 (patch.js:122-126)

**코드에서 도출한 예상**

- REMOVE 에서 diff 가 그 아래로 내려가지 않아도, 노드를 지우면 하위 DOM 도 함께 사라진다

**실행 관측과 기존 기록값**

- 이번에 실행한 관측 없음

**미실행 · 미확인**

- 브라우저에서 패치 수를 직접 센 확인: 하지 않음

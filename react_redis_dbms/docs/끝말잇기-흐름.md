# 끝말잇기 동작 흐름 (한 장)

서버를 켜는 순간부터 단어 하나가 화면에 반영되기까지를 위에서 아래로 한 흐름으로 이었다. 번호는 본류 순서, `[ ]` 는 그 코드가 실행되는 서버, `↳` 는 분기, `↺` 는 앞에서 펼친 길을 다시 타는 곳이다. 겹치던 단계 12개는 남는 단계 안으로 합쳤다 (맨 아래 표).

색 구분: 입력(요청이나 데이터가 들어오는 단계), 제한·상수(TTL, 적재율, 잠금 시간처럼 정해 둔 값이 판단을 가르는 단계), 실행·관측(코드가 실행되거나 상태를 읽는 단계), 계산 결과(응답, 고른 번호, 바뀐 상태처럼 계산이 끝나 나온 값)

## ① 서버 켜기

> npm start 한 번에 server.js 가 DBMS → 레디스 → 게임 서버 순서로 켠다 (server.js:39-55).

1. [미니 DBMS] **DBMS 켜기: 워커마다 엔진을 연다** → 워커 스레드가 준비되고 4000번 포트가 열린다 (`server.js:39-41` · `dbms/src/api.js:68-74` · `dbms/src/db-worker.js:15`)
2. [미니 DBMS] **테이블을 열 때 인덱스 재구성** → 인덱스는 파일에 저장하지 않고 열 때마다 만든다 (`dbms/src/table.js:73-77`)
3. [미니 레디스] **레디스 켜기: 기록 파일 열기** → 아직 메모리는 비어 있음 (`server.js:43-45`)
4. [미니 레디스] **줄 단위로 읽기** → records: [{op:'set', key:'game:7', …}, …] (`redis/src/aof.js:28-36`)
    - ↳ 해석 안 되는 줄 → 거기서 멈춤 → 복구는 깨진 줄 앞까지 (`redis/src/aof.js:33`)
5. [미니 레디스] **기록을 순서대로 다시 실행** → 메모리에 꺼지기 직전의 키들이 돌아온다 (`redis/src/aof.js:84-87`)
6. [미니 레디스] **이미 지난 만료는 건너뜀** → 꺼져 있는 동안 10초가 지난 turn 키는 복구되지 않는다 → 켜자마자 시간 초과 (`redis/src/store.js:213-216`)
7. [미니 레디스] **살아 있는 키만 새 파일로 교체** → 파일에는 살아 있는 키의 set 줄만 남는다 (`redis/src/aof.js:54-62`)
8. [미니 레디스] **주기 삭제 타이머 켜기 (0.1초)** → 타이머가 돌기 시작 (`redis/src/store.js:240-244`)
9. [게임 서버] **게임 서버 켜기: 단어 캐시 비우기** → 브라우저로 http://127.0.0.1:3000 을 열 수 있다 (`server.js:50-55`)

**결과** DBMS 워커는 인덱스를 다시 세우고, 레디스는 기록 파일로 꺼지기 직전 키를 되살린 뒤 주기 삭제 타이머를 건다. 게임 서버는 단어 캐시를 비우고 포트를 연다.

## ② 판 시작

> 브라우저의 '시작' 이 POST /api/games 로 들어온다. 레디스 명령과 DBMS 질의가 처음 지나가는 곳이라 두 서버의 안쪽 길을 여기서 펼친다.

10. [게임 서버] **판 시작: POST /api/games → 판 번호 INCR** → 예: game:seq 6 → 7, 판 7 의 상태 객체가 게임 서버 메모리에 생김 (`game/server.js:84-86` · `game/service.js:256-262`)
11. [게임 서버] **클라이언트가 명령을 HTTP 로 보낸다** → 요청 여러 개가 거의 동시에 서버에 도착 (`redis/src/client.js:51-56`)
12. [미니 레디스] **본문 읽기까지만 비동기** → 본문이 다 온 요청부터 하나씩 execute 로 들어간다 (`redis/src/api.js:108-113`)
13. [미니 레디스] **execute 가 명령 하나로 바꿔 실행** → store 명령 하나가 처음부터 끝까지 이어서 실행된다 (`redis/src/api.js:97`)
14. [미니 레디스] **읽고 → 더하고 → 쓰기를 한 함수 안에서** → 예: game:seq 6 → 7 (`redis/src/store.js:148-156`)
    - ↳ 정수가 아닌 값 → 400 → 값은 그대로, 응답 400 (`redis/src/api.js:114-118`)
15. [미니 레디스] **응답 { value }** → 판 번호가 겹치지 않는다 (`redis/src/api.js:120-122`)
16. [게임 서버] **라운드 열기 openRound** → 시작 단어를 뽑는 중 (`game/service.js:228-230`)
17. [게임 서버] **시작 단어 뽑기: WHERE id = 무작위 번호** → 예: SELECT word FROM words WHERE id = 163947 를 DBMS 로 보낸다 (`game/service.js:213-217`)
18. [게임 서버] **game/db.js: SQL 을 HTTP 로 보낸다** → DBMS 스레드 풀의 워커 하나가 배정된다 (`game/db.js:42-44`)
19. [미니 DBMS] **POST /query { sql }** → 워커 안에서 engine.execute(sql) 시작 (`dbms/src/api.js:84-87`)
20. [미니 DBMS] **pool.run({ sql })** → queue: [{ id: 42, payload: { sql } }] (`dbms/src/thread-pool.js:84-91`)
    - ↳ 대기열 초과 · 잠금 시간 초과 → 503 → 요청 하나가 503 으로 거절된다 (`dbms/src/api.js:98-101`)
21. [미니 DBMS] **쉬는 워커에게 배정** → 워커 2번이 일 42를 받는다 (`dbms/src/thread-pool.js:34-41`)
22. [미니 DBMS] **워커가 자기 엔진으로 실행** → engine.execute(sql) 시작 (`dbms/src/db-worker.js:19-23`)
23. [미니 DBMS] **문장 나누기 → 파싱 → 실행** → AST: { type: 'select', table: 'words', where: [...] } (`dbms/src/engine.js:236-240`)
24. [미니 DBMS] **테이블 · 컬럼 · 타입 확인** → conds: [{ index: 1, op: '=', value: '기차' }] (`dbms/src/engine.js:159-167`)
    - ↳ SQL 오류 → 400, 그 문장에서 멈춤 → 워커가 kind 'sql' 로 알리고 API 가 400 으로 답한다 (`dbms/src/engine.js:241-243`)
25. [미니 DBMS] **읽는 방법 고르기** → id = 163947 → INDEX_POINT (`dbms/src/engine.js:76-79`)
    - ↳ id 범위 → INDEX_RANGE, 그 밖 → FULL_SCAN → WHERE word = '기차' → FULL_SCAN (`dbms/src/engine.js:88-89`)
26. [미니 DBMS] **읽기 잠금 → 따라잡기 → 읽기** → 찾은 레코드 배열 (`dbms/src/engine.js:183-193`)
27. [미니 DBMS] **잠금 잡기: Atomics 비교 후 교환** → SELECT: state 0 → 1 (`dbms/src/rw-lock.js:37-46`)
    - ↳ 못 잡으면 잠들었다가 다시 → INSERT 가 쓰는 동안 SELECT 워커는 잠든다 (`dbms/src/rw-lock.js:49-56`)
28. [미니 DBMS] **잠금 안에서 따라잡기** → 내 인덱스가 파일 끝까지 따라잡은 상태에서 실행 (`dbms/src/engine.js:122-132`)
29. [미니 DBMS] **SELECT … WHERE id = ? : 루트에서 리프까지** → 높이 4 면 노드 4개를 거친다 (`dbms/src/bplus-tree.js:53-57`)
    - ↳ 범위 검색: 리프의 next 를 따라감 → WHERE id >= 10 AND id < 20 → 10~19 (`dbms/src/bplus-tree.js:118-124`)
30. [미니 DBMS] **offset 위치의 한 줄만 읽기** → [163947,"기차",…] 한 줄 (`dbms/src/table.js:124-127`)
31. [미니 DBMS] **결과: plan, columns, rows** → { plan: 'INDEX_POINT', columns: ['word'], rows: [['기차']] } (`dbms/src/engine.js:211-215`)
32. [미니 DBMS] **결과를 돌려주고 다음 일** → 메인 스레드가 200 { results, worker } 응답 (`dbms/src/thread-pool.js:56-61`)
    - ↳ 워커가 죽음 → 그 일만 실패, 새 워커 → 다른 요청은 계속 처리된다 (`dbms/src/thread-pool.js:69-73`)
33. [게임 서버] **판 상태 30분 · turn 키 10초 저장** → game:7:used:<시작 단어>, game:7 (30분), game:7:turn (10초) (`game/service.js:234-237`)
- ↺ [미니 레디스] SET 도 11~13단계 길로 들어온다: PUT /keys/:key → store.set
34. [미니 레디스] **ttl 과 함께 저장** → data: game:7:turn → 1, expires: game:7:turn → 지금 + 10000 (`redis/src/store.js:87-89`)
35. [미니 레디스] **키와 값이 들어온다** → 같은 키가 없으면 다음 단계로, 아직 바뀐 것 없음 (`redis/src/hash-table.js:59-61`)
    - ↳ 같은 키가 이미 있음 → size 그대로, 값만 교체 (`redis/src/hash-table.js:61`)
36. [미니 레디스] **FNV-1a 로 해시값 계산** → 'game:7' → 1180080784 (원본 함수로 계산한 값) (`redis/src/hash-table.js:26-33`)
37. [미니 레디스] **버킷 번호 = 해시값 & (capacity − 1)** → capacity 16: 1180080784 & 15 = 0 → 0번 버킷 (`redis/src/hash-table.js:46-48`)
38. [미니 레디스] **버킷 맨 앞에 노드를 끼운다** → 0번 버킷: game:7 → null, size 1 (`redis/src/hash-table.js:62-64`)
    - ↳ 다른 키와 같은 버킷 (충돌) → 5번 버킷: word:기차 → game:7:turn → null (`redis/src/hash-table.js:63`)
39. [미니 레디스] **적재율 0.75 검사** → size 1, capacity 16 → 적재율 0.0625, 늘리지 않음 (`redis/src/hash-table.js:65-66`)
    - ↳ 적재율 초과 → resize(capacity × 2) → 13번째 키에서 16 × 0.75 = 12 를 넘어 32칸으로 늘어난다 (`redis/src/hash-table.js:101-114`)
40. [미니 레디스] **쓰기 명령마다 한 줄** → 운영체제 버퍼에 한 줄 추가 (`redis/src/aof.js:48-51`)
    - ↳ fsync = always → 손실 범위는 줄고 쓰기는 느려진다 (`redis/src/aof.js:50`)

**결과** 판 번호는 INCR 로 겹치지 않게 받고, 시작 단어는 B+ 트리로 한 줄만 읽어 찾는다. 판 상태와 turn 키는 해시 테이블 버킷에 들어가고 기록 파일에 한 줄씩 남는다.
